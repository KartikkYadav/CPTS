# File Upload Vulnerabilities — Absent Validation

## 1. Absent Validation

**Absent validation** occurs when a web application has **no validation/filtering on uploaded files**.

### Impact
If no restrictions exist, an attacker may be able to upload:

- Web shells
- Server-side scripts
- Reverse-shell scripts
- Other executable files

If the uploaded file is stored in a web-accessible directory and executed by the server, this can lead to **Remote Code Execution (RCE)** and potentially full server compromise.

---

## 2. Arbitrary File Upload

### Initial Testing

When testing a file-upload function, check whether the application:

- Specifies allowed file extensions
- Restricts MIME types
- Restricts file content
- Renames uploaded files
- Prevents execution of uploaded files
- Stores uploads outside the web root

### Front-End Indicators

Possible indicators of missing restrictions:

- Upload form accepts arbitrary extensions such as `.php`
- File selector shows **All Files**
- No message specifies allowed file types
- Application accepts files without apparent filtering

> **Important:** Front-end restrictions are not sufficient. Always test the **server-side validation**, since client-side controls can often be bypassed.

---

# 3. Identifying the Web Framework

Before uploading a server-side payload, determine **which language/framework processes the uploaded file**.

A web shell generally needs to be written in the same server-side language used by the application.

### Common Extensions

| Extension | Technology |
|---|---|
| `.php` | PHP |
| `.asp` | Classic ASP |
| `.aspx` | ASP.NET |
| `.jsp` | Java/JSP |

### Manual Method

Try common `index` extensions:

```text
/index.php
/index.asp
/index.aspx
/index.jsp
```

Example:

```text
http://SERVER_IP:PORT/index.php
```

If `/index.php` loads the same application, this is a strong indication that the application uses **PHP**.

### Limitations

This technique is **not always reliable** because:

- The application may not use an `index` file.
- Web frameworks may use routes instead of file extensions.
- Multiple technologies may be used.
- Uploaded files may not be directly accessible through normal routes.

---

## 4. Technology Fingerprinting

### Wappalyzer

**Wappalyzer** can identify technologies used by a web application, including:

- Web server
- Programming language
- Framework
- Operating system
- JavaScript libraries
- Other technologies

It is useful for quickly fingerprinting the target, but manual identification techniques should also be understood.

### Web Scanners

Other options include:

- Burp Suite scanners
- OWASP ZAP
- Web vulnerability assessment tools

# 5. Vulnerability Identification

Once the server-side language is identified, test whether files using that extension can actually be **executed**.

### PHP Example

Create a harmless test file:

```php
<?php echo "Hello HTB";?>
```

Save it as:

```text
test.php
```

Upload it through the application's file-upload functionality.

### Expected Results

If the application reports:

```text
File successfully uploaded
```

then locate/access the uploaded file, for example:

```text
/uploads/test.php
```

If the browser displays:

```text
Hello HTB
```

then the server **executed the PHP code**.

This demonstrates:

```text
File Upload
     ↓
PHP file accepted
     ↓
File stored in web-accessible location
     ↓
PHP interpreted by server
     ↓
Server-side code execution
```

### Source Code vs Execution

If PHP execution is **not** enabled, the browser may display the PHP source code instead of executing it.

**Executed:**

```text
Hello HTB
```

**Not executed:**

```php
<?php echo "Hello HTB";?>
```

---

# 6. Key Takeaways

- **Absent validation** = application accepts uploaded files without adequate server-side restrictions.
- Never rely only on client-side upload restrictions.
- Identify the **server-side language/framework** before testing executable uploads.
- Common identification methods:
  - Try common file extensions
  - Wappalyzer
  - Burp/ZAP
  - Other technology fingerprinting tools
- A successful upload **does not automatically mean RCE**.
- To confirm executable upload, upload a **harmless test script** and verify whether the server executes it.
- The most important conditions for exploitation are:
  1. Arbitrary file upload is possible.
  2. The uploaded file is stored somewhere accessible.
  3. The server interprets the uploaded file as executable code.

### Exam Mental Model

```text
Can I upload arbitrary files?
        ↓
What server-side language is used?
        ↓
Can I upload that language's file extension?
        ↓
Where is the file stored?
        ↓
Can I access the uploaded file?
        ↓
Does the server execute it?
        ↓
Potential server-side code execution
```
