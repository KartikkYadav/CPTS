# Command Injection Prevention


---

## Overview

Preventing command injection requires combining: avoiding risky system-command functions, validating input, sanitizing input, and securely configuring the server.

---

## System Commands

- **Avoid functions that execute system commands**, especially with user input — even *indirect* user influence can lead to injection.
- Prefer **built-in secure functions** over shelling out.
  - Example: to check if a host is alive in PHP, use `fsockopen` instead of `system("ping ...")`.
- If a system command is unavoidable (no built-in alternative):
  - **Never** pass raw user input directly into it.
  - Always **validate and sanitize** first.
  - Minimize use of these functions overall.

---

## Input Validation

- Ensure input **matches the expected format**; deny the request if not.
- Must be done **both on front-end and back-end** (front-end-only validation is insufficient — seen in the example app).

### PHP — Built-in Filters

```php
if (filter_var($_GET['ip'], FILTER_VALIDATE_IP)) {
    // call function
} else {
    // deny request
}
```

### Custom Formats — Regex

```php
preg_match(...)
```

### JavaScript (front-end or NodeJS back-end)

```javascript
if(/^(25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.(25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.(25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.(25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)$/.test(ip)){
    // call function
}
else{
    // deny request
}
```

- NodeJS can also use libraries like **`is-ip`** (`npm install is-ip` → `isIp(ip)`).
- Other languages (.NET, Java) have their own validation mechanisms — consult their docs.

---

## Input Sanitization

- **Most critical** step for preventing injection: remove unnecessary special characters from input.
- Performed **after** validation — validation can still fail (e.g., bad regex), so sanitization is a required second layer.
- **Blacklisting specific words/characters is not sufficient** (as demonstrated throughout this module) — prefer built-in sanitization functions.

### PHP — `preg_replace`

```php
$ip = preg_replace('/[^A-Za-z0-9.]/', '', $_GET['ip']);
```

- Keeps only alphanumeric characters and `.` (suitable for IPs); strips everything else.

### JavaScript

```javascript
var ip = ip.replace(/[^A-Za-z0-9.]/g, '');
```

### NodeJS — DOMPurify

```javascript
import DOMPurify from 'dompurify';
var ip = DOMPurify.sanitize(ip);
```

### When Special Characters Must Be Allowed (e.g., comments)

- PHP: `filter_var` with the **`escapeshellcmd`** filter to escape special characters.
- NodeJS: `escape(ip)`.
- **Caution:** escaping (rather than removing) is **not considered fully secure** — as shown throughout this module, it can often be bypassed.

## Server Configuration

Reduce impact if the web server is compromised:

- Use the web server's **built-in WAF** (e.g., Apache `mod_security`) **plus** an external WAF (Cloudflare, Fortinet, Imperva, etc.).
- Follow the **Principle of Least Privilege (PoLP)** — run the web server as a low-privileged user (e.g., `www-data`).
- **Disable risky functions** at the language level (e.g., PHP `disable_functions=system,...`).
- **Restrict filesystem scope** accessible to the app (e.g., PHP `open_basedir = '/var/www/html'`).
- **Reject double-encoded requests** and non-ASCII characters in URLs.
- **Avoid sensitive/outdated libraries and modules** (e.g., PHP CGI).

---

## Key Takeaways

- Defense in depth: avoid risky functions → validate → sanitize → secure server config.
- Blacklists and escaping alone are insufficient — this entire module demonstrated how they get bypassed.
- Even with all mitigations in place, **penetration testing is still necessary** — large codebases mean a single mistake anywhere can reintroduce the vulnerability.
- Secure coding best practices **complement**, not replace, thorough pentesting.
