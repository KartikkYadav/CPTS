# **Introduction to Attacking Common Applications**

## **Overview**

- Web applications are common targets in both **internal and external penetration tests**.
- Applications may be vulnerable due to:
  - Outdated software and unpatched versions
  - Misconfigurations
  - Weak/default credentials
  - Vulnerable plugins, themes, or extensions
  - Abusable built-in functionality
  - Publicly known vulnerabilities (CVEs)

## **Web Application Architecture**

- **Front-end:** Client-side components rendered in the browser.
- **Back-end:** Server-side application code, databases, and processing logic.
- Most web applications follow a **client-server architecture**.

## **Common Attack Opportunities**

- SQL Injection (SQLi)
- Cross-Site Scripting (XSS)
- Remote Code Execution (RCE)
- Local File Read
- Unrestricted File Upload
- Credential abuse
- Misconfigured administrative functionality
- Exploitation of built-in features to execute commands/scripts

> **Exam takeaway:** Don't focus only on CVEs. Investigate application functionality, permissions, default credentials, and features that may allow code execution.

## **Application Enumeration Mindset**

When discovering a web application:

1. **Identify the application and version.**
2. Search for known vulnerabilities and CVEs.
3. Check for default or weak credentials.
4. Enumerate exposed functionality.
5. Inspect plugins, modules, extensions, and integrations.
6. Look for administrative interfaces.
7. Identify features that can execute scripts, commands, or upload files.
8. Check for sensitive information disclosure.
9. Determine the privileges of the application service account.

> **Key principle:** Learn how an application works and identify how its functionality can be abused—not just how to run a public exploit.

## **Example: Nexus Repository OSS**

Potential attack paths encountered during assessments:

- Default credentials: `admin:admin123`
- Abuse authenticated API functionality.
- Abuse the **Tasks** functionality to execute scripts.
- Use Groovy scripts to achieve RCE when applicable.

**Lesson:** Default credentials and built-in administrative functionality can provide RCE even when no public exploit is immediately available.

## **HTB Lab Target Configuration**

HTB uses virtual hosts (Vhosts) to host different applications on the same target IP.

### **Add Vhosts to&#x20;**`/etc/hosts`

```
IP=10.129.42.195

printf "%s\t%s\n\n" "$IP" \
"app.inlanefreight.local dev.inlanefreight.local blog.inlanefreight.local" \
| sudo tee -a /etc/hosts
```

### **Verify**

```
cat /etc/hosts
```

Example entry:

```
10.129.42.195 app.inlanefreight.local dev.inlanefreight.local blog.inlanefreight.local
```

**Why?**

- Multiple applications may share the same IP.
- The web server uses the **Host header / hostname** to route requests to the correct Vhost.
- Accessing only the IP may return the wrong application.

> **Exam tip:** When a target uses domain names, add discovered Vhosts to `/etc/hosts` before browsing or enumerating them.

If you spawn a target during a section and cannot access it directly via the FQDN be sure to check your hosts file and update any entries!

Module exercises that require vhosts will display a list that you can use to edit your hosts file after spawning the target VM at the bottom of the respective section.
