# GitLab – Discovery & Enumeration (CPTS Notes)

## Overview
- **GitLab** — web-based **Git repository hosting** platform with wiki, issue tracking, and **CI/CD pipeline** functionality
- Open-source; originally written in **Ruby**, current stack: **Go, Ruby on Rails, Vue.js**
- Launched **2014**; now a **1,400-person company** with **$150M revenue (2020)**
- Free + open-source core, with a **paid enterprise version**
- Comparable to **GitHub** and **BitBucket**

### Stats
- **1,466 employees**
- **30M+ registered users** across **66 countries**
- Publishes internal procedures/OKRs publicly
- Notable users: **Drupal, Goldman Sachs, HackerOne, Ticketmaster, Nvidia, Siemens**

### Pentest Relevance
- Common to find **company GitHub/GitLab/BitBucket repos** during internal & external pentests
- Repos may contain:
  - **Cleartext secrets** (passwords, API keys) accidentally committed
  - **SSH private keys**
  - Scripts/configs with credentials
- Repository visibility levels:
  - **Public** — no auth required
  - **Internal** — any authenticated user
  - **Private** — restricted to specific users
- **2FA is disabled by default**
- Some GitLab instances allow **open self-registration** — a major risk if not restricted to company email domains or admin-approved

## Footprinting & Discovery

### Identifying GitLab
Simply browse to the instance — redirected to login page with GitLab branding:
```
http://gitlab.inlanefreight.local:8081/users/sign_in
```

### Version Fingerprinting
- **Only reliable way:** browse to `/help` **while logged in**
- If registration is open → register an account → check `/help`
- If registration is closed and no other way to determine version (dates on page, first public commit, etc.) exists:
  - **Do not blindly fire exploits** at the app
  - Stick to **hunting for secrets** instead
- Known serious past vulnerabilities affected:
  - GitLab **12.9.0**
  - GitLab **11.4.7**
  - GitLab CE **13.10.3, 13.9.3, 13.10.2**

## Enumeration

### 1. Browse `/explore` (No Auth Required)
```
http://gitlab.inlanefreight.local:8081/explore
```
- Lists public **projects, groups, snippets**
- Example finding: a project called "Inlanefreight dev" — may be a throwaway/example repo, but **always worth digging through**
- Explore linked pages: **groups, snippets, help**; also use **search** to find more projects

### 2. Account Registration (Key Technique)
```
http://gitlab.inlanefreight.local:8081/users/sign_up
```
- If sign-up isn't properly restricted (company email only / admin approval), **anyone can register and log in**
- Once registered → may gain access to **internal** (not just public) projects

### 3. Username/Email Enumeration via Registration Form
- Attempting to register a **taken username** → error: *"Username is already taken"*
  - Confirmed example: `root` is taken
- Attempting to register with a **taken email** → error: *"Email has already been taken"*
- **Important:** This enumeration works **even if Sign-up is disabled** in settings — the `/users/sign_up` page itself remains browsable for enumeration purposes (registration is just blocked, not page access)
- Build a valid user list this way → feed into:
  - Password guessing / spraying
  - Credential reuse checks against breach dumps (e.g., via **Dehashed**, as seen in osTicket examples)

### Mitigations (worth noting for reports)
- Enforce **2FA** on all accounts
- Use **Fail2Ban** to block brute-force attempts
- **Restrict IP access** if the instance must be internet-facing

## Example Walkthrough: Registering & Finding Internal Data

1. Register with example creds: `hacker:Welcome`
2. Immediately logged in → redirected to projects dashboard
3. Revisit `/explore` → now see additional **internal** project: "Inlanefreight website"
4. Investigate repo — in this case just a static site, but:
   - If the app were **dynamic (e.g., PHP)**, source code could be downloaded and reviewed for:
     - Vulnerabilities
     - Hidden functionality
     - Hardcoded credentials or other secrets

> Real-world engagements can yield substantial sensitive data once repo access is gained — referenced further in external research on GitLab/GitHub secret-hunting.

## Key Takeaways
- GitLab doesn't need to be directly "exploitable" to be valuable — **enumeration and secret-hunting** are often more productive than chasing CVEs
- Always check:
  1. `/explore` for public projects (no auth needed)
  2. `/help` for version (if you can log in)
  3. `/users/sign_up` for **open registration** and **username/email enumeration** (works even when sign-up is officially disabled)
- Register if possible → re-check `/explore` for newly visible **internal** projects
- This is especially valuable on **external pentests** where attack surface is otherwise limited
- May need to **combine findings across multiple sources** (GitLab + other recon) to build a full attack chain
