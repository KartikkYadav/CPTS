# Application Discovery & Enumeration

**Module:** HTB Academy (Attacking Enterprise Applications track)

---

## Why Application Discovery Matters

- Orgs should maintain a continuously updated **asset inventory**: devices, installed software, applications — local or third-party hosted, patch level, EOL status, rogue/"shadow IT" apps.
- Should ensure apps use **strong non-default credentials**, ideally **MFA**, and restrict admin portals to specific IPs/localhost where possible.
- Reality: many orgs have **poor visibility** into their own network — pentest enumeration directly helps build/improve their asset inventory.

### What We Typically Find
- Forgotten applications.
- Expired trial software that silently drops to an **unauthenticated** mode (e.g., Splunk free license behavior).
- Default/weak credentials.
- Unauthorized/misconfigured applications.
- Apps with known public vulnerabilities.

- Deliverable value: report findings (e.g., `admin:admin` on App X), appendices mapping services→hosts, supplemental scan data — and optionally **educate the client** on the tools used so they can self-assess proactively.

---

## General Methodology

1. **Ping sweep** → identify live hosts.
2. **Targeted port scan** → common web ports first.
3. **Deeper port scan** → full/top-N ports as time allows.
4. **Screenshot/triage web services** at scale (EyeWitness/Aquatone) rather than browsing manually — manual browsing doesn't scale past a handful of hosts.

### Example Initial Web-Discovery Scan

```bash
nmap -p 80,443,8000,8080,8180,8888,10000 --open -oA web_discovery -iL scope_list
```

- Iterative process: after reviewing screenshot results, may follow up with a **top 10,000 ports** or **all TCP ports** scan, then re-run screenshotting against the new results for full coverage.
- On **non-evasive full-scope** tests, a **Nessus scan** is often run too — but manual methodology must not depend solely on scanners. **Human-driven manual testing finds the most unique/severe issues.**
- All scanning is an **input to manual validation**, never a substitute for it.

## Getting Organized — Notetaking Structure

- Pick a notetaking tool (OneNote, Evernote, Notion, Cherrytree, etc.) — personal preference, but **be consistent** and build reusable templates per assessment type.
- **Always timestamp scans**, save raw output + exact scan syntax + targeted hosts — useful if the client asks about observed activity later.
- Build the **report skeleton** alongside the notebook at the start of the engagement — fill sections in while waiting on scans, saves time at the end.

### Example Notebook Structure (External Pentest)

```
External Penetration Test - <Client Name>
├── Scope (IPs/ranges, URLs, fragile hosts, testing windows, limitations)
├── Client Points of Contact
├── Credentials
├── Discovery/Enumeration
│   ├── Scans
│   ├── Live hosts
│   ├── Application Discovery
│   │   ├── Scans
│   │   └── Interesting/Notable Hosts
├── Exploitation
│   ├── <Hostname or IP>
│   └── <Hostname or IP>
└── Post-Exploitation
    ├── <Hostname or IP>
    └── <Hostname or IP>
```

## Example Walkthrough — INLANEFREIGHT.LOCAL

### Scope List (Example)

```
app.inlanefreight.local
dev.inlanefreight.local
drupal-dev.inlanefreight.local
gitlab-dev.inlanefreight.local
jenkins.inlanefreight.local
web01.inlanefreight.local
support-dev.inlanefreight.local
inlanefreight.local
10.129.201.50
...
```

### Initial Web-Port Scan

```bash
sudo nmap -p 80,443,8000,8080,8180,8888,10000 --open -oA web_discovery -iL scope_list
```

**Findings to note:**
- `app-dev.inlanefreight.local` — multiple web ports open (80, 8000, 8009, 8080, 8180, 8888) — Linux likely.
- `10.129.201.50` — ports suggest **Windows** (135, 139, 445, 3389 alongside web ports).
- **`dev`-named hosts** are worth flagging — may run untested features / debug mode.
- Generic names like `app.inlanefreight.local` need further enumeration to identify the actual running app.
- `gitlab-dev.inlanefreight.local` → add to **"interesting hosts"** list: GitLab often allows self-registration without admin approval, repos/commit history may leak credentials.

### Deeper Service Scan on a Single Host

```bash
sudo nmap --open -sV 10.129.201.50
```

```
80/tcp   open  http          Microsoft IIS httpd 10.0
8000/tcp open  http          Splunkd httpd
8080/tcp open  http          Indy httpd (Paessler PRTG bandwidth monitor)
8089/tcp open  ssl/http      Splunkd httpd (free license; remote login disabled)
```

- Reveals **IIS, Splunk (x2 ports), PRTG Network Monitor** all on one host — doing this host-by-host across hundreds/thousands of hosts is impractical → screenshotting tools solve this.

## Tool: EyeWitness

- Takes **Nmap or Nessus XML** output → screenshots every web app found (via Selenium).
- Also **categorizes/fingerprints** apps and **suggests default credentials** where applicable.
- Can take a plain host/URL list too; supports DNS resolution, custom ports, prepending `http(s)://`.

### Install

```bash
sudo apt install eyewitness
# or clone repo -> Python/setup/setup.sh
# Docker and Windows (via Visual Studio build) versions also exist
```

### Run

```bash
eyewitness --web -x web_discovery.xml -d inlanefreight_eyewitness
```

```
Starting Web Requests (26 Hosts)
Attempting to screenshot http://app.inlanefreight.local
...
Finished in 57.86 seconds
[*] Done! Report written in .../inlanefreight_eyewitness folder!
```

## Tool: Aquatone

- Similar purpose to EyeWitness; takes a host list or Nmap XML (`-nmap` flag). Actively maintained fork exists — check repo for current install steps.

### Install (Precompiled Binary)

```bash
wget https://github.com/michenriksen/aquatone/releases/download/v1.7.0/aquatone_linux_amd64_1.7.0.zip
unzip aquatone_linux_amd64_1.7.0.zip
# optionally move to a $PATH directory, e.g. /usr/local/bin
```

### Run

```bash
cat web_discovery.xml | ./aquatone -nmap
```

```
Targets    : 65
Ports      : 80, 443, 8000, 8080, 8443
http://app.inlanefreight.local/: 200 OK
http://jenkins.inlanefreight.local/: 403 Forbidden
...
Screenshots: Successful: 65 / Failed: 0
Wrote HTML report to: aquatone_report.html
```

- Also clusters similar-looking pages and generates a full HTML report with timing/request stats.

## Interpreting the Report

- Reports are typically organized into categories — **High Value Targets** listed first (most "juicy").
- **Large environments (500–5,000+ hosts)** can produce massive reports (hundreds of pages) — still worth reviewing in full; interesting hosts can be buried deep.
- **Real example (from the module author):** found a **ManageEngine OpManager** instance deep in a large report, still on default creds `admin:admin`, exposed to the internet. Logged in → RCE via PowerShell script → app was running as a **Domain Admin** account → full internal network compromise.

### Application-Specific Triage Tips

| App Seen | Why It Matters |
|---|---|
| **Apache Tomcat** | Try default creds on `/manager` and `/host-manager` — if accessible, upload a malicious **WAR file** → RCE via JSP (covered later in the module) |
| **Custom web apps / main company site** | Wide vulnerability surface; check for an underlying CMS (WordPress, Joomla, Drupal) |
| **osTicket (support ticketing)** | History of severe vulns; may allow login/data access; if social engineering in scope, could enable registering a valid company-domain email → pivot to other services (see HTB box *Delivery* by IppSec) |

- **Discipline reminder:** stay in information-gathering mode — don't start attacking hosts immediately upon finding something interesting. Note it down and keep reviewing; premature attacking risks missing something more critical later in the list.

### Typical App Mix by Engagement Type

**External Pentest:** custom apps, CMS platforms, Tomcat/Jenkins/Splunk, RDS, SSL VPN, OWA/O365, edge device login pages.

**Internal Pentest:** similar, plus printer login pages (sometimes leak cleartext LDAP creds), ESXi/vCenter, iLO/iDRAC, network/IoT devices, IP phones, internal code repos, SharePoint/intranet portals, security appliances.

### Real Example — Unvalidated File Upload

- Found a lone page: "Please only upload .zip and .tar.gz files."
- Tested anyway (in-scope) → uploaded a `.aspx` file → **no validation at all**, file uploaded successfully.
- Directory brute-forced → found `/files` with **directory listing enabled** → located the uploaded test file.
- Uploaded a proper `.aspx` webshell → **foothold into the internal environment**.
- Lesson: **leave no stone unturned** — even a single oddly-worded upload page can be a goldmine.

## Key Takeaways

- Application discovery at scale **requires automated screenshotting** (EyeWitness/Aquatone) — manual browsing doesn't scale beyond a handful of hosts.
- Feed these tools raw **Nmap/Nessus/Masscan XML** — avoid manually re-typing host/port lists.
- Treat scanner output as a **lead generator for manual testing**, never a final verdict — the most severe findings usually come from manual follow-up.
- Build a **consistent notetaking structure** (Scope → Discovery → Application Discovery → Exploitation → Post-Exploitation) from day one of every engagement — pays off heavily at report-writing time.
- Watch for recurring high-value app types: **Tomcat, Jenkins, Splunk, GitLab, osTicket, ManageEngine, PRTG** — each has well-known default-credential or vulnerability patterns worth checking immediately.
- Internal vs. external engagements tend to surface different but overlapping app categories — know what's "normal" to expect for each so anomalies stand out.
