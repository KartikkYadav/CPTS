# Pivoting, Tunneling, and Port Forwarding — Dynamic Port Forwarding with SSH and SOCKS Tunneling

**Module:** HTB Academy – Pivoting, Tunneling, and Port Forwarding

---

## Port Forwarding — Concept

- **Port forwarding:** redirects a communication request from one port to another.
- Uses **TCP** as the primary transport; can be encapsulated via application-layer protocols like **SSH**, or non-application-layer like **SOCKS**.
- Useful for **bypassing firewalls** and leveraging an existing compromised host's services/access to pivot into other networks.

---

## SSH Local Port Forwarding

**Scenario:** Attack host (10.10.15.x) ↔ compromised Ubuntu server (10.129.x.x) with a local-only MySQL service on port 3306.

### Step 1 — Scan the Pivot Target

```bash
nmap -sT -p22,3306 10.129.202.64
```
```
PORT     STATE  SERVICE
22/tcp   open   ssh
3306/tcp closed mysql
```

- MySQL shows **closed** externally — it's bound to localhost on the target, so not directly reachable. SSH is open — usable as the forwarding mechanism.

### Step 2 — Forward Local Port to Remote Service

```bash
ssh -L 1234:localhost:3306 ubuntu@10.129.202.64
```

- `-L` = local port forward: requests the SSH server forward data sent to local port **1234** → `localhost:3306` **on the remote (Ubuntu) server**.
- Result: MySQL becomes reachable at `localhost:1234` on your **attack host**.
- Benefit: enables running remote exploits against the MySQL service **as if it were local**, which wouldn't otherwise be possible since it's bound to localhost on the target.

### Step 3 — Confirm the Forward

```bash
netstat -antp | grep 1234
# tcp  127.0.0.1:1234  LISTEN  ssh
```

```bash
nmap -v -sV -p1234 localhost
# 1234/tcp open  mysql  MySQL 8.0.28-...
```

### Forwarding Multiple Ports at Once

```bash
ssh -L 1234:localhost:3306 -L 8080:localhost:80 ubuntu@10.129.202.64
```

- Chain multiple `-L local_port:server:remote_port` flags in one SSH command.

## Setting Up to Pivot — Identifying Dual-Homed Hosts

```bash
ifconfig
```

On the compromised Ubuntu host (`WEB01`):
- `ens192` → `10.129.202.64` (connects back to attack host's network)
- `ens224` → `172.16.5.129` (connects to a **separate, otherwise unreachable** internal network)
- `lo` → loopback

→ This host is **dual-homed** and can bridge into `172.16.5.0/23`.

## Dynamic Port Forwarding via SOCKS

- Problem: unlike the MySQL example, you often **don't know** what services exist on the far-side network (`172.16.5.0/23`) — and your attack host has **no route** there directly.
- Solution: **dynamic port forwarding** — open a local **SOCKS listener**, and have SSH forward arbitrary traffic through the pivot host into that network.

### What is SOCKS?

- **SOCKS** = Socket Secure — protocol for communicating with servers across firewall restrictions.
- SOCKS **client** connects to a SOCKS **server** (controlled by whoever wants to reach the restricted service); once established, traffic is routed through the server on the client's behalf.
- Used to **bypass firewall restrictions**, and can pivot via NAT'd networks by creating a route through an external server.
- **SOCKS4:** no authentication, no UDP support.
- **SOCKS5:** supports both authentication and UDP.

### Enable Dynamic Port Forwarding (SSH)

```bash
ssh -D 9050 ubuntu@10.129.202.64
```

- `-D` = dynamic port forward: SSH client listens locally on `9050`; anything sent there gets relayed over the SSH connection into the target's reachable network(s).

### Routing Tool Traffic Through SOCKS — Proxychains

- **Proxychains** redirects a tool's TCP connections through SOCKS4/5, TOR, or HTTP/HTTPS proxies, and can chain multiple proxies.
- Also hides the originating host's IP — the destination only sees the pivot host's IP.

**Config:** `/etc/proxychains.conf`

```bash
tail -4 /etc/proxychains.conf
# socks4  127.0.0.1 9050
```

- Add/confirm `socks4 127.0.0.1 9050` as the last line to match your `-D` port.

### Scanning Through the Tunnel

```bash
proxychains nmap -v -sn 172.16.5.1-200
```

This entire process — packaging tool traffic via proxychains and forwarding it through SSH — is called **SOCKS tunneling**.

**Important limitations:**
- Only a **full TCP connect scan** works over proxychains — it can't interpret partial/half-open packets (e.g., SYN scans give incorrect results).
- **ICMP (ping) host-discovery often fails against Windows targets** — Windows Defender Firewall blocks ICMP by default.
- Full connect scans without ping across a whole range are **slow** — prefer scanning individual hosts or small known-alive ranges.

### Targeted Scan Example (Windows Host)

```bash
proxychains nmap -v -Pn -sT 172.16.5.19
```

- `-Pn` (skip host discovery) + `-sT` (full connect scan) — required combo through proxychains.
- Output shows open ports via the proxy chain, e.g. **445, 135, 3389 (RDP), 139**.

## Pivoting Other Tools Through Proxychains

### Metasploit

```bash
proxychains msfconsole
```

- All Metasploit module traffic now routes through the SOCKS tunnel.

**RDP scanner example:**

```
msf6 > search rdp_scanner
msf6 > use auxiliary/scanner/rdp/rdp_scanner
msf6 auxiliary(scanner/rdp/rdp_scanner) > set rhosts 172.16.5.19
msf6 auxiliary(scanner/rdp/rdp_scanner) > run
```

- Confirms RDP open on 172.16.5.19, reveals hostname/domain/OS version (e.g., `DC01`, Windows `10.0.17763`).

### RDP Login via Proxychains + xfreerdp

```bash
proxychains xfreerdp /v:172.16.5.19 /u:victor /p:pass@123
```

- Requires accepting the RDP certificate prompt.
- Result: full RDP session into the internal Windows host, **pivoting entirely through the Ubuntu server**.

## Key Takeaways

| Technique | SSH Flag | Use Case |
|---|---|---|
| **Local port forward** | `-L local_port:target_host:target_port` | Reach one **known** remote service (e.g., a DB bound to localhost on the pivot) |
| **Dynamic port forward (SOCKS)** | `-D local_port` | Reach an **entire unknown network** behind the pivot — general-purpose tunnel |

- Combine `-D` (SSH) + **proxychains** to route arbitrary tools (Nmap, Metasploit, xfreerdp, etc.) through a compromised host into networks your attack host has no direct route to.
- Always check `proxychains.conf` matches your `-D` port.
- Scan smart: full TCP connect only, skip ping (`-Pn`) for Windows targets, and target known/small ranges to keep scans fast.
