# Pivoting, Tunneling, and Port Forwarding — SSH Pivoting with Sshuttle

**No Proxy chain needed** 

---

## What is Sshuttle?

- Python-based pivoting tool — **removes the need to configure proxychains**.
- **SSH-only**: unlike proxychains, it does **not** support TOR or HTTPS proxy pivoting.
- Automates **iptables** rule creation to route traffic through the remote (pivot) host.
- Key advantage: once running, **any tool can be used directly** — no need to prefix commands with `proxychains`.

---

## Installation

```bash
sudo apt-get install sshuttle
```

---

## Running Sshuttle

```bash
sudo sshuttle -r ubuntu@10.129.202.64 172.16.5.0/23 -v
```

- `-r user@host` → the pivot host to SSH into.
- `172.16.5.0/23` → the target network/CIDR to route through the pivot.
- `-v` → verbose output.
- Prompts for the pivot's SSH password (or uses key-based auth if configured).

### What Happens Under the Hood

- Sshuttle starts a **firewall manager** and a **TCP redirector** (e.g., listening on `127.0.0.1:12300` / `::1:12300`).
- It automatically inserts **iptables (and ip6tables) NAT rules**, e.g.:

```
iptables -w -t nat -N sshuttle-12300
iptables -w -t nat -A sshuttle-12300 -j REDIRECT --dest 172.16.5.0/32 -p tcp --to-ports 12300
```

- Effect: any traffic destined for `172.16.5.0/23` from your attack host is **transparently redirected** through the SSH tunnel to the pivot, with no per-tool proxy configuration needed.
- Local traffic (`127.0.0.1`, `::1`) is explicitly **excluded** from forwarding.

## Using Tools Directly (No Proxychains Needed)

```bash
sudo nmap -v -A -sT -p3389 172.16.5.19 -Pn
```

```
PORT     STATE SERVICE       VERSION
3389/tcp open  ms-wbt-server Microsoft Terminal Services
| rdp-ntlm-info:
|   Target_Name: INLANEFREIGHT
|   NetBIOS_Domain_Name: INLANEFREIGHT
|   NetBIOS_Computer_Name: DC01
|   DNS_Domain_Name: inlanefreight.local
|   DNS_Computer_Name: DC01.inlanefreight.local
```

- Notice: **no `proxychains` prefix** — the scan just works because the OS-level routing (iptables) handles redirection transparently.
- Still need `-Pn` (skip ping) and `-sT` (full connect scan), same caveats as with proxychains-based pivoting.
- Nmap output here also reveals useful AD context via `rdp-ntlm-info` (domain name, hostname, FQDN) — useful recon even from a simple port scan.

## Key Takeaways

| Aspect | Proxychains + SSH `-D` | Sshuttle |
|---|---|---|
| Config required | Per-tool via `/etc/proxychains.conf`, prefix every command | None after setup — transparent routing |
| Protocols supported | SOCKS4/5, TOR, HTTP/HTTPS | **SSH only** |
| Mechanism | App-layer SOCKS proxying | **iptables-based NAT redirection** |
| Usage | `proxychains <tool> ...` | `<tool> ...` (no prefix needed) |

- Sshuttle is the **simpler, lower-friction option** when SSH access to the pivot is all you have/need — ideal for routing an entire subnet without juggling proxychains config per tool.
- Choose proxychains when you need **non-SSH** pivot mechanisms (TOR, HTTP/S proxies) or finer per-tool control.
