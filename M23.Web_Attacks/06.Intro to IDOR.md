# Intro to IDOR (Insecure Direct Object References)

## What is IDOR?
- Occurs when a web app exposes a **direct reference to an object** (file, DB record, resource) that the user can control/manipulate to access **other similar objects**.
- If **any user can access any resource** due to lack of proper access control, the app is vulnerable.
- Example:
  - Download link: `download.php?file_id=123`
  - Attacker tries: `download.php?file_id=124`
  - If no back-end access control exists, this returns another user's file.
  - IDs are often **easily guessable/sequential**, making mass enumeration possible.

## Why IDOR is so common
- Building a **solid access control system** is genuinely hard.
- Automated scanners **struggle to detect** access control weaknesses → many IDORs survive into production.

## What actually makes it a vulnerability
- **Exposing a direct object reference alone isn't a vulnerability.**
- It becomes exploitable when combined with a **weak/missing access control system** on the back-end.
- Many apps restrict access only by **hiding** pages/functions/APIs from the UI (front-end restriction) rather than enforcing checks server-side.
- If a user obtains a link/parameter (shared, guessed, or leaked) and the back-end **doesn't verify the user is authorized for that specific resource**, access succeeds anyway.
- Proper fix pattern: **Role-Based Access Control (RBAC)** or equivalent, checking the **requesting user's authentication against the resource's access list** on every request.
- Root cause: **lack of back-end access control**, not just the presence of a visible ID.
- Without access control, the **front-end UI is the only thing hiding** other users' data — trivial to bypass by manually crafting/modifying HTTP requests.
- Even large, mature apps (Facebook, Instagram, Twitter) have had IDOR/access-control issues — shows how hard comprehensive access control is to implement correctly without breaking functionality.

## Impact of IDOR
1. **IDOR Information Disclosure**
   - Most basic form: viewing other users' private files/resources (personal files, credit card data, etc.)
2. **Data Modification / Deletion**
   - If the exposed reference allows write/delete actions → can lead to **full account takeover**.
3. **IDOR Insecure Function Calls → Privilege Escalation**
   - Admin-only functions/APIs are often just **hidden in the front-end** for non-admin users.
   - If the back-end doesn't explicitly deny non-admin access to these calls, a standard user invoking them directly can perform **admin actions** (e.g., changing passwords, granting roles).
   - Can escalate from standard user → full application takeover.

## Typical exploitation flow
1. Identify a direct reference (DB ID, URL parameter, file path, etc.).
2. Test patterns (incrementing/decrementing IDs, substituting other users' values).
3. Check if data for arbitrary users/resources can be accessed, modified, or if admin functions can be called.

## Key takeaways
- IDOR = **direct object reference** + **missing/weak access control** = vulnerability.
- Can cause: **information disclosure, data tampering, account takeover, privilege escalation**.
- Found even in major, well-resourced applications — it's a design/architecture challenge, not just a coding bug.
- Defense requires **server-side authorization checks on every object access**, not reliance on hiding UI elements or obscure/hard-to-guess IDs.
