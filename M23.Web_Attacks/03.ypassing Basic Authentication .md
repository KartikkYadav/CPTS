# Bypassing Basic Authentication 

## General
- Exploiting verb tampering is usually **simple**: try alternate HTTP methods and observe how the server/app handles them.
- **Automated scanners** are good at catching the **insecure configuration** type (easy to spot once auth is bypassed), but usually **miss** the **insecure coding** type, which needs active/manual testing.
- This section covers the **insecure server configuration** type → bypassing **HTTP Basic Authentication**.

## Scenario
- Target: a basic **File Manager** web app.
  - Lets you add files via a name input.
  - Has a **Reset** button that deletes all files — restricted to authenticated users.
- Clicking **Reset** triggers an **HTTP Basic Auth prompt**; without credentials you get a **401 Unauthorized**.

## Step 1 — Identify the restricted scope
- The Reset button points to `/admin/reset.php`.
- Visiting `/admin` directly also prompts for login → the **entire `/admin` directory** is restricted, not just the one file.

## Step 2 — Identify the method in use
- Intercept the request in **Burp Suite**: Reset uses a **GET** request to `/admin/reset.php`.

## Step 3 — Try tampering with the method
1. **Try POST** (Burp: right-click → *Change Request Method*):
   - Still prompted to log in → **401 Unauthorized**.
   - Conclusion: the server's auth config covers **both GET and POST**.
2. **Check what methods the server accepts** using an `OPTIONS` request:
   ```bash
   curl -i -X OPTIONS http://SERVER_IP:PORT/
   ```
   Example response:
   ```
   HTTP/1.1 200 OK
   Allow: POST,OPTIONS,HEAD,GET
   ```
   → Server accepts **GET, POST, HEAD, OPTIONS**.
3. **Try HEAD** (identical to GET but no response body):
   - Intercept the reset request, change method to **HEAD**, forward it.
   - Result: **no 401, no login prompt**, just an empty response (expected for HEAD).
   - Checking the File Manager afterward confirms: **all files were deleted** — the Reset action executed successfully **without authentication**.

## Why this works
- The server's `<Limit GET POST>` style config only enforces auth on **GET and POST**.
- **HEAD** wasn't included in the restriction, so the request reaches `reset.php` and executes the sensitive action, bypassing auth entirely.

## Key takeaways
- Don't stop at testing just GET/POST — enumerate **all accepted methods** via `OPTIONS`.
- **HEAD** is a common and effective bypass vector since it's often enabled by default and overlooked in auth configs.
- A full fix requires restricting authentication to **all HTTP methods** the server accepts, not just GET/POST (e.g., `<LimitExcept>` instead of `<Limit GET POST>` in Apache).
- Exercise prompt: test other HTTP methods (PUT, DELETE, PATCH, etc.) against restricted endpoints to see which else bypass authentication.
