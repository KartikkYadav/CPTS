# Intro to HTTP Verb Tampering 

## Background
- HTTP requests begin with a **verb/method**, and apps may perform different actions depending on which one is used.
- Developers mostly think about **GET** and **POST**, but any client can send any other method and see how the server reacts.
- If both the server and app accept only GET/POST, other methods just trigger an error page. This is not severe on its own (bad UX, possible information disclosure).
- **The vulnerability:** the server isn't restricted to the methods it needs (e.g. GET/POST) and the app isn't built to handle other methods (e.g. HEAD, PUT). Attackers can then reach functionality they shouldn't or bypass security controls.

## HTTP verbs
HTTP defines **9 verbs**. Beyond GET and POST, the common ones are:

| Verb | Description |
|---|---|
| HEAD | Same as GET, but the response contains **only headers**, no body |
| PUT | Writes the request payload to the specified location |
| DELETE | Deletes the resource at the specified location |
| OPTIONS | Shows options the server accepts, such as allowed HTTP verbs |
| PATCH | Applies partial modifications to the resource at the specified location |

- PUT and DELETE are especially sensitive, since they can write or delete files in the webroot. An insecurely configured server could give an attacker control of the back-end.
- Verb tampering is **more common (and more critical)** than other flaws because **either** the web server **or** the web application can cause it.

## Type 1: Insecure server configuration
- Authentication is **limited to specific HTTP methods**, leaving other methods unauthenticated.
- Example (Apache-style config):
  ```xml
  <Limit GET POST>
      Require valid-user
  </Limit>
  ```
- Only GET and POST require authentication here, so an attacker can send another method (e.g. **HEAD**) to **bypass authentication entirely**.
- **Impact:** authentication bypass, giving access to pages and domains the attacker shouldn't reach.
- Usually avoided in practice, because documentation warns against this kind of config.

## Type 2: Insecure coding
- A developer applies a security filter (e.g. against SQL injection) but **doesn't cover all HTTP methods**. Some may not consider this true verb tampering.
- Example (PHP):
  ```php
  $pattern = "/^[A-Za-z\s]+$/";

  if(preg_match($pattern, $_GET["code"])) {
      $query = "Select * from ports where port_code like '%" . $_REQUEST["code"] . "%'";
      ...SNIP...
  }
  ```
- **The flaw:** the filter checks only `$_GET["code"]`, but the query uses `$_REQUEST["code"]`, which also includes **POST** parameters.
- **Exploit:** send the payload via **POST**. The GET parameter stays empty, so it has no bad characters and passes the filter. The query then uses the malicious POST value, so SQL injection still works.
- **Root cause:** inconsistent use of HTTP verbs between validation and use.
- This type is **much more common**, since it comes from coding mistakes rather than a configuration that documentation already cautions against.

## Quick comparison

| | Insecure configuration | Insecure coding |
|---|---|---|
| Cause | Server auth/access rules limited to certain methods | Filters/validation applied to only some methods |
| Example | `<Limit GET POST>` bypassed via HEAD | Filter on `$_GET`, query uses `$_REQUEST` |
| Result | Authentication bypass | Security-filter bypass (e.g. SQLi) |
| Frequency | Less common | More common |

## Key takeaways
- Security controls must apply to **all HTTP methods**, not just GET and POST.
- Validation and usage of input must read from the **same source** (e.g. don't check `$_GET` but use `$_REQUEST`).
- Restrict the server to only the verbs the app actually needs.
