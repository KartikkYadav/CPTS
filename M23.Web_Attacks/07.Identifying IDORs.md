# Identifying IDORs

## 1. URL Parameters & APIs
- First step: study HTTP requests for **object references** in URL parameters/APIs (e.g. `?uid=1`, `?filename=file_1.pdf`).
- May also appear in **other HTTP headers**, like cookies.
- Basic test: **increment/change the value** (`?uid=2`, `?filename=file_2.pdf`) and see if you get data that isn't yours.
- Can **fuzz** thousands of variations automatically; any successful hit on non-owned data = IDOR.

## 2. AJAX Calls (Front-end JavaScript)
- Some apps insecurely place **all function calls** (including admin-only ones) in front-end JS, just disabling/hiding them based on role.
- Reviewing the JS source can reveal **unused/hidden API calls or endpoints** containing direct object references — even if the UI never triggers them for your role.
- Example:
  ```javascript
  function changeUserPassword() {
      $.ajax({
          url:"change_password.php",
          type: "post",
          dataType: "json",
          data: {uid: user.uid, password: user.password, is_admin: is_admin},
          success:function(result){ }
      });
  }
  ```
  - A non-admin user might never trigger this call via the UI, but finding it in the JS lets an attacker **call it directly** and test whether the back-end actually blocks it.
- Not limited to admin functions — applies to **any function/endpoint** not visible through normal HTTP traffic monitoring.
- Same technique applies to **back-end source code** review when available (e.g. open-source apps).

## 3. Understanding Hashing/Encoding of References
Object references aren't always plain sequential numbers — they may be **encoded** or **hashed**. Doesn't mean they're secure.

### Encoded references
- E.g. `?filename=ZmlsZV8xMjMucGRm` → recognizable as **Base64** by its character set.
- Decode → `file_123.pdf`.
- Modify the plaintext (`file_124.pdf`), **re-encode**, and try the new value (`?filename=ZmlsZV8xMjQucGRm`).
- Success = IDOR, since encoding ≠ access control.

### Hashed references
- E.g. `download.php?filename=c81e728d9d4c2f636f067f89cc14862c` — looks secure at first glance.
- Check front-end source for how the hash is generated:
  ```javascript
  $.ajax({
      url:"download.php",
      type: "post",
      dataType: "json",
      data: {filename: CryptoJS.MD5('file_1.pdf').toString()},
      success:function(result){ }
  });
  ```
  - Reveals the **hashing algorithm and input** (MD5 of filename) → attacker can **calculate hashes** for other filenames (`file_2.pdf`, etc.) and request them.
- If source isn't available, try **hash identifier tools** to determine the algorithm, then brute-force/calculate hashes for likely filenames.
- Successfully downloading files that aren't yours = IDOR.

## 4. Compare User Roles
- For more advanced testing: **register multiple accounts**, compare their HTTP requests/object references side by side.
- Goal: understand how **unique identifiers/parameters are calculated**, then try computing them for other users.
- Example:
  ```json
  {
    "attributes": {
      "type": "salary",
      "url": "/services/data/salaries/users/1"
    },
    "Id": "1",
    "Name": "User1"
  }
  ```
  - User1 can view their own salary via this API call referencing `users/1`.
  - Log in as **User2**, replay the **same call** (referencing `users/1`) to see if it returns User1's data.
  - If the app only checks for a **valid session** (not whether the session owns the requested resource) → data leaks = **IDOR confirmed**.
- Even if you can't calculate another user's exact parameters, **discovering the access-control gap itself** is valuable — prompts further hunting for other object references to exploit.

## Summary table

| Technique | What to look for | How to test |
|---|---|---|
| URL Parameters & APIs | IDs/filenames in requests | Increment/fuzz values |
| AJAX Calls | Hidden/role-restricted JS functions | Call directly regardless of role |
| Encoded references | Recognizable encoding (e.g. Base64 charset) | Decode → modify → re-encode |
| Hashed references | Hash algorithm exposed in front-end code | Recalculate hash for other inputs |
| Compare user roles | Differences in API calls between accounts | Replay one user's call as another |

## Key takeaway
IDOR identification is fundamentally about finding **any reference to an object** — whether plain, encoded, or hashed — and testing whether the **back-end actually verifies ownership/authorization**, rather than relying on obscurity (hidden UI, encoding, hashing) as a substitute for real access control.
