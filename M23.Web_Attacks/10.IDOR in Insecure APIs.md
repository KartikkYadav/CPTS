# IDOR in Insecure APIs

## Two categories of IDOR, revisited
| Type | What it allows |
|---|---|
| **IDOR Information Disclosure** | Reading resources/data belonging to other users |
| **IDOR Insecure Function Calls** | Calling APIs/functions **as** another user — changing data, resetting passwords, making purchases, etc. |

- Often chained together: an **information disclosure IDOR** leaks data (e.g. a missing parameter value) that is then used to exploit an **insecure function call IDOR**.

## Scenario: Employee Manager — Edit Profile
- Edit Profile page lets a user update **Full Name, Email, About Me**.
- Intercepting the **Update profile** request in Burp:
  ```
  PUT /profile/api.php/profile/1
  ```
  ```json
  {
      "uid": 1,
      "uuid": "40f5888b67c748df7efba008e7c2f9d2",
      "role": "employee",
      "full_name": "Amy Lindon",
      "email": "a_lindon@employees.htb",
      "about": "A Release is like a boat. 80% of the holes plugged is not good enough."
  }
  ```
- **PUT** = update item (standard REST convention: POST=create, PUT=update, DELETE=delete, GET=retrieve).
- **Key issue spotted:** the request includes **hidden/sensitive parameters** — `uid`, `uuid`, and especially `role` (currently `"employee"`).
- The app also reflects role via a client-side cookie: `Cookie: role=employee`.
- **Core problem:** access-control-relevant data (`role`) is sent **from the client** (JSON body + cookie) rather than being enforced purely server-side — meaning it's potentially attacker-controllable if the back-end doesn't validate it properly.

## Exploitation attempts

### 1. Change own `uid` to another user's (account takeover attempt)
- Set `"uid": 2` while still hitting `/profile/api.php/profile/1`.
- **Result:** `uid mismatch` error.
- → Back-end **compares the JSON `uid` to the URL endpoint's uid** — a working access control check.

### 2. Change another user's details directly
- Change endpoint to `/profile/api.php/profile/2` **and** `"uid": 2` (to avoid the mismatch above).
- **Result:** `uuid mismatch` error.
- → Back-end also checks that the **`uuid`** in the request matches the target user's real `uuid` — since the attacker only knows their own `uuid`, this fails.
- → Another working access control layer.

### 3. Create a new user (POST) / Delete a user (DELETE)
- Switch method to **POST** (create) with a new `uid`.
- **Result:** `"Creating new employees is for admins only"`.
- Same outcome for **DELETE**: `"Deleting employees is for admins only"`.
- → Authorization here appears to be enforced via the **`role=employee` cookie**, since it's the only authorization signal present.

### 4. Escalate privileges — change own role to admin
- Attempt to set `"role": "admin"` (or similar) without knowing the exact valid role name.
- **Result:** `"Invalid role"` — role not updated.
- → Fails only because the **exact role string** isn't known, not because the field is otherwise protected.

## Interim conclusion
- Every **function-call-based (write) IDOR attempt** so far has been blocked by some access control check:
  - `uid` vs endpoint comparison
  - `uuid` matching
  - role-based cookie authorization
  - role-name validation
- **But:** only the **PUT/POST/DELETE (write)** side has been tested so far.
- **Not yet tested:** the API's **GET** requests — i.e., whether **IDOR Information Disclosure** is possible by reading other users' profile data (uid, uuid, role name, etc.) directly.

## Exercise prompt (module's "try it yourself")
> Test the API against **IDOR Information Disclosure** by sending **GET** requests for other users' details. If successful, this could leak exactly the missing pieces (e.g. another user's correct `uuid`, or a valid admin **role name**) needed to complete the function-call attacks that failed above — i.e., chaining a read IDOR into a write/privilege-escalation IDOR.

## Key takeaways
1. **Writes/function calls can have strong authorization checks (uid/uuid/role matching) even when reads do not** — always test GET endpoints separately, don't assume uniform protection across methods.
2. Sensitive data like **role** should never be trusted from client input (cookies, JSON body) — it must be derived and enforced server-side from the authenticated session.
3. Failed write attempts can still reveal **what checks exist** (error messages like `uid mismatch`, `uuid mismatch`, `Invalid role` are valuable reconnaissance) — these guide what information to go hunt for via a read-side IDOR.
4. A full IDOR assessment must cover **all CRUD operations** (Create/Read/Update/Delete) independently, since access control is often inconsistent across them.
