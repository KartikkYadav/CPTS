# HTB Web Attacks Skill Assessment — Chaining IDOR, HTTP Verb Tampering & XXE

**Source:** Medium article by ZeroByte (write-up of HTB's Web Attacks module Skill Assessment, CWES cert path)

## Overview
- Demonstrates a **real-world multi-stage exploit chain** combining all three attacks from the module into one attack path: **IDOR → HTTP Verb Tampering → Account Takeover → XXE → Flag Exfiltration**.
- Shows how individually "moderate" flaws **compound** into full admin compromise + source code/data exfiltration.

---

## Attack Chain Summary

| Phase | Technique | Outcome |
|---|---|---|
| 0 | Initial access | Logged in as low-priv user, found leaking user ID |
| 1 | IDOR (API enumeration) | Found admin account + stole admin's reset token |
| 2 | HTTP Verb Tampering | Bypassed auth check → reset admin's password → Account Takeover |
| 3 | In-Band XXE | Read `/etc/passwd`, then base64-exfiltrated `/flag.php` source |

---

## Phase 0 — Initial Access
- Logged in with provided creds (`htb-student` / `Academy_student!`).
- Landed on `profile.php` — a standard user dashboard.
- Intercepting the request in Burp revealed the app was **leaking the user's ID** both in the URL and in a **`uid` cookie**.
- The endpoint `/api.php/user/74` returned the logged-in user's own details directly — first sign that **uid is used as a direct object reference with no validation**.

## Phase 1 — IDOR / API Enumeration
- Two sensitive endpoints found, both referencing `uid` directly:
  ```
  /api.php/user/${uid}
  /api.php/token/${uid}
  ```
- **Back-end never verified** whether the logged-in user was authorized to view another user's profile or token — classic **IDOR**.
- Automated enumeration via bash:
  ```bash
  #!/bin/bash
  BASE_URL="http://154.57.164.71:30176/api.php/user"
  for uid in {1..100}; do
      response=$(curl -s -w "\n" "${BASE_URL}/${uid}")
      if [ -n "$response" ]; then
          echo "[*] User ID: ${uid} | ${response}"
      fi
  done
  ```
- Found an **admin account** at `uid=52`:
  ```json
  {"uid":"52","username":"a.corrales","full_name":"Amor Corrales","company":"Administrator"}
  ```
- Requested `/api.php/token/52` → returned the **admin's live password-reset token**, with no access check:
  ```json
  {"token":"e51a85fa-17ac-11ec-8e51-e78234eb7b0c"}
  ```

## Phase 2 — HTTP Verb Tampering → Account Takeover
- Goal: use the stolen token on `/reset.php`.
- Sending a normal `application/json` **POST body** → `"Missing parameters"` error.
- **Root cause found:** the back-end authorization check compared the `uid` **cookie** to the `uid` **value in the request**:
  ```php
  $_COOKIE['uid'] === $_REQUEST['uid']
  ```
  — but it only checked parameters from one source (and the POST-body parsing wasn't matching).
- **Bypass:** send parameters as **URL query string** instead of POST body, and set the cookie to `uid=52`:
  ```
  POST /reset.php?uid=52&token=e51a85fa-17ac-11ec-8e51-e78234eb7b0c&password=a HTTP/1.1
  Host: 154.57.164.71:30176
  Cookie: PHPSESSID=16vrs65ncrfrgv51r7kiogl864; uid=52
  Content-Type: application/x-www-form-urlencoded
  Content-Length: 0
  ```
- Server responded `200 OK`: **"Password changed successfully"**.
- Logged in as `a.corrales` with the new password → **full admin panel access**.
- **This is a textbook example** of the module's "insecure coding" HTTP Verb Tampering pattern: validation logic trusts `$_REQUEST`/mixed parameter sources inconsistently, so changing *where* (and how) parameters are sent bypasses the check — here compounded by cookie-based "identity" (`uid` cookie) being fully attacker-controlled, chaining straight into the IDOR-leaked token.

## Phase 3 — In-Band XXE Injection
1. **Recon:** `/event.php` (now accessible as admin) has an event-creation form.
2. Intercepting a legitimate submission showed the form sends **raw XML** to `/addEvent.php`, and the **event `name` field is reflected** back: `"Event 'a' has been created."` → confirmed **injection/reflection point**.
3. **Confirm entity processing** with an internal entity:
   ```xml
   <?xml version="1.0" encoding="UTF-8"?>
   <!DOCTYPE name [
     <!ENTITY company "Inlane Freight">
   ]>
   <root>
     <name>&company;</name>
     <details>aaa</details>
     <date>2026-05-20</date>
   </root>
   ```
   - Response: `"Event 'Inlane Freight' has been created"` → parser **resolves and reflects entities** → confirmed vulnerable.
4. **Test external entity** against a known file (`/etc/passwd`) → full file contents returned → **confirmed working In-Band XXE**.
5. **Target the flag:** `/flag.php` — but referencing it directly breaks the XML parser, since **PHP tags (`<?php ?>`) conflict with XML syntax**.
6. **Fix:** use the `php://filter` wrapper to **Base64-encode** the file before the XML parser sees it (same technique as earlier module sections):
   - Entity defined with `php://filter/convert.base64-encode/resource=flag.php` (implied, consistent with module's technique).
   - Response contained a **Base64 string** embedded in the event echo.
7. Decoding (via Burp Inspector → Base64 decode) revealed:
   ```php
   <?php $flag = "HTB{m45------ck3r}"; ?>
   ```

## Key Defensive Recommendations (from the article)

### IDOR
- **Validate resource ownership on every request** — never trust a client-supplied ID alone.
- Object references should be **tied to the server-side session**, not a user-supplied URL/cookie value.
- Avoid **sequential numeric IDs** → use unpredictable references like **UUIDs**.

### HTTP Verb Tampering
- Apply **authorization checks consistently**, regardless of whether parameters arrive via body, query string, or cookies.
- **Never resolve a user's identity from client-controlled values** (e.g. don't trust a `uid` cookie as truth).
- Use a **single centralized authorization function** for all incoming requests — avoid inconsistent per-endpoint checks.

### XXE
- **Disable external entity and DTD processing** at the parser level.
  - In PHP: `libxml_disable_entity_loader(true)` before parsing, and use `LIBXML_NOENT` carefully.
  - Blocks both **In-Band** and **Out-of-Band** XXE at the root.
- Extra layer: **avoid reflecting user-supplied XML values back** in responses — limits impact even if a bypass is found.

## Key takeaway
This write-up is a practical illustration of the module's core lesson: **individually moderate vulnerabilities chain into critical compromise.** An information-disclosure IDOR (leaked token) fed directly into an HTTP Verb Tampering auth bypass (account takeover), which then unlocked an admin-only XXE injection point used for full source/data exfiltration — reinforcing why **defense-in-depth across all three vulnerability classes** matters, not just patching one in isolation.
