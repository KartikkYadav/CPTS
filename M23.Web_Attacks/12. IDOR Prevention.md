# IDOR Prevention

## Two pillars of prevention
1. **Object-Level Access Control** (the core fix)
2. **Secure Object Referencing** (a supporting/secondary defense)

---

## 1. Object-Level Access Control

- Access control should be **core to the application's design**, not bolted on — it affects the entire structure.
- Needs **centralized** segmentation of roles and permissions.
- Best realized via **Role-Based Access Control (RBAC)**, mapped to **every object/resource**.
- On each request: check the user's **role/privileges** against the **specific object being requested** before allowing access.

### Example (pseudocode, Firestore-style rules)
```javascript
match /api/profile/{userId} {
    allow read, write: if user.isAuth == true
    && (user.uid == userId || user.roles == 'admin');
}
```
- Access is granted only if:
  - The user is **authenticated**, **and**
  - Either their `uid` **matches** the requested `userId`, **or**
  - Their role is `admin`.
- **Key detail:** `user.uid` and `user.roles` here come from the **back-end RBAC system**, resolved via the user's **session/auth token** — **not** from client-supplied data (HTTP body/cookie), unlike the vulnerable examples earlier in the module where `role` was sent in the request itself and could be tampered with.

### Lesson from earlier attacks
- Previously, the app stored/trusted `role` in the **request body or cookie** → fully attacker-controllable → privilege escalation.
- **Fix:** always derive role/permissions **server-side** from an authenticated session, never trust role data sent by the client.

---

## 2. Object Referencing

- IDOR's root cause is **broken access control**, but **direct object references** (predictable IDs) are what make it **easy to enumerate and exploit**.
- Direct references are **fine to use** — but only **on top of** a solid access control system, never as a substitute for one.

### Guidance
- **Never** use cleartext/sequential/simple references (e.g. `uid=1`).
- Use **strong, unique, unpredictable** references instead:
  - **Salted hashes**
  - **UUIDs** (e.g. UUID v4: `89c9b29b-d19f-4515-b2dd-abb6e693eb20`)
- Map the UUID to its actual object in the **back-end database**; the UUID itself carries no predictable meaning.

### Vulnerable example (cleartext, enumerable reference)
```php
$uid = intval($_REQUEST['uid']);
$query = "SELECT url FROM documents where uid=" . $uid;
$result = mysqli_query($conn, $query);
$row = mysqli_fetch_array($result);
echo "<a href='" . $row['url'] . "' target='_blank'></a>";
```
- Directly uses a simple, guessable `uid` to fetch documents — easy to enumerate if access control is weak/missing.

### Important rules for implementing secure references
- **Never calculate hashes/references on the front-end** (as seen earlier with the `CryptoJS.MD5(btoa(uid))` flaw) — this exposes the generation logic to attackers.
- Generate references **at object creation time**, store them in the **back-end database**, and maintain **database maps** for fast lookup/cross-referencing.

### Important caveat
- UUIDs/strong references can make IDOR **harder to detect during testing** — but they don't fix broken access control.
- If access control is still broken, attacks like **replaying one user's request with another user's session** can still succeed even with strong, unpredictable references.
- **Strong referencing is always the second layer, after (not instead of) strong access control.**

---

## Summary: the two-layer defense

| Layer | Purpose | Example |
|---|---|---|
| **Access Control (primary)** | Verify the *requesting user* is authorized for the *specific object*, enforced server-side via RBAC | Compare authenticated `user.uid`/role from session to the resource owner |
| **Object Referencing (secondary)** | Make references hard to guess/enumerate, reducing attack surface | UUID v4 / salted hash generated and stored server-side |

## Key takeaways
1. **Access control is the real fix** — object referencing alone (hashing, UUIDs) is not a substitute.
2. Never trust **role/permission data from the client** (cookies, JSON body) — always resolve it server-side from an authenticated session/token.
3. Never generate sensitive hashes/IDs **client-side** — always generate and store them server-side.
4. Even unpredictable references don't stop IDOR if access control is broken — attackers can still exploit via other users' valid sessions/requests.
5. **Both layers together** (solid RBAC + strong object references) provide the most complete protection against IDOR.
