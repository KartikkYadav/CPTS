# Chaining IDOR Vulnerabilities

## Starting point
- Previous section tested write actions (PUT/POST/DELETE) on `/profile/api.php` — all blocked by checks (`uid mismatch`, `uuid mismatch`, role-based restrictions, `Invalid role`).
- **Not yet tested:** the **GET** request to the same API endpoint.
- Only authorization present in requests: the `role=employee` **cookie** — no JWT or other session-bound token.
- Even if a token existed, it would only matter if the **back-end actually compares it** against the requested object's owner — otherwise it's just as bypassable.

## Step 1 — IDOR Information Disclosure via GET
- Send a **GET** request to the profile API for another `uid`.
- **Result:** full details of another user returned:
  ```json
  {
      "uid": "2",
      "uuid": "4a9bd19b3b8676199592a346051f950c",
      "role": "employee",
      "full_name": "Iona Franklyn",
      "email": "i_franklyn@employees.htb",
      "about": "It takes 20 years to build a reputation and few minutes of cyber-incident to ruin it."
  }
  ```
- **Confirmed:** IDOR Information Disclosure vulnerability.
- Critically, this leaks the **uuid** — the exact missing value that previously blocked modifying other users' data (`uuid mismatch`).

## Step 2 — Modifying Other Users' Details
- With the leaked `uuid`, send a **PUT** to `/profile/api.php/profile/2` with that user's correct `uuid` + desired changes.
- **Result:** `200 OK`, **no access control errors**.
- Confirmed via a follow-up GET — the target user's details were genuinely updated.

### Real-world attack potential from this
- **Account takeover:** change the victim's email → trigger a **password reset** → reset link goes to attacker-controlled email.
- **Stored XSS:** inject an XSS payload into a free-text field (e.g. `about`) → executes when the victim views their own profile.

## Step 3 — Chaining into Privilege Escalation
1. **Enumerate all users** (same scripting approach as earlier sections) to find valuable accounts, especially an **admin** user.
2. Found an admin account:
   ```json
   {
       "uid": "X",
       "uuid": "a36fa9e66e85f2dd6f5e13cad45248ae",
       "role": "web_admin",
       "full_name": "administrator",
       "email": "webadmin@employees.htb",
       "about": "HTB{FLAG}"
   }
   ```
3. This reveals the **actual admin role name**: `web_admin` (previously unguessable → caused the earlier `Invalid role` error).
4. **Two attack options now available:**
   - Modify the admin's own details directly (email takeover / XSS), **or**
   - Set **your own** `role` to `web_admin` using the now-known valid role name.

### Self-escalation to admin
- Intercept your own **Update profile** PUT request, set `"role": "web_admin"`.
- **Result:** no `Invalid role` error, no access control rejection → **role successfully changed**.
- GET confirms:
  ```json
  {
      "uid": "1",
      "uuid": "40f5888b67c748df7efba008e7c2f9d2",
      "role": "web_admin",
      "full_name": "Amy Lindon",
      "email": "a_lindon@employees.htb",
      "about": "..."
  }
  ```
- **Root cause:** back-end validates that the role *string* is a known/valid role, but does **not** enforce *who is allowed to set which role* — no check that only existing admins can assign the `web_admin` role.

## Step 4 — Exploiting the escalated privileges
- Refresh page (or manually set `Cookie: role=web_admin`) to apply new privileges.
- Retry the earlier blocked **POST** (create user) request → now succeeds (`200 OK`), no "admins only" error.
- GET on the new user confirms it was created successfully.
- **Now unlocked:** create/delete employees, and other admin-only actions previously denied.

## Mass exploitation potential
- With `web_admin` privileges, could perform **mass assignment** across all users:
  - Inject XSS payloads into every user's profile.
  - Change all users' emails to an attacker-controlled address (mass account takeover).
- Suggested exercise: script that retrieves all `uuids` then sends a PUT per user updating their email.

## The full attack chain (summary)
1. **Insecure config/coding reconnaissance** → found write-side access controls (`uid`/`uuid` matching, role cookie, role validation).
2. **IDOR Information Disclosure (GET)** → leaked other users' `uuid` values and the real `web_admin` role name.
3. **IDOR Insecure Function Call (PUT)** → used leaked `uuid` to modify arbitrary users' data.
4. **Privilege Escalation** → used leaked role name to set own role to `web_admin`.
5. **Full Admin Takeover** → create/delete users, mass-modify all accounts.

## Key takeaways
1. **Always test GET/read endpoints separately** — an app can have strong write-side checks (`uid`/`uuid` matching) while leaving reads completely open.
2. **Information disclosure IDORs are rarely "just" a privacy issue** — leaked identifiers (uuids, role names, tokens) often unlock IDOR function-call attacks that were previously blocked.
3. **Validating that a value is a legitimate option (e.g., role name is real) is not the same as authorizing who may set it.** Back-ends must check both "is this value valid?" and "is this user allowed to use it?"
4. **Chaining vulnerabilities** (read IDOR → write IDOR → privilege escalation) is a core penetration-testing technique — a vulnerability that seems low-impact alone can become critical combined with another.
5. Once elevated privileges are obtained, assess the **full blast radius** — mass assignment, account takeovers, stored XSS injection across many users, etc.
