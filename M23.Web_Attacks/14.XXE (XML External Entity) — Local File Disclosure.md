# XXE (XML External Entity) — Local File Disclosure

## 1. Overview

**XML External Entity (XXE)** is a vulnerability that occurs when a web application processes untrusted XML input without properly restricting external entity references.

An attacker may exploit XXE to:

- Read sensitive files from the back-end server.
- Retrieve application source code and configuration files.
- Expose credentials, API keys, and SSH private keys.
- Perform Server-Side Request Forgery (SSRF).
- Potentially achieve Remote Code Execution (RCE) in certain configurations.
- Cause Denial of Service (DoS).

### How XXE Works

1. Identify a web application that accepts XML input.
2. Determine whether user-defined XML entities are processed.
3. Define an external entity that references a local file or another resource.
4. Inject the entity into an XML element whose value is reflected in the response.
5. Retrieve the resulting file contents or other accessible data.

**Key requirement:** The XML parser must permit the relevant entity processing, and the application must expose a useful result or side channel.

## 2. Identifying XXE Vulnerabilities

### Step 1: Find XML Input

Look for web applications that accept user input through:

- Contact forms
- File uploads
- API requests
- XML-based integrations
- SOAP endpoints

Example endpoint:

```text
http://SERVER_IP:PORT/index.php
```

Submit the form and intercept the HTTP request using Burp Suite.

### Step 2: Inspect the HTTP Request

An application may submit form data in XML format:

```xml
<?xml version="1.0"?>
<root>
    <name>John</name>
    <tel>123456789</tel>
    <email>john@example.com</email>
    <message>Hello</message>
</root>
```

If user-controlled XML is processed by a vulnerable parser, the endpoint may be a potential XXE target.

### Step 3: Identify Reflected XML Elements

Observe which XML values appear in the HTTP response.

For example:

```text
Check your email john@example.com for further instructions.
```

Here, the value of the `<email>` element is reflected in the response.

**Exam tip:** Identify reflected elements before attempting file disclosure. A reflected element can provide a convenient way to retrieve the output of an XXE payload.

### Step 4: Test XML Entity Injection

Add a custom entity definition inside a document type declaration (DOCTYPE):

```xml
<?xml version="1.0"?>
<!DOCTYPE email [
    <!ENTITY company "Inlane Freight">
]>
```

Reference the entity in the XML document:

```xml
<email>&company;</email>
```

If entity processing is enabled, the application may display:

```text
Inlane Freight
```

If the application displays the literal string `&company;`, the entity may not have been expanded. This alone does not conclusively establish whether the application is vulnerable.

### Vulnerability Confirmation

Successful expansion of a custom entity indicates that the XML parser processes the supplied entity definition. Further testing is required to determine whether external entities are also permitted.

**Important:** Internal entity expansion does not automatically prove that external entity resolution is enabled.

## 3. Testing JSON-Based Applications

Some web applications normally accept JSON but may also accept XML.

When authorized to test the application:

1. Intercept the HTTP request in Burp Suite.
2. Change the `Content-Type` header to `application/xml`.
3. Convert the request body into valid XML.
4. Send the modified request.
5. Observe whether the server accepts and processes the XML input.

Example header:

```http
Content-Type: application/xml
```

**Key point:** The application's default request format does not necessarily reveal every format it accepts.

## 4. Reading Sensitive Files with XXE

Once external entity processing has been confirmed, an external entity may be defined using the `SYSTEM` keyword and a resource identifier.

### Example: Read `/etc/passwd`

```xml
<?xml version="1.0"?>
<!DOCTYPE email [
    <!ENTITY company SYSTEM "file:///etc/passwd">
]>
```

Reference the entity in a reflected element:

```xml
<email>&company;</email>
```

If the application permits local file access and returns the entity's contents, the response may disclose the contents of `/etc/passwd`.

### Why `/etc/passwd`?

On Linux systems, `/etc/passwd` commonly contains local account information, including usernames and account metadata.

It generally does **not** contain users' actual password hashes on modern Linux systems.

### Other Files of Interest

Depending on the operating system, application configuration, permissions, and testing scope, potentially sensitive files include:

- Application configuration files
- Database connection settings
- Files containing API keys or credentials
- SSH private keys, such as a user's `id_rsa`
- Application source code
- Environment or deployment configuration files

**Exam note:** Successful file disclosure depends on the web server process's permissions and the parser's ability to access the requested resource.

## 5. Reading Application Source Code

Obtaining application source code may expose:

- Authentication and authorization weaknesses
- Database credentials
- API keys and secrets
- Internal endpoints
- Additional vulnerabilities suitable for follow-up testing

### Why Direct PHP Source Disclosure May Fail

Consider the following external entity:

```xml
<!DOCTYPE email [
    <!ENTITY company SYSTEM "file:///var/www/html/index.php">
]>
```

The source file may contain characters such as:

```text
<
>
&
```

These characters can conflict with XML parsing when the file is interpreted as an external parsed entity.

Consequently, the application may fail to display the source code, even if the file is readable.

**Key distinction:** Failure to display a file does not necessarily mean the file is inaccessible. The file's contents may simply be incompatible with XML entity parsing.

### PHP Filter Wrapper Technique

PHP provides stream wrappers that can transform resource contents before they are returned.

The `php://filter` wrapper can Base64-encode a file so that its output is suitable for transport through XML entity expansion.

Example:

```xml
<?xml version="1.0"?>
<!DOCTYPE email [
    <!ENTITY company SYSTEM
    "php://filter/convert.base64-encode/resource=index.php">
]>
```

Reference the entity:

```xml
<email>&company;</email>
```

If successful, the response contains a Base64-encoded representation of the source file.

### Decoding the Output

1. Capture the Base64 output from the HTTP response.
2. Copy the encoded string.
3. Decode it using Burp Suite's Inspector or a trusted Base64 decoder.
4. Review the recovered source code.

Example Linux command:

```bash
echo 'BASE64_STRING' | base64 -d
```

**Important limitations:**

- This technique relies on PHP wrapper support.
- The PHP environment and XML parser must permit the relevant resource access.
- The target file must be accessible to the web application process.
- The example uses `index.php` as a relative resource path; an absolute path may be necessary depending on the application's working directory.

## 6. Remote Code Execution (RCE) Through XXE

XXE primarily enables XML-related resource access, but it may contribute to Remote Code Execution under specific conditions.

Potential prerequisites include:

- A vulnerable XML parser
- An available command-execution mechanism or wrapper
- Suitable server-side configuration
- Sufficient process permissions
- A way to retrieve or observe the result

### PHP `expect://` Wrapper

Some PHP environments may support the `expect://` wrapper, which can execute commands through the Expect extension.

Example:

```text
expect://id
```

If the relevant extension is installed and enabled, and the XML parser supports this resource, the command may execute.

However, the `expect` extension is not enabled by default in many modern PHP installations.

### General Web-Shell Delivery Concept

In a suitably vulnerable, authorized lab environment, an attacker may attempt to:

1. Host a PHP web shell on a controlled HTTP server.
2. Cause the target to retrieve that file.
3. Place the file in a location writable by the web application.
4. Access the resulting endpoint to execute commands.

For example, a minimal PHP command-execution shell may contain:

```php
<?php system($_REQUEST["cmd"]); ?>
```

This is highly dangerous if deployed on a real server. Use such code only in an explicitly authorized, isolated lab.

**Exam takeaway:** RCE is not an inherent property of XXE. It requires additional capabilities or a vulnerable configuration.

## 7. Other XXE Attacks

### A. Server-Side Request Forgery (SSRF)

XXE can sometimes be used to make the server issue requests to resources chosen by the tester.

Potential impacts include:

- Accessing internal web applications
- Enumerating services listening on local ports
- Reaching internal endpoints unavailable directly from the internet
- Interacting with cloud or infrastructure services, depending on network controls

The impact depends on outbound connectivity, network segmentation, access controls, and the XML parser's resource-resolution behavior.

**Remember:** XXE-based SSRF uses the vulnerable server as the source of a request.

### B. Denial of Service (DoS)

XML entity expansion can cause excessive memory consumption or CPU usage.

A classic example is the *Billion Laughs* attack, which uses nested entity definitions to create an extremely large amount of expanded data.

Conceptual structure:

```xml
<!DOCTYPE root [
    <!ENTITY a0 "DOS">
    <!ENTITY a1 "&a0;&a0;&a0;&a0;">
    <!ENTITY a2 "&a1;&a1;&a1;&a1;">
    <!ENTITY a3 "&a2;&a2;&a2;&a2;">
]>
```

Each entity references a previous entity multiple times, causing exponential growth in the expanded content.

Potential consequences:

- High memory consumption
- Excessive CPU usage
- Slow application responses
- Service unavailability

Modern XML parsers commonly implement protections against entity expansion and related attacks.

**CPTS exam note:** DoS testing can disrupt services. Only test entity expansion within the scope and limits of an authorized lab.

## 8. Common XXE Indicators

| Observation | Possible Meaning |
|---|---|
| XML input is accepted by the server | Potential XML parsing attack surface |
| A custom internal entity is expanded | User-controlled entity definitions are processed |
| An external entity returns local file contents | Local file disclosure through XXE |
| A PHP source file fails to display | Its contents may not be valid as a parsed XML entity |
| Base64-encoded source is returned | File contents may have been encoded before XML processing |
| Internal resources are accessed through XML | Potential XXE-based SSRF |
| Large entity expansions consume resources | Potential XML entity expansion DoS |
| Commands execute through a supported wrapper | Additional configuration may permit RCE |

These observations are indicators, not universal proof. Interpret them in the context of the application and parser behavior.
