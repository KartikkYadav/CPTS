# Bypassing Security Filters

## General
- This is the **second, more common** type of HTTP Verb Tampering vulnerability — caused by **Insecure Coding**, not server configuration.
- Happens when a security filter (meant to catch malicious input) only checks **one HTTP method's parameters** (e.g. only `$_POST['parameter']`), while the app processes input from **other methods too**.
- **Bypass idea:** if a filter only checks POST data, switch the request to **GET** (or vice versa) to slip malicious input past it.

## Scenario
- Same **File Manager** web app as before.
- Creating a file with special characters (e.g. `test;`) triggers:
  > **"Malicious Request Denied!"**
- This shows the app has a **back-end filter** detecting injection attempts (e.g. command injection via `;`).

## Step 1 — Identify
- Normal requests with injection payloads are consistently blocked → filter appears to work correctly for the default method (POST, in this case).
- Hypothesis: the filter may only check one HTTP method's parameters.

## Step 2 — Exploit
1. Intercept the file-creation request in **Burp Suite**.
2. Use **Change Request Method** to switch it to a different method (e.g. GET).
3. Resend the request with the same payload (`test;` → URL-encoded as `test%3B`).
4. Result: **no "Malicious Request Denied!" message** — the file is created successfully.
   → Confirms the filter **does not check this method's parameters**, so the filter is bypassed.

## Step 3 — Confirm real impact (Command Injection)
- Bypassing the filter message alone isn't proof of exploitation — need to confirm actual **command injection**.
- Use a payload that runs two chained commands via filename input:
  ```
  file1; touch file2;
  ```
  (URL-encoded: `file1%3B+touch+file2%3B`)
- Change the request method (e.g. to GET) and send it.
- Result: **both `file1` and `file2` are created** on the server.
  → Confirms genuine **OS command injection**, achieved only because the verb-tampering bypass defeated the filter.

## Why this works
- The filter likely only validates `$_POST['filename']` (or similar), but the app's processing logic uses a method-agnostic source (like `$_REQUEST`) or the attacker simply moved the same parameter to an unchecked method.
- Without the HTTP Verb Tampering flaw, the app might have been **properly protected** against Command Injection — the tampering vulnerability is what defeats an otherwise working defense.

## Key takeaways
- A visible, working-looking security filter can still be **completely bypassed** if it isn't applied consistently across **all HTTP methods**.
- Always test **the same payload across different HTTP verbs** (GET, POST, HEAD, PUT, etc.) when a filter blocks you — don't assume the block means the app is secure.
- **Root fix:** validate input based on the actual parameter value used by the app logic, regardless of which HTTP method delivered it — not based on `$_POST` or `$_GET` specifically.
