# Verb Tampering Prevention

## Overview
- Two root causes to fix: **Insecure Configuration** and **Insecure Coding**.
- Found in most modern web servers: **Apache, Tomcat, ASP.NET**.

---

## 1. Insecure Configuration

**Core problem:** Authorization is scoped to a specific verb (e.g. only `GET`), leaving other methods (POST, HEAD, OPTIONS, etc.) unprotected — even specifying both GET and POST still misses others.

### Apache example (vulnerable)
Found in site config (`000-default.conf`) or `.htaccess`:
```xml
<Directory "/var/www/html/admin">
    AuthType Basic
    AuthName "Admin Panel"
    AuthUserFile /etc/apache2/.htpasswd
    <Limit GET>
        Require valid-user
    </Limit>
</Directory>
```
- `<Limit GET>` → auth applies **only to GET**; page remains accessible via POST, HEAD, etc.

### Tomcat example (vulnerable)
Found in `web.xml`:
```xml
<security-constraint>
    <web-resource-collection>
        <url-pattern>/admin/*</url-pattern>
        <http-method>GET</http-method>
    </web-resource-collection>
    <auth-constraint>
        <role-name>admin</role-name>
    </auth-constraint>
</security-constraint>
```
- `<http-method>GET</http-method>` → restriction limited to GET only.

### ASP.NET example (vulnerable)
Found in `web.config`:
```xml
<system.web>
    <authorization>
        <allow verbs="GET" roles="admin">
            <deny verbs="GET" users="*">
        </deny>
        </allow>
    </authorization>
</system.web>
```
- `allow`/`deny` scoped to `verbs="GET"` only → other verbs bypass the rule.

### Fix
- **Never** restrict authorization to a specific HTTP verb — always allow/deny **all** verbs.
- To intentionally exempt one method, use safe "all-except" style keywords:

| Server | Safe keyword |
|---|---|
| Apache | `LimitExcept` |
| Tomcat | `http-method-omission` |
| ASP.NET | `add` / `remove` |

- General hardening tip: **disable/deny HEAD requests** unless the app specifically requires them.

## 2. Insecure Coding

**Core problem:** Harder to catch than config issues — requires spotting **inconsistent use of HTTP parameter sources** across different functions in the code.

### Vulnerable PHP example
```php
if (isset($_REQUEST['filename'])) {
    if (!preg_match('/[^A-Za-z0-9. _-]/', $_POST['filename'])) {
        system("touch " . $_REQUEST['filename']);
    } else {
        echo "Malicious Request Denied!";
    }
}
```
- **Looks secure** at a glance — `preg_match` blocks special characters.
- **The real flaw:** filter checks `$_POST['filename']`, but the command execution uses `$_REQUEST['filename']` (covers **GET + POST**).
- **Exploit path:** send payload via **GET** → `$_POST['filename']` is empty → passes the filter (no special chars found) → `$_REQUEST['filename']` still picks up the malicious GET value → command injection executes.
- In real-world code, this is **much subtler**: filtering and execution are often in separate functions, spread across the codebase — not on consecutive lines — making the inconsistency easy to miss and more likely to reach production.

### Fix
- Be **consistent** with HTTP method/parameter sources for the **same functionality** everywhere in the app.
- Broaden security filters to check **all request parameters**, not just one method's:

| Language | All-methods parameter access |
|---|---|
| PHP | `$_REQUEST['param']` |
| Java | `request.getParameter('param')` |
| C# | `Request['param']` |

- If validation and execution logic use the **same, method-agnostic parameter source**, this bypass is avoided.

---

## Key takeaways (Prevention)
1. **Config-level:** never scope auth rules to a single/few HTTP verbs — use "except" style directives and disable unneeded methods (esp. HEAD).
2. **Code-level:** always validate the **same parameter source** that will later be used/executed — avoid mixing `$_GET`/`$_POST`/`$_REQUEST` inconsistently.
3. Insecure config is easier to spot and patch; insecure coding is harder to detect and more common in production.
