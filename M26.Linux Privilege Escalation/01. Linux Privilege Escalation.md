# Linux Privilege Escalation — CPTS Exam Notes

## 1. Introduction to Linux Privilege Escalation

**Linux privilege escalation** is the process of obtaining higher privileges on a Linux system, typically from a low-privileged user to `root`.

The `root` account has full administrative access to the operating system.

### Why Is Privilege Escalation Important?

Gaining root access may allow an attacker to:

* Access sensitive files and system configurations.
* Capture network traffic.
* Read credentials and other secrets.
* Access other systems using discovered credentials or SSH keys.
* Obtain NTLM hashes and investigate Active Directory when the Linux host is domain-joined.

**Key concept:** After obtaining an initial shell, enumerate the system thoroughly before attempting privilege escalation.

---

## 2. Linux Privilege Escalation Enumeration

Enumeration is the foundation of privilege escalation. Automated scripts such as [LinEnum](https://github.com/rebootuser/LinEnum) can assist, but understanding manual enumeration is essential during the CPTS exam.

### 2.1 Operating System Version

Identify the Linux distribution and version to determine available tools and potential vulnerabilities.

```bash
cat /etc/os-release
uname -a
```

**Look for:**

* Distribution: Ubuntu, Debian, Fedora, CentOS, Red Hat, etc.
* Operating system version.
* Outdated software or versions with known vulnerabilities.

### 2.2 Kernel Version

The kernel version may reveal publicly known local privilege escalation vulnerabilities.

```bash
uname -r
uname -a
```

**Important:** Kernel exploits can cause system instability or crashes. Understand their behavior and potential impact before executing them.

### 2.3 Running Services and Processes

Processes running as `root` deserve particular attention, especially if they use vulnerable software or insecure configurations.

#### List Processes Running as Root

```bash
ps aux | grep root
```

#### List Processes Attached to Terminals

```bash
ps au
```

**Look for:**

* Services running with root privileges.
* Unexpected or unusual processes.
* Vulnerable or outdated services.
* Processes associated with other logged-in users.

Services mentioned in the source material include Nagios, Exim, Samba, and ProFTPd.

**Example vulnerability:** CVE-2016-9566 is cited in the source material as a local privilege escalation vulnerability affecting Nagios Core versions earlier than 4.2.4.

## 3. Installed Packages and Versions

Outdated packages may contain vulnerabilities that can be exploited for privilege escalation.

### Enumeration

```bash
dpkg -l
```

On RPM-based systems:

```bash
rpm -qa
```

**What to check:**

* Installed software and versions.
* Known vulnerabilities affecting installed packages.
* Software with elevated privileges.

**Example:** GNU Screen version `4.05.00` is mentioned in the source material as having a privilege escalation vulnerability.

**Exam tip:** Identify the exact software version before investigating a potential exploit.

## 4. Logged-In Users and User Enumeration

Identifying other users can reveal possible lateral movement opportunities and additional privilege escalation paths.

### List User Accounts

```bash
cat /etc/passwd
```

### List Home Directories

```bash
ls -la /home
```

### Inspect a Specific User's Directory

```bash
ls -la /home/<username>/
```

**Look for:**

* Other user accounts.
* Accessible home directories.
* Sensitive configuration files.
* SSH keys.
* Bash history files.
* Scripts and backup files.

## 5. User Home Directories and SSH Keys

User directories may contain credentials, private SSH keys, configuration files, or scripts that reveal additional access paths.

### Inspect a User's Home Directory

```bash
ls -la /home/<username>/
```

### Check SSH Directory Contents

```bash
ls -la ~/.ssh/
```

Common SSH key filenames include:

| File              | Purpose                                               |
| ----------------- | ----------------------------------------------------- |
| `id_rsa`          | Common filename for an RSA private key                |
| `id_rsa.pub`      | Corresponding public key                              |
| `authorized_keys` | Public keys authorized to authenticate to the account |
| `known_hosts`     | Records of previously encountered SSH hosts           |

### Why SSH Keys Matter

If a usable private key is discovered, it may allow authentication to another system, depending on the key's permissions, account access, and SSH configuration.

The source material also recommends examining the ARP cache to identify other hosts that may be relevant when investigating discovered SSH keys.

### Check the ARP Cache

```bash
ip neigh
```

**Look for:**

* Internal hosts communicating with the machine.
* Potential SSH destinations.
* Accessible credentials or keys that may be valid on other systems.

## 6. Bash History Enumeration

Bash history can reveal commands executed by users and may expose credentials or information about system administration activities.

### View Command History

```bash
history
```

### Read a User's Bash History

```bash
cat /home/<username>/.bash_history
```

Check permissions before attempting to read another user's history.

### Look For

* Passwords passed as command-line arguments.
* SSH connections to other systems.
* Backup scripts.
* Git repositories and related configuration.
* Cron job creation or modification.
* Sensitive file paths and administrative commands.

**Exam tip:** A history entry may reveal a username, hostname, script path, or operational workflow that helps identify the next enumeration target.

## 7. Sudo Privileges

Sudo permissions determine which commands a user can execute with elevated privileges.

### Enumerate Sudo Permissions

```bash
sudo -l
```

Example output:

```text
User sysadm may run the following commands on NIX02:
    (root) NOPASSWD: /usr/sbin/tcpdump
```

### Important Sudo Terms

| Term       | Meaning                                                         |
| ---------- | --------------------------------------------------------------- |
| `sudo -l`  | Lists commands the current user may execute through sudo        |
| `NOPASSWD` | The specified command can be run without a sudo password prompt |
| `(root)`   | The command may be executed as the root user                    |

### Full Sudo Access

If the current user is permitted to run commands as root without restrictive limitations, the following command may provide a root shell:

```bash
sudo su
```

This only works when the user's sudo permissions allow it.

### Sudo Enumeration Checklist

* Identify every permitted command.
* Check the target user specified in each rule.
* Identify whether password authentication is required.
* Determine whether the permitted command can execute other commands or interact with privileged files.
* Investigate the command's functionality and security implications.

**Key concept:** Having sudo access does not automatically mean root access. The permitted command and its configuration determine whether escalation is possible.

## 8. Configuration Files and Credential Discovery

Configuration files frequently contain information about applications, services, users, and credentials.

### Search for Configuration Files

```bash
find / -type f \( -name "*.conf" -o -name "*.config" \) 2>/dev/null
```

### Search for Potential Credential References

```bash
grep -RniE 'password|passwd|username|user|secret|token' /etc 2>/dev/null
```

**Look for:**

* Usernames and passwords.
* API tokens and application secrets.
* Database credentials.
* Service configuration details.
* File paths referenced by privileged services.

**Important:** A matching string is not necessarily a valid credential. Verify the context and permissions before drawing conclusions.

## 9. Linux Password Files: `/etc/passwd` and `/etc/shadow`

### 9.1 `/etc/passwd`

The `/etc/passwd` file contains account information and is normally readable by all users.

```bash
cat /etc/passwd
```

Typical entry:

```text
mrb3n:x:1000:1000:mrb3n,,,:/home/mrb3n:/bin/bash
```

### `/etc/passwd` Field Structure

```text
username:password:UID:GID:comment:home_directory:login_shell
```

| Field          | Description                                                    |
| -------------- | -------------------------------------------------------------- |
| Username       | Account name                                                   |
| Password       | Commonly `x`, indicating the password hash is stored elsewhere |
| UID            | User ID                                                        |
| GID            | Primary group ID                                               |
| Comment        | Account description or user information                        |
| Home directory | User's home directory                                          |
| Login shell    | Shell or executable configured for login                       |

**Important:** A password hash may occasionally be stored directly in the password field instead of `x`, indicating an unusual or potentially insecure configuration.

### 9.2 `/etc/shadow`

The `/etc/shadow` file normally stores password hashes and is restricted to privileged access.

```bash
ls -l /etc/shadow
```

If the file is readable due to misconfiguration, its contents may expose password hashes for offline password-cracking attempts.

### Password Hash Investigation

If a hash is discovered:

1. Identify the account associated with it.
2. Determine the likely hash format.
3. Assess whether the hash can be recovered through authorized offline password auditing.
4. Verify any recovered credential only in an authorized environment.

**Exam tip:** Check both `/etc/passwd` and `/etc/shadow` permissions. Do not assume the password hashes are stored in `/etc/passwd`.

## 10. Cron Jobs and Scheduled Tasks

Cron jobs execute scheduled commands and are commonly used for maintenance, logging, and backups.

A privileged cron job may create a privilege escalation opportunity if its script, dependencies, or execution environment are improperly secured.

### Inspect Daily Cron Jobs

```bash
ls -la /etc/cron.daily/
```

### Inspect Other Cron Locations

```bash
ls -la /etc/cron.d/
ls -la /etc/cron.hourly/
ls -la /etc/cron.weekly/
ls -la /etc/cron.monthly/
```

### Inspect the System Crontab

```bash
cat /etc/crontab
```

### Inspect User Cron Jobs

```bash
crontab -l
```

For other users, access depends on the permissions and privileges available to the current account.

### What to Investigate

* Scripts executed by root.
* Scripts or configuration files writable by lower-privileged users.
* Relative executable paths.
* Unsafe file permissions.
* Backup scripts and their dependencies.
* The frequency with which a scheduled task executes.

**Key concept:** A root-owned cron job alone is not a vulnerability. The important question is whether an unprivileged user can influence what it executes.

## 11. Unmounted File Systems and Additional Drives

Additional partitions or unmounted file systems may contain backups, credentials, or sensitive files.

### List Block Devices

```bash
lsblk
```

### Display Mounted File Systems

```bash
findmnt
```

### Review Disk Usage and Mount Points

```bash
df -h
```

### What to Look For

* Additional partitions.
* Unmounted file systems.
* Backup volumes.
* Data directories containing sensitive information.
* Files that may be accessible through existing permissions.

**Exam tip:** Discovering a disk does not guarantee that it is mountable or readable. Access depends on the system configuration and the current user's privileges.

## 12. SUID and SGID Permissions

SUID and SGID are special permission bits that can change the effective user or group identity used when a program executes.

* **SUID (Set User ID):** Can cause an executable to run with the file owner's effective UID.
* **SGID (Set Group ID):** Can cause an executable to run with the file's group identity. On directories, SGID also affects group ownership inheritance for newly created entries.

If an executable runs with elevated privileges and exposes unsafe functionality, it may provide a privilege escalation path.

### Find SUID Files

```bash
find / -type f -perm -4000 2>/dev/null
```

### Find SGID Files

```bash
find / -type f -perm -2000 2>/dev/null
```

### What to Investigate

* Unusual SUID or SGID binaries.
* Executables owned by root.
* Custom scripts or programs with special permissions.
* Known vulnerabilities in installed binaries.
* Unsafe command execution or file-handling behavior.

**Important:** SUID or SGID permissions alone do not prove that a binary is exploitable. Investigate its functionality and configuration.

## 13. Writable Directories

Writable directories can allow users to create or modify files. This becomes important when privileged processes use those directories.

### Find World-Writable Directories

```bash
find / -path /proc -prune -o -type d -perm -o+w 2>/dev/null
```

Example locations may include:

```text
/tmp
/var/tmp
/dev/shm
```

Other writable locations may be more significant if they are used by privileged scripts or services.

### What to Investigate

* Directories writable by the current user.
* Backup directories.
* Directories used by cron jobs.
* Application and service directories.
* Locations where privileged processes create or execute files.

**Key concept:** A writable directory is only a meaningful escalation lead when its usage, permissions, or interaction with privileged processes creates an exploitable condition.

---

## 14. Writable Files

Writable scripts and configuration files may expose privilege escalation opportunities, especially when executed or read by privileged services.

### Find World-Writable Files

```bash
find / -path /proc -prune -o -type f -perm -o+w 2>/dev/null
```

Example files from the source material:

```text
/etc/cron.daily/backup
/dmz-backups/backup.sh
/home/backupsvc/backup.sh
```

### What to Investigate

* Scripts executed by root.
* Backup scripts and their dependencies.
* Configuration files used by privileged services.
* Files writable by the current user but owned by another account.
* Whether a privileged process trusts or executes the file.

**Important:** Do not modify system files blindly. First determine their ownership, permissions, execution context, and operational impact.

## 16. CPTS Exam Enumeration Checklist

Use this checklist after obtaining an initial low-privileged Linux shell.

### System Information

* [ ] Identify the OS distribution and version.
* [ ] Identify the kernel version.
* [ ] Review installed packages and versions.
* [ ] Inspect running services and processes.

### Users and Credentials

* [ ] Enumerate user accounts.
* [ ] Inspect accessible home directories.
* [ ] Check readable Bash history files.
* [ ] Inspect accessible SSH keys and configuration files.
* [ ] Review configuration files for credentials and secrets.
* [ ] Check `/etc/passwd` and `/etc/shadow` permissions.

### Privileges and Scheduled Tasks

* [ ] Run `sudo -l`.
* [ ] Inspect SUID binaries.
* [ ] Inspect SGID binaries.
* [ ] Review cron jobs and scheduled scripts.
* [ ] Identify privileged scripts or dependencies that may be writable.

### Files and Storage

* [ ] Identify writable directories.
* [ ] Identify writable files.
* [ ] Inspect backup locations.
* [ ] Enumerate block devices and mounted file systems.
* [ ] Investigate relevant internal hosts and SSH access paths.

### Analysis

* [ ] Correlate findings instead of treating each one independently.
* [ ] Determine whether a finding actually creates an exploitable privilege boundary.
* [ ] Research relevant software versions and known vulnerabilities.
* [ ] Understand the potential impact before executing an exploit.

## 17. Key Takeaways

1. **Enumeration comes first.** Thorough system discovery helps identify the available privilege escalation paths.
2. **Prioritize privileged processes.** Services and scripts running as root deserve particular attention.
3. **Inspect permissions carefully.** Sudo rules, SUID/SGID binaries, writable scripts, and cron jobs can reveal misconfigurations.
4. **Look for credentials.** Bash history, SSH keys, configuration files, and password hashes may provide additional access.
5. **Check the broader environment.** Additional disks, backup directories, and internal hosts may reveal further opportunities.
6. **Validate every lead.** A suspicious file or unusual permission is not automatically an exploitable vulnerability.
7. **Understand your findings.** Automated enumeration tools can help, but manual analysis is essential for interpreting results.

### Final Exam Strategy

**Initial shell → System enumeration → User and credential enumeration → Privilege and permission checks → Identify a viable path → Validate and escalate within the authorized assessment.**

The objective is not simply to collect command output. It is to understand how the system is configured and identify a specific, evidence-supported route to higher privileges.
