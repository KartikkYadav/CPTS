 # Identifying Filters

---

## Injection Mitigations Overview

- Even "securely coded" apps may still be exploitable if mitigations are weak/incomplete.
- Common mitigation layers:
  1. **Blacklisted characters/words** on the back-end — detects injection attempts, denies the request.
  2. **Web Application Firewalls (WAFs)** — broader scope, detects/blocks injections, SQLi, XSS, etc.

---

## Filter/WAF Detection

- Same `Host Checker` app, now with mitigations.
- Previously working operators (`;`, `&&`, `||`) now trigger: **`invalid input`**.
- **Where the error appears matters:**
  - Error shown **in the output field** → likely detected/blocked by the **PHP application itself**.
  - Error shown on a **different page** (with info like your IP, request details) → likely blocked by a **WAF**.

### Test Payload

```bash
127.0.0.1; whoami
```

Components sent (besides the known-good IP):
1. Semi-colon `;`
2. Space character
3. `whoami` command

→ App may have blacklisted a **character**, a **command**, or both.

---

## Blacklisted Characters

Example vulnerable-but-filtered PHP logic:

```php
$blacklist = ['&', '|', ';', ...SNIP...];
foreach ($blacklist as $character) {
    if (strpos($_POST['ip'], $character) !== false) {
        echo "Invalid input";
    }
}
```

- Any blacklisted character found anywhere in the input → request denied.

### Identifying the Blacklisted Character

- Reduce the payload to **one change at a time**.
- Baseline: `127.0.0.1` → works.
- Test: `127.0.0.1;` → still returns `invalid input` → **semicolon `;` is blacklisted**.
- Next step: test each injection operator individually to map out the full blacklist.

---

## Key Takeaways

- Always isolate variables: test one character/operator at a time to pinpoint exactly what's filtered.
- Error message location/format is a clue to **where** filtering happens (app-level vs WAF-level).
- Goal of this section: build a picture of the blacklist before attempting to bypass it.
