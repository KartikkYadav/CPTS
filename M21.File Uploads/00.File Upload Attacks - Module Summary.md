# M21 — File Upload Attacks: Module Summary

> Consolidated wrap-up of files 01–05 in the [CPTS repository's File Uploads module](https://github.com/KartikkYadav/CPTS/tree/main/M21.File%20Uploads). Use only in an authorized lab or assessment.

## 1. Core Concept

A file-upload vulnerability occurs when an application fails to validate, store, or serve uploaded files safely. The impact depends on multiple conditions—not simply whether the upload succeeds.

Potential outcomes include:

- **Stored XSS** through uploaded HTML, SVG, or unsafely rendered metadata.
- **XML External Entity (XXE)** when an uploaded XML-based format is processed by a vulnerable XML parser.
- **Server-side code execution** when a script is accepted, stored in a reachable location, and interpreted by the server.
- **Denial of Service (DoS)** through excessive file size, expensive decompression, malicious image dimensions, or unsafe parser behavior.
- **Information disclosure / SSRF** when a vulnerable XML or document-processing component can access local files or internal services.

### The exploitation decision tree

```text
Can the application accept the file?
              |
              v
Does server-side validation reject it?
              |
              v
Where is the file stored, and is it reachable?
              |
              v
How does the server/browser process the file?
              |
              +--> Is it interpreted as server-side code?
              |        |
              |        +--> Potential code execution
              |
              +--> Is active content rendered in a browser?
              |        |
              |        +--> Potential XSS
              |
              +--> Is attacker-controlled XML parsed unsafely?
              |        |
              |        +--> Potential XXE / SSRF / file disclosure
              |
              +--> Is processing resource-intensive?
                       |
                       +--> Potential DoS
```

**Remember:** A successful upload does not by itself prove that the file is accessible or executable.

## 2. File Upload Vulnerabilities and Missing Validation

### What to inspect

During initial assessment, determine whether the application:

- Enforces an extension allowlist on the **server**.
- Validates the file's actual format and content, not just its supplied name.
- Checks MIME type as one signal—not as the only control.
- Generates a safe server-side filename.
- Limits file size and processing resources.
- Stores uploads outside the web root where possible.
- Prevents scripts and other active content from executing in upload directories.
- Serves user-controlled files with safe response headers and an appropriate content type.

### Identify the technology

The server-side language matters when assessing whether an uploaded script could execute. Typical filename hints include:

| Extension | Common technology |
|---|---|
| `.php` | PHP |
| `.asp` | Classic ASP |
| `.aspx` | ASP.NET |
| `.jsp` | Java / JSP |

Technology clues can come from response headers, page behavior, source references, known routes, and tools such as Wappalyzer. Treat fingerprinting as an indication rather than proof: frameworks can hide file extensions, and applications may use multiple technologies.

### Conditions for server-side execution

The following conditions generally need to align:

1. The application accepts a script or a file that the server treats as a script.
2. The file is saved in a location that can be requested.
3. The server is configured to interpret that file type there.
4. The request reaches the uploaded file and triggers its processing.

A safe validation test in an authorized lab can use a harmless script that prints a fixed marker. Confirm whether the server returns the marker as executed output or merely displays the source. Do not assume execution solely from an “upload successful” message.

## 3. Upload Exploitation: Understand the Stages

A typical authorized workflow is:

1. **Reconnaissance:** inspect the upload form, application behavior, technology hints, and response messages.
2. **Validation review:** determine whether controls exist on the client, server, or both.
3. **Controlled testing:** submit benign files and compare outcomes as one property is changed at a time.
4. **Storage discovery:** identify the returned URL/path or the application's documented retrieval workflow.
5. **Processing verification:** determine whether the file is rendered, downloaded, parsed, converted, or executed.
6. **Impact validation:** use a minimal, non-destructive proof appropriate to the suspected issue.
7. **Documentation:** retain the exact request, response, filename, content type, location, and evidence supporting each conclusion.

### Web shell vs reverse shell

| Type | How it works | Assessment notes |
|---|---|---|
| **Web shell** | Accepts command input through web requests | Depends on server-side code execution and may be restricted by PHP/runtime configuration |
| **Reverse shell** | The server initiates a connection to a listener | Also depends on execution, network reachability, egress rules, and runtime capabilities |

A shell payload is not a validation test in itself. First establish that the application stores the file where expected and that the server executes its file type. In real systems, use non-destructive proof-of-execution checks and follow the engagement's authorization and rules of engagement.

## 4. Client-Side Validation Bypass

Client-side controls improve usability but **must not be trusted as a security boundary**. Common examples include:

- HTML file-input `accept` attributes.
- JavaScript checks triggered by `onchange`.
- Browser-side checks for filename extensions or file size.

A proxy such as Burp Suite can be used in an authorized test to observe the upload request and verify whether the server independently enforces the same restrictions. Developer Tools can help identify the client-side logic, but removing a browser check does not change server-side enforcement.

### Useful indicators to recognize

| Indicator | What it suggests |
|---|---|
| `accept=".jpg,.jpeg,.png"` | File-picker guidance; not server-side enforcement |
| `onchange="checkFile(this)"` | A JavaScript validation hook may be used |
| A filename in `Content-Disposition` | The client supplies a filename that must be treated as untrusted |
| Upload accepted after a request modification | The modified request passed some checks; further validation is still required |
| Browser shows an uploaded-file URL | Indicates a potential retrieval path, not proof of server-side execution |

**Troubleshooting principle:** If a browser blocks a file but a modified request reaches the server, inspect the server's response. If the server rejects it, the restriction is not merely client-side.

## 5. Blacklist Filters and Extension Fuzzing

### Blacklist vs allowlist

| Approach | Behavior | Security characteristics |
|---|---|---|
| **Blacklist** | Rejects a list of known-bad extensions | Fragile; can miss alternatives, case variants, or server-specific mappings |
| **Allowlist** | Permits only explicitly supported extensions | Preferable, but should be combined with content validation and safe storage |
| **MIME check** | Checks the declared media type | The supplied MIME type can be spoofed; it is not sufficient alone |
| **Signature/content check** | Inspects file bytes or parses the expected format | Stronger when implemented with robust libraries, though parser risks remain |

A weak blacklist might compare only the extension extracted by `pathinfo()`. Its effectiveness depends on the list, normalization, case handling, server configuration, and how the application maps filenames to handlers.

### Controlled extension testing

In an authorized lab, extension fuzzing helps characterize the filter:

1. Capture a baseline upload request with a benign file.
2. Change only the filename extension while keeping other request fields constant.
3. Compare status code, response body, response length, and any returned file identifier.
4. Record which extensions are rejected and which are accepted.
5. For accepted types, separately determine how the server handles the file before drawing conclusions.

Burp Intruder can automate variation of a single extension position using a suitable wordlist. Response differences are more informative than status codes alone; applications may return the same status for rejection and acceptance.

**Critical distinction:** An extension that passes the upload filter is not automatically an executable extension. Execution depends on server configuration, handler mappings, storage location, and request routing.

### Case and filename handling

Case variations can expose inconsistent normalization where comparisons are case-sensitive. Path cleanup such as PHP's `basename()` only removes directory components from a name; it does not validate the content or guarantee safe storage. Date prefixes and similar naming schemes can also create collisions.

## 6. Limited File Uploads: Attacks Beyond Script Execution

A form that allows only images or documents can still introduce risks. The result depends on how the uploaded content is rendered or parsed.

### XSS through HTML, SVG, and metadata

- **HTML:** an uploaded HTML document can contain active browser content. Risk increases when it is served from a trusted origin and opened by another user.
- **SVG:** SVG is XML-based and may support active content in some browser contexts. Whether script runs depends on how the SVG is embedded, served, and protected by browser security controls.
- **Image metadata:** if the application places metadata into HTML without context-appropriate output encoding, metadata can become a stored-XSS vector.
- **Content type:** serving an uploaded file with an unsafe or incorrect media type can change how browsers interpret it. Use correct server-generated content types and safe disposition/nosniff policies.

For a lab, verify XSS using a harmless marker or alert and document the exact rendering context. A payload stored in a file does not prove a vulnerability unless it is interpreted in a vulnerable context.

### XXE through XML processing

XXE requires a component to parse attacker-controlled XML with external entity resolution or another unsafe XML feature enabled. SVG and XML documents can be relevant because they contain XML; some document formats also package XML internally.

Potential impacts include:

- Local file disclosure.
- Disclosure of application source or configuration.
- Requests to internal resources (SSRF-like behavior).
- Blind interactions where the data is not returned directly.

**Important format distinction:** A normal JPEG parser does not interpret XML external entities. Putting XML text into a JPG, or merely renaming SVG to `.jpg`, does not automatically create XXE. First establish whether the backend invokes an XML-aware parser or a vulnerable document conversion component.

In an authorized lab, use a controlled harmless file or an explicitly designated test resource. Do not access sensitive files or internal services without specific authorization.

### Denial of Service (DoS)

File uploads can consume storage, memory, CPU, or parser resources. Relevant classes include:

| Technique | Risk mechanism |
|---|---|
| Excessive upload size | Disk exhaustion or slow processing |
| Decompression bomb | Small compressed input expands to huge output |
| Malformed or extreme image dimensions | Expensive allocation or image-processing exhaustion |
| Unsafe XML/entity processing | Excessive expansion, resource access, or parser exhaustion |
| Path traversal in the destination name | Writing outside the intended directory, potentially overwriting files |

DoS validation must be controlled and non-destructive. Use limits, test fixtures, and isolated environments rather than generating resource-exhaustion files against production systems.

## 7. Practical Assessment Checklist

### Reconnaissance and validation

- [ ] Identify the upload endpoint and the expected workflow.
- [ ] Record allowed types, size limits, and server responses.
- [ ] Determine whether checks are client-side, server-side, or both.
- [ ] Review filename handling, extension normalization, MIME handling, and actual file-content validation.
- [ ] Check how the server stores and serves uploaded files.
- [ ] Identify whether the upload directory can execute scripts.

### Filter testing

- [ ] Keep a baseline request and response.
- [ ] Test one variable at a time in an authorized environment.
- [ ] Distinguish allowlist behavior from blacklist behavior.
- [ ] Compare response body, length, status, and generated file path.
- [ ] Remember: accepted extension does not imply code execution.

### Limited-file testing

- [ ] Determine whether HTML/SVG content is rendered by the browser.
- [ ] Check whether metadata is safely encoded before display.
- [ ] Determine whether XML-based content is parsed by the backend.
- [ ] Verify whether document/image conversion introduces a risky parser.
- [ ] Consider file-size, decompression, image-processing, and storage limits.
- [ ] Avoid destructive DoS tests and unauthorized local-file/internal-service access.

### Evidence and reporting

For each test, record:

- Request URL and method.
- Relevant headers and multipart fields.
- Original filename, supplied content type, and actual file format.
- Exact response/status and any uploaded-file URL.
- Whether the file was stored, rendered, downloaded, parsed, or executed.
- Screenshots or response excerpts supporting the conclusion.
- Impact, reproducibility, and a practical remediation.

## 8. Common Troubleshooting

### Problem: Upload reports success, but the file does not execute

**Symptoms:** The application confirms the upload, but requesting the file does not execute code.

**Possible causes:**
- The file is stored outside the web root or served through a download handler.
- The extension is not mapped to the server-side interpreter.
- Script execution is disabled in the upload directory.
- The file URL/path is incorrect, or authorization is required.
- Runtime functions or outbound network access are restricted.

**Next step:** Verify file retrieval and handler behavior independently using a benign test. Do not infer RCE from the upload response.

### Problem: A blacklist bypass candidate is accepted but has no impact

**Symptoms:** The upload succeeds, but the file is downloaded, displayed as text, or rejected when opened.

**Possible causes:**
- The extension is not executable on that server.
- The application changes the filename or serves the file statically.
- The server applies additional content validation or processing.
- The uploaded object is not directly reachable.

**Next step:** Document the accepted extension and investigate processing/serving behavior separately.

### Problem: XXE payload in an uploaded image does not work

**Symptoms:** The image uploads normally, but no XML entity is processed.

**Possible causes:**
- The format is not XML-based (for example, ordinary JPEG).
- No XML parser processes the uploaded content.
- External entities are disabled or blocked.
- The SVG is embedded in a context that does not execute/parse the expected features.
- The application sanitizes, rasterizes, or rejects the file.

**Next step:** Identify the actual parser and processing route. Do not assume that every image upload invokes an XML parser.

## 9. Defensive Recommendations

1. **Use a strict server-side allowlist** based on the business requirement.
2. Validate extension, detected format, and file content; do not rely on the client-supplied MIME type.
3. Generate random server-side filenames and safely handle collisions.
4. Store uploaded files outside the web root or serve them from a separate origin.
5. Disable script execution in upload directories and use least-privilege filesystem permissions.
6. Serve files with correct content types, safe content-disposition policies, and appropriate anti-sniffing headers.
7. Sanitize or safely encode metadata before inserting it into HTML.
8. Disable XML external entities and unnecessary external resource resolution in XML/document parsers.
9. Apply upload-size, decompression, dimension, timeout, and resource limits.
10. Keep parsing and image/document conversion libraries patched, and log validation failures.

## 10. Final Mental Model

| Question | What it tells you |
|---|---|
| Can the file be uploaded? | Whether the request passes upload validation |
| Where is it stored? | Whether it may be reachable and what controls apply |
| Can I request it? | Whether the uploaded object is accessible |
| How is it served or processed? | Whether the browser, script engine, XML parser, or converter handles it |
| What is the demonstrated impact? | Whether evidence supports XSS, XXE, code execution, disclosure, SSRF, or DoS |

The central lesson of this module is that **file-upload security is not just an extension-filter problem**. Validate the content on the server, store and serve it safely, and understand the component that processes it. Always distinguish a filter bypass from a confirmed vulnerability and a confirmed vulnerability from demonstrated impact.
