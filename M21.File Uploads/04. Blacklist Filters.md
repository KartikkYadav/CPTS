# Blacklist Filters

## 1. Key Concept

**Never rely only on client-side validation.**

- Client-side validation can be easily bypassed by modifying the HTTP request.
- Security controls should always be implemented **server-side**.
- However, poorly implemented server-side validation can also be bypassed.
- A common weak implementation is an **extension blacklist**.

### File Upload Validation Methods

| Method | Description | Security |
|---|---|---|
| **Blacklist** | Reject specific dangerous extensions | Weak |
| **Whitelist** | Allow only known-safe extensions | Better |
| **File type validation** | Validate actual MIME/file type | Better |
| **Content validation** | Inspect file contents/signature | Better |

> **Exam takeaway:** A blacklist is generally weak because it is impossible to reliably enumerate every potentially executable extension.

---

# 2. Blacklisting Extensions

A typical vulnerable blacklist implementation may look like:

```php
$fileName = basename($_FILES["uploadFile"]["name"]);
$extension = pathinfo($fileName, PATHINFO_EXTENSION);

$blacklist = array('php', 'php7', 'phps');

if (in_array($extension, $blacklist)) {
    echo "File type not allowed";
    die();
}
```

### How It Works

1. Get the uploaded filename.
2. Extract the extension using `pathinfo()`.
3. Compare the extension against a blacklist.
4. Reject the upload if it matches.

### Weakness

The blacklist only blocks extensions explicitly included:

```text
.php
.php7
.phps
```

Other PHP-enabled extensions may not be included and could potentially execute PHP code.

---

# 3. Case-Sensitivity Bypass

The comparison may also be **case-sensitive**.

For example:

```text
.php
```

may be blocked while:

```text
.pHp
.PhP
.PHP
```

may bypass the blacklist.

This is especially relevant on **Windows**, where filenames are generally case-insensitive.

### Exam Point

When testing an extension blacklist, always consider:

- Alternative extensions
- Case variations
- Server-specific executable extensions

> A secure implementation should normalize the extension before comparison.

---

# 4. Fuzzing File Extensions

Instead of manually testing extensions, **fuzz the upload functionality** with a wordlist containing possible executable extensions.

### Goal

Identify extensions that:

- Do **not** return `Extension not allowed`
- Return a different response
- Successfully upload the file

These extensions may be allowed by the blacklist.

---

## Useful Wordlists

### PayloadsAllTheThings

PHP extension list:

```text
Upload Insecure Files/Extension PHP/extensions.lst
```

ASP/.NET extension list:

```text
Upload Insecure Files/Extension ASP
```

### SecLists

Common web extensions:

```text
Discovery/Web-Content/web-extensions.txt
```

# 5. Burp Suite Intruder — Extension Fuzzing

### Workflow

1. Upload a test file.
2. Capture the request in **Burp Suite**.
3. Find the request to:

```text
/upload.php
```

4. Right-click → **Send to Intruder**.
5. Go to **Positions**.
6. Click **Clear** to remove automatically selected positions.
7. Select only the extension in:

```http
filename="HTB.php"
```

8. Add the extension as the fuzzing position:

```http
filename="HTB.§php§"
```

9. Go to **Payloads**.
10. Load the PHP extension wordlist.
11. Disable **URL Encoding** so the `.` in the extension is not encoded.
12. Start the attack.

---

# 6. Interpreting Intruder Results

Look for responses that differ from the normal blacklist response.

Example:

```text
Extension not allowed
```

indicates the extension was blocked.

A response such as:

```text
File successfully uploaded
```

indicates the extension passed the blacklist.

### Useful Indicators

Sort Intruder results by:

- **Length**
- HTTP status
- Response body

For example:

```text
Content-Length: 193
File successfully uploaded
```

may identify extensions that bypass the blacklist.

> **Exam takeaway:** When fuzzing, look for response differences rather than only HTTP status codes. A successful bypass may return the same HTTP status as a failed request.

---

# 7. Non-Blacklisted Extensions

Finding an extension that bypasses the blacklist does **not automatically mean PHP execution is possible**.

The extension must also be recognized by the target web server/PHP configuration as executable.

Therefore:

> **Allowed extension ≠ automatically executable extension**

Different server configurations support different PHP-related extensions.

---

## Common Example: `.phtml`

A potentially useful alternative is:

```text
.phtml
```

Some PHP server configurations allow `.phtml` files to execute PHP code.

### Workflow

1. Find a `.phtml` request that successfully passed the blacklist.
2. Send the request to **Repeater**.
3. Change the filename to:

```text
shell.phtml
```

4. Replace the file contents with the desired PHP payload/web shell.
5. Send the request.
6. Confirm that the server reports successful upload.

---

# 8. Accessing the Uploaded File

If uploaded files are stored in:

```text
/profile_images/
```

the uploaded file may be accessible at:

```text
/profile_images/shell.phtml
```

If the file is executed by the server, PHP parameters can potentially be used to interact with it.

Example:

```text
/profile_images/shell.phtml?cmd=id
```

A successful response may execute:

```bash
id
```

and return information such as:

```text
uid=33(www-data)
gid=33(www-data)
groups=33(www-data)
```

This confirms that the uploaded PHP file is being **executed server-side**.

---

# 9. Attack Chain

The overall process can be remembered as:

```text
Upload Image
     ↓
Intercept Request with Burp
     ↓
Replace Filename/Content
     ↓
.php → Extension Blocked
     ↓
Identify Blacklist
     ↓
Fuzz Alternative Extensions
     ↓
Find Non-Blacklisted Extension
     ↓
Test Executable PHP Extension
     ↓
Upload PHP Payload
     ↓
Access Uploaded File
     ↓
Confirm Code Execution
```

# 10. CPTS Exam Checklist

When dealing with a file-upload blacklist:

- [ ] Test whether validation exists only client-side.
- [ ] Intercept the upload request with Burp.
- [ ] Test direct modification of filename/content.
- [ ] Determine whether the server uses a blacklist or whitelist.
- [ ] Inspect the blacklist behavior.
- [ ] Test **case variations**.
- [ ] Fuzz alternative extensions.
- [ ] Use PHP extension wordlists.
- [ ] Compare response **length/body/status**.
- [ ] Identify extensions that bypass the blacklist.
- [ ] Determine which allowed extensions can actually execute PHP.
- [ ] Test candidates such as `.phtml` where appropriate.
- [ ] Upload the payload using the allowed extension.
- [ ] Locate the uploaded file.
- [ ] Request the file directly.
- [ ] Verify server-side code execution.

---


### Most Important Exam Concept

> **A file-upload blacklist is only as strong as its completeness and implementation.** Alternative extensions, case variations, and server-specific executable extensions can potentially bypass poorly implemented blacklists.
