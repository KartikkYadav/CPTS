# Burp Scanner

## 1. Overview

**Burp Scanner** is a web vulnerability scanning feature in Burp Suite that helps identify potential security vulnerabilities in web applications.

It consists of two main components:

- **Crawler:** Discovers pages, links, forms, and application structure.
- **Scanner:** Performs passive and active vulnerability scanning.

> **Important:** Burp Scanner is available only in **Burp Suite Professional**, not the Community Edition.

### Scanning Workflow


## 2. Target Scope

### What Is Target Scope?

The **Target Scope** defines which hosts, URLs, directories, and resources Burp Suite should process.

Scope can be used across Burp features to focus testing on authorized targets and avoid wasting resources on irrelevant URLs.

### Starting a Scan

Burp provides three common ways to initiate a scan:

1. Scan a specific request from **Proxy → HTTP history**.
2. Create a scan using **Dashboard → New Scan**.
3. Scan items already defined in the target scope.

To scan a request from Proxy History:

1. Open `Proxy → HTTP history`.
2. Right-click the desired request.
3. Select `Scan` to configure the scan.
4. Alternatively, select `Passive Scan` or `Active Scan` to start a scan with default settings, where available.

### Adding Targets to Scope

1. Navigate to `Target → Site map`.
2. Locate the desired host, directory, or resource.
3. Right-click the item.
4. Select `Add to scope`.

When the first item is added, Burp may offer to restrict its features to in-scope items only.

### Excluding Targets from Scope

Some resources should be excluded because accessing them may cause unwanted side effects, such as terminating a session through a logout function.

To exclude a resource:

1. Right-click the in-scope item.
2. Select `Remove from scope`.

Scope settings can be managed under:

`Target → Scope`

This interface allows you to add or remove targets and configure advanced scope rules using regular expressions.

**Key exam points:**

- Scope determines which targets are included in testing.
- Out-of-scope URLs can be ignored to conserve resources.
- Exclude sensitive or state-changing endpoints when appropriate.
- Confirm the authorized testing scope before scanning.

## 3. Crawler

### Purpose

The Burp Crawler automatically navigates a web application to discover its accessible content and build a site map.

It discovers content by:

- Following links found in pages.
- Accessing forms.
- Examining requests generated by the application.
- Mapping discovered pages and resources.

### Crawl Options

Burp's scan configuration provides two main options:

| Option | Function |
|---|---|
| `Crawl` | Discovers and maps application content. |
| `Crawl and Audit` | Crawls the application and then performs vulnerability auditing. |

### Configuring a Crawl

1. Navigate to `Dashboard → New Scan`.
2. Select the appropriate target.
3. Choose `Crawl`.
4. Open the `Scan configuration` tab.
5. Select or create a crawl configuration.
6. Configure application login if authentication is required.
7. Click `OK` to start the scan.
8. Monitor progress in `Dashboard → Tasks`.
9. Review the updated site map under `Target → Site map`.

### Crawl Configuration

Burp provides predefined configurations through `Select from library`.

Example:

- `Crawl strategy - fastest`

Custom configurations can control settings such as:

- Crawling speed and limits.
- Authentication attempts.
- Other crawling behavior.

### Authenticated Crawling

Burp can be configured to access authenticated portions of a web application.

Authentication can be configured by:

- Providing credentials for login forms.
- Recording a sequence of login steps using the preconfigured browser.

Authenticated crawling is useful when important application functionality is available only after login.

### Important Limitation

**Crawling is not equivalent to directory brute-forcing.**

The crawler primarily follows discovered links and pages. It does not perform a fuzzing scan to discover every unlinked or unreferenced page.

Tools and features such as `ffuf`, `dirbuster`, Burp Intruder, and Content Discovery can help identify additional content. Discovered targets can then be added to scope when appropriate.

## 4. Passive Vulnerability Scanner

### What Is Passive Scanning?

A passive scan analyzes requests, responses, and page content that Burp has already observed to identify potential vulnerabilities.

**Key characteristic: A passive scan does not send new requests to test vulnerabilities.**

### What It Can Detect

Examples include:

- Cookies missing the `HttpOnly` flag.
- Responses that may be vulnerable to clickjacking.
- Missing HTML security-related elements.
- Potential DOM-based cross-site scripting (XSS).

### How to Start a Passive Scan

1. Open `Target → Site map` or `Proxy → HTTP history`.
2. Right-click the target or request.
3. Select `Do passive scan` or `Passively scan this target`, depending on the context.
4. Monitor the task in `Dashboard`.
5. Review findings under `Issue activity`.

### Advantages

- Does not actively probe the application.
- Useful for quickly reviewing observed traffic.
- Generally less intrusive than active scanning.
- Can identify potential security issues without sending additional test payloads.

### Limitations

- Findings may be potential vulnerabilities rather than verified exploitable flaws.
- Vulnerabilities requiring active testing may not be confirmed.
- Results depend on the traffic and application content Burp has observed.

### Severity and Confidence

Burp assigns findings a severity and a confidence level.

| Attribute | Meaning |
|---|---|
| Severity | Indicates the potential impact of the issue. |
| Confidence | Indicates how certain Burp is that the issue exists. |

For prioritization, pay particular attention to findings with **High severity** and **Certain confidence**.

For sensitive applications, review lower-severity and lower-confidence findings as well.

## 5. Active Vulnerability Scanner

### What Is Active Scanning?

An active scan performs more comprehensive testing by sending requests and injecting test payloads to identify and verify vulnerabilities.

Unlike passive scanning, active scanning **generates additional requests and may interact with application functionality**.

### Active Scan Workflow

According to the module, Burp's active scanner performs the following operations:

1. Crawls the application and uses web fuzzing to discover additional pages.
2. Performs passive scanning on discovered pages.
3. Sends requests to verify vulnerabilities identified by passive scanning.
4. Analyzes JavaScript to identify additional potential vulnerabilities.
5. Fuzzes discovered insertion points and parameters to test for common vulnerabilities.

### Vulnerability Classes

Active scanning can test for vulnerabilities such as:

- Cross-Site Scripting (XSS).
- OS Command Injection.
- SQL Injection.
- Other common web application vulnerabilities.

### How to Start an Active Scan

**Method 1: Scan a request**

1. Open `Proxy → HTTP history`.
2. Right-click the request.
3. Select `Do active scan`, where available.

**Method 2: Scan a target or scope**

1. Open `Dashboard → New Scan`.
2. Select the appropriate target.
3. Choose `Crawl and Audit`.
4. Configure crawling and auditing options.
5. Configure authentication if required.
6. Start the scan.
7. Monitor progress under `Dashboard → Tasks`.

### Audit Configuration

Audit configurations control which vulnerabilities Burp attempts to test and where it inserts payloads.

Configurations can be selected from the library or customized.

Example:

- `Audit checks - critical issues only`

This preset is useful when focusing on critical issues rather than running every available audit check.

### Monitoring Scan Requests

During an active scan, requests can be reviewed through:

- The scan task's `View details → Logger` tab.
- Burp's `Logger` tab.

The Logger records requests and responses passing through or generated by Burp, subject to its capture settings.

### Reviewing Findings

After the scan:

1. Open `Dashboard → Issue activity`.
2. Filter findings by severity and confidence.
3. Select an issue.
4. Read the advisory and technical details.
5. Inspect the associated request and response.
6. Determine whether the vulnerability is exploitable and assess its impact.

### Example: OS Command Injection

The module demonstrates an OS command injection finding with:

- **Severity:** High
- **Confidence:** Firm
- **Insertion point:** `ip` parameter

The issue details describe command injection involving a pipe character.

**Exam takeaway:** Do not rely only on the scanner's finding title. Review the insertion point, request, response, evidence, and advisory to understand the vulnerability and validate its impact.

### Active vs. Passive Scanning

| Feature | Passive Scan | Active Scan |
|---|---|---|
| Sends new test requests | No | Yes |
| Analyzes observed traffic | Yes | Yes |
| Injects test payloads | No active probing | Yes |
| Attempts to verify vulnerabilities | Limited | Yes |
| Can discover additional pages through active fuzzing | No | Yes, as described in the module |
| Potential impact on application state | Generally lower | Higher |
| Typical duration | Shorter | Longer |

**Important:** Active scans may generate substantial traffic, take considerably longer, and interact with application functionality. Use them only within the authorized scope and with suitable scan settings.

## 6. Understanding Severity and Confidence

Burp's issue listings help prioritize findings using severity and confidence.

### Severity

Severity indicates how serious a vulnerability may be.

Common levels include:

- High
- Medium
- Low
- Information

### Confidence

Confidence indicates how certain Burp is that the reported issue exists.

Examples of confidence labels used in the module include:

- Certain
- Firm

### Prioritization Strategy

A practical review sequence is:

1. Filter for `High` severity and `Certain` confidence.
2. Review other high-severity findings, including those with `Firm` confidence.
3. Investigate medium- and low-severity issues.
4. Review informational findings when relevant to the application's security requirements.
5. Validate findings manually before reporting them as confirmed vulnerabilities.

**Remember:** Severity and confidence describe different things. A high-severity finding is not automatically a confirmed vulnerability, and a lower-confidence result may still warrant investigation.

## 7. Generating Reports

Burp Scanner can export reports containing identified issues and supporting technical information.

### Report Generation Steps

1. Navigate to `Target → Site map`.
2. Right-click the target.
3. Select `Issue → Report issues for this host`.
4. Choose the desired export format.
5. Configure which findings and details to include.
6. Export the report.
7. Open the generated report in a web browser.

### Report Contents

Depending on the selected options, reports can include:

- Findings grouped by severity and confidence.
- Vulnerability descriptions and technical details.
- Proof-of-concept information.
- Evidence related to exploitation.
- Remediation guidance.

Reports can be customized to include only selected issues based on severity and confidence.

### Professional Reporting Best Practice

**Never submit an automatically generated scanner report as the sole final penetration testing deliverable.**

Use Burp's report as supplementary evidence or an appendix to a manually prepared report.

A professional penetration test report should interpret the findings, explain their business and technical impact, validate the evidence, and provide appropriate remediation recommendations. Raw scanner output may also help developers investigate and track issues.

## 9. Key Exam Takeaways

- **Burp Scanner is a Pro-only feature.**
- **Scope** controls which targets are included in testing.
- **Crawler** maps accessible application content by following links and interacting with forms.
- Crawling alone does not discover every unlinked resource through directory brute-forcing.
- **Passive scanning** analyzes observed content without sending new test requests.
- **Active scanning** sends additional requests and payloads to identify and verify vulnerabilities.
- `Crawl and Audit` combines crawling with vulnerability auditing.
- Authenticated crawling can expose application functionality unavailable to unauthenticated users.
- Use severity and confidence together to prioritize findings.
- Inspect the request, response, insertion point, and advisory before drawing conclusions about a vulnerability.
- Use the Logger to understand traffic generated during scanning.
- Generate reports from identified issues, but supplement automated output with manual analysis and professional reporting.
