# Skills Assessment — File Inclusion Write-Up

## Overview

The objective of this skills assessment is to assess a web application and use multiple techniques to achieve **Remote Code Execution (RCE)** and retrieve a flag located in the root directory (`/`) of the target filesystem.

### Objectives

* Identify file upload functionality.
* Discover and exploit Local File Inclusion (LFI).
* Use PHP filters to read application source code.
* Analyze file upload behavior and predict uploaded filenames.
* Bypass input validation using double URL encoding.
* Achieve RCE through an uploaded PHP web shell.
* Retrieve the flag from the root directory.

### Vulnerabilities Identified

* Insufficient file upload validation.
* Local File Inclusion (LFI).
* Improper input validation and URL decoding.
* PHP file inclusion of user-controlled input.
* Remote Code Execution through an uploaded PHP file.

---

## 1. Initial Reconnaissance

After starting the target, a welcome page is displayed. The first step is to enumerate the application and identify its available pages and functionalities.

The following pages were identified:

* `index.php`
* `contact.php`
* `apply.php`

Among these pages, `apply.php` was selected for further investigation because it contains a file upload functionality.

---

## 2. File Upload Testing

### 2.1 Identifying the Upload Functionality

The `apply.php` page contains an application form with several input fields, including a file upload field intended for submitting a resume.

Initial observations:

* No visible client-side file type validation.
* No obvious restrictions on the uploaded file extension.
* The form submits data to `api/application.php`.

### 2.2 Uploading a PHP Web Shell

To test whether the application accepts PHP files, the following PHP web shell was prepared in an authorized lab environment:

```php
<?php system($_GET["cmd"]); ?>
```

The file was uploaded through the application form.

The upload completed successfully without displaying any validation errors or warnings.

**Observation:** The application accepted the PHP file, suggesting that file type validation might be insufficient.

However, uploading a file alone did not immediately provide code execution. The next step was to determine whether the uploaded file could be included or accessed by the PHP application.

---

## 3. Initial LFI Attempt

The `thanks.php` endpoint was tested for Local File Inclusion using the `n` parameter.

```text
http://<IP>:<PORT>/thanks.php?n=<LFI_PAYLOAD>
```

### Result

* The supplied input was reflected in the response.
* No evidence of file inclusion was observed.
* No code execution was achieved.

Based on this test, the `n` parameter did not provide a confirmed LFI vulnerability.

Further enumeration was required to identify another potential inclusion point.

---

## 4. Discovering LFI in the Image API

While reviewing the page source using the browser's **View Page Source** feature (`Ctrl+U`) and Burp Suite, an API endpoint was identified:

```text
/api/image.php?p=<md5_hash>
```

The endpoint appeared to retrieve images using the `p` parameter.

### Observations

* Supplying a valid hash returned a PNG image.
* Supplying invalid input produced a blank response rather than a descriptive error.
* The parameter appeared to influence which file the endpoint accessed.

This behavior warranted further testing for file path manipulation and LFI.

---

## 5. Fuzzing for LFI

The `p` parameter was fuzzed using an LFI wordlist from SecLists.

### Command

```bash
ffuf -w <PATH>/SecLists/Fuzzing/LFI/LFI-Jhaddix.txt:FUZZ \
-u http://<IP>:<PORT>/api/image.php?p=FUZZ -fs 0
```

### Command Breakdown

| Parameter | Description                                               |
| --------- | --------------------------------------------------------- |
| `-w`      | Specifies the wordlist.                                   |
| `FUZZ`    | Marks the position where each wordlist entry is inserted. |
| `-u`      | Specifies the target URL.                                 |
| `-fs 0`   | Filters responses with a size of zero.                    |

### Result

The fuzzing process identified a traversal payload resembling the following:

```text
....//....//....//....//etc/passwd
```

Testing the discovered payload confirmed that the endpoint could read `/etc/passwd`.

**Conclusion:** Local File Inclusion was confirmed in `api/image.php`.

---

## 6. Reading PHP Source Code Using PHP Filters

After confirming LFI, PHP stream filters were used to retrieve application source code.

The following PHP filter can encode a source file as Base64:

```text
php://filter/read=convert.base64-encode/resource=<FILE_PATH>
```

### Purpose

* `php://filter` accesses PHP stream filtering functionality.
* `read=convert.base64-encode` Base64-encodes the file contents.
* `resource=<FILE_PATH>` specifies the file to read.

The resulting Base64 data can be decoded locally to inspect the source code.

This technique was used to examine `api/application.php` and `contact.php`.

---

## 7. Analyzing `application.php`

The decoded source code of `api/application.php` was:

```php
<?php
$firstName = $_POST["firstName"];
$lastName = $_POST["lastName"];
$email = $_POST["email"];
$notes = (isset($_POST["notes"])) ? $_POST["notes"] : null;

$tmp_name = $_FILES["file"]["tmp_name"];
$file_name = $_FILES["file"]["name"];
$ext = end((explode(".", $file_name)));
$target_file = "../uploads/" . md5_file($tmp_name) . "." . $ext;
move_uploaded_file($tmp_name, $target_file);

header("Location: /thanks.php?n=" . urlencode($firstName));
?>
```

### Key Observations

* The uploaded file is stored in the `../uploads/` directory relative to the script's location.
* The filename is generated using `md5_file($tmp_name)`.
* The original file extension is appended to the generated filename.
* `move_uploaded_file()` moves the uploaded file to the destination.
* The code does not visibly enforce an allowlist of permitted file extensions.

The filename-generation logic made it possible to predict the uploaded file's name from its contents.

---

## 8. Identifying the Vulnerable Inclusion in `contact.php`

The source code of `contact.php` revealed another critical vulnerability.

```php
<?php
$region = "AT";
$danger = false;

if (isset($_GET["region"])) {
    if (str_contains($_GET["region"], ".") || str_contains($_GET["region"], "/")) {
        echo "'region' parameter contains invalid character(s)";
        $danger = true;
    } else {
        $region = urldecode($_GET["region"]);
    }
}

if (!$danger) {
    include "./regions/" . $region . ".php";
}
?>
```

### Vulnerability Analysis

| Code behavior                           | Security implication                                                       |
| --------------------------------------- | -------------------------------------------------------------------------- |
| Reads user input from `$_GET["region"]` | User-controlled data influences file selection.                            |
| Checks for `.` and `/`                  | Uses a limited character blacklist.                                        |
| Calls `urldecode()` after validation    | Decoding can introduce characters that were not present during validation. |
| Passes `$region` to `include`           | User-controlled input determines the included PHP file path.               |
| Automatically appends `.php`            | The supplied path must account for the appended extension.                 |

### Root Cause

The application validates the encoded input before decoding it. Consequently, encoded path traversal characters can bypass the initial character checks and become meaningful after decoding.

Additionally, the application passes the resulting value to PHP's `include` statement without enforcing a strict allowlist of permitted region names.

**Conclusion:** The `region` parameter contains a path traversal and file inclusion vulnerability caused by weak input validation and unsafe file inclusion.

---

## 9. Exploitation Strategy

The exploitation path combines the previously identified file upload and file inclusion weaknesses.

### Step 1: Predict the Uploaded Filename

The upload handler uses the MD5 hash of the uploaded file's contents as its filename.

For the web shell used in the assessment, the reported hash was:

```text
fc023fcacb27a7ad72d605c4e300b389
```

The hash can be calculated from the exact uploaded file contents using:

```bash
md5sum shell.php | cut -d ' ' -f1
```

The command calculates the MD5 checksum and extracts the hash value.

The resulting uploaded filename follows this pattern:

```text
../uploads/<MD5_HASH>.php
```

For the example above:

```text
../uploads/fc023fcacb27a7ad72d605c4e300b389.php
```

Because `contact.php` automatically appends `.php` to the supplied region value, the intended relative path must account for that behavior.

### Step 2: Understand the URL-Encoding Bypass

The vulnerable code checks the input for literal `.` and `/` characters before calling `urldecode()`.

A double-encoded representation of the relative path is:

```text
%252E%252E%252Fuploads%252Ffc023fcacb27a7ad72d605c4e300b389
```

The encoding layers work as follows:

1. `%25` represents the percent sign (`%`).
2. The first decoding stage exposes the singly encoded characters, such as `%2E` and `%2F`.
3. A subsequent decoding stage can turn `%2E` into `.` and `%2F` into `/`.

This illustrates why validating input before canonicalization is unsafe. The exact decoding behavior depends on the request path and the application's processing layers.

### Step 3: Include the Uploaded PHP File

The `region` parameter is used to construct the path passed to `include`. When the encoded path bypasses the validation and resolves to the uploaded PHP file, PHP processes that file as part of the current request.

The web shell reads the `cmd` query parameter and passes its value to `system()`. If the inclusion succeeds and the PHP environment permits command execution, this results in server-side command execution.

### Step 4: Verify Code Execution

The assessment used a basic directory-listing command to verify that the uploaded PHP file was executing.

Successful execution demonstrates that the combined file upload and file inclusion weaknesses can lead to **Remote Code Execution (RCE)**.

## 10. Retrieving the Flag

The assessment objective required retrieving a flag located in the root directory (`/`) of the target filesystem.

After confirming RCE, the final step was to locate and read the designated flag file within the authorized lab environment.

The contents of the flag were then submitted as the assessment answer.

> **Result:** The vulnerability chain demonstrated how insufficient upload validation, LFI, weak input filtering, and unsafe PHP file inclusion can be combined to achieve RCE.

## 11. Remediation Recommendations

### 11.1 Secure File Uploads

* Allow only explicitly approved file types, such as PDF or DOCX.
* Validate file content and MIME type on the server rather than relying on the filename or client-side checks.
* Generate random server-side filenames and store uploads outside the web root.
* Prevent uploaded files from being interpreted as executable scripts.
* Enforce appropriate filesystem permissions.

### 11.2 Eliminate User-Controlled File Inclusion

* Avoid passing user-controlled input directly to `include` or `require`.
* Map user input to a fixed allowlist of permitted region identifiers.
* Reject any value that does not match an expected identifier.
* Keep included application files in a controlled directory.

For example:

```php
<?php
$regions = [
    "AT" => __DIR__ . "/regions/AT.php",
    "US" => __DIR__ . "/regions/US.php",
];

$region = $_GET["region"] ?? "AT";

if (!isset($regions[$region])) {
    http_response_code(400);
    exit("Invalid region");
}

include $regions[$region];
?>
```

This approach uses predefined file paths instead of constructing an include path from arbitrary user input.

### 11.3 Validate Canonical Input

* Decode and normalize input before validating it.
* Apply strict validation after canonicalization.
* Reject path separators, traversal sequences, and unexpected encodings where they are not required.
* Do not treat character blacklists as a substitute for safe path handling.

### 11.4 Restrict Command Execution

* Remove unnecessary uses of `system()`, `exec()`, `shell_exec()`, and similar functions.
* Run the web application with a dedicated, unprivileged service account.
* Restrict filesystem access and operating-system permissions.
* Monitor application processes for unexpected command execution.

### 11.5 Improve Error Handling and Monitoring

* Avoid exposing filesystem paths and application internals in HTTP responses.
* Log suspicious file upload and path traversal attempts.
* Monitor for unexpected PHP files in upload directories.
* Review web server and application logs for signs of command execution.

---

## 12. Key Takeaways

* File upload functionality should always be assessed for server-side validation weaknesses.
* LFI vulnerabilities can expose sensitive files and application source code.
* PHP filters can help security testers inspect source code when file inclusion is present.
* Predictable upload filenames can make uploaded files easier to locate.
* URL decoding and validation order are important when assessing path traversal protections.
* Unsafe inclusion of user-controlled paths can turn an LFI vulnerability into RCE.
* Effective remediation requires eliminating unsafe file inclusion and enforcing strict upload validation.
