# Introduction to File Inclusion (LFI)

## What is File Inclusion?

Modern web applications use **HTTP parameters** to dynamically load different pages or content instead of creating separate static pages. This makes development easier because the same template (header, footer, navigation bar, etc.) can be reused while only the main content changes.

For example:

```text
http://example.com/index.php?page=about
```

Here, the application loads the content specified in the **page** parameter.

If the application does **not properly validate or sanitize user input**, an attacker may modify this parameter to load unintended files from the server. This vulnerability is known as **Local File Inclusion (LFI)**.

---

# What is Local File Inclusion (LFI)?

Local File Inclusion (LFI) is a vulnerability that allows an attacker to read files stored on the web server by manipulating file path parameters.

LFI commonly occurs when a web application loads files based on **user-controlled input** without proper validation.

Example:

```text
/index.php?page=about
```

Instead of loading:

```text
about.php
```

an attacker may attempt to load:

```text
/etc/passwd
```

if the application is vulnerable.

---

# Where is LFI Commonly Found?

The most common place where LFI occurs is in **templating engines**.

A templating engine keeps common website components such as:

- Header
- Footer
- Navigation Bar
- Sidebar

the same across every page while dynamically loading only the page content.

Example:

```text
index.php?page=about
```

The application loads:

```text
about.php
```

based on the value of the **page** parameter.

Since the user controls this parameter, improper validation can allow arbitrary file inclusion.

---

# Why is LFI Dangerous?

LFI is considered a **critical vulnerability** because it may lead to:

- Source Code Disclosure
- Sensitive File Disclosure
- Credential Leakage
- Configuration File Disclosure
- Private Key Exposure
- Database Credential Leakage
- Application Enumeration
- Remote Code Execution (under certain conditions)
- Complete Server Compromise

Even if only source code is disclosed, attackers may discover additional vulnerabilities within the application.

---

# Common Example

Normal Request:

```text
/index.php?page=about
```

Application loads:

```text
about.php
```

Potential malicious request:

```text
/index.php?page=../../../etc/passwd
```

If vulnerable, the server may display:

```text
/etc/passwd
```

---

# How LFI Happens

The basic flow is:

```text
User Input
      │
      ▼
HTTP Parameter
      │
      ▼
Application loads file
      │
      ▼
No Validation
      │
      ▼
Arbitrary File Read (LFI)
```

---

# Vulnerable PHP Code

Example:

```php
if (isset($_GET['language'])) {
    include($_GET['language']);
}
```

### Why is this vulnerable?

The application directly passes user input into the **include()** function.

Example request:

```text
/index.php?language=en.php
```

loads:

```text
en.php
```

But an attacker may supply:

```text
/index.php?language=../../../etc/passwd
```

which causes the server to include that file if no filtering exists.

---

# Common PHP Functions Vulnerable to LFI

| Function | Reads File | Executes File | Supports Remote URL |
|----------|------------|---------------|---------------------|
| `include()` | ✅ | ✅ | ✅ |
| `include_once()` | ✅ | ✅ | ✅ |
| `require()` | ✅ | ✅ | ❌ |
| `require_once()` | ✅ | ✅ | ❌ |
| `file_get_contents()` | ✅ | ❌ | ✅ |
| `fopen()` | ✅ | ❌ | ❌ |
| `file()` | ✅ | ❌ | ❌ |

---

# NodeJS Example

Example:

```javascript
if(req.query.language) {
    fs.readFile(path.join(__dirname, req.query.language), function(err, data) {
        res.write(data);
    });
}
```

Here,

```javascript
req.query.language
```

comes directly from user input.

If no validation exists, attackers can manipulate the file path to read unintended files.

---

# Express.js Example

```javascript
app.get("/about/:language", function(req, res) {
    res.render(`/${req.params.language}/about.html`);
});
```

Instead of a GET parameter, Express.js accepts the value from the URL path.

Example:

```text
/about/en
```

or

```text
/about/es
```

If not validated, attackers may manipulate this path to include other files.

---

# Java Example

Using **jsp:include**

```jsp
<c:if test="${not empty param.language}">
    <jsp:include file="<%= request.getParameter('language') %>" />
</c:if>
```

Another example using **import**

```jsp
<c:import url="<%= request.getParameter('language') %>"/>
```

Both functions may include files based on user-controlled input.

---

# .NET Example

Using **Response.WriteFile**

```cs
@if (!string.IsNullOrEmpty(HttpContext.Request.Query["language"])) {
    <% Response.WriteFile("<% HttpContext.Request.Query["language"] %>"); %>
}
```

Using **Html.Partial**

```cs
@Html.Partial(HttpContext.Request.Query["language"])
```

Using **include**

```cs
<!--#include file="<% HttpContext.Request.Query["language"] %>"-->
```

If user input is not validated, these functions may become vulnerable to File Inclusion.

---

# Read vs Execute

One important concept in LFI is understanding whether the vulnerable function:

- Only **reads** a file
- **Reads and executes** a file

Functions that execute files are significantly more dangerous because they can eventually lead to **Remote Code Execution (RCE).**

---

---

# Why is "Execute" More Dangerous?

If a function executes the included file:

- PHP code executes
- Server-side scripts run
- May lead to Remote Code Execution (RCE)

If a function only reads the file:

- Only the file contents are displayed
- Source code can be leaked
- Sensitive information can still be exposed

---

# Key Takeaways (CPTS)

- LFI occurs when user-controlled input determines which file the application loads.
- Templating engines are one of the most common places where LFI vulnerabilities occur.
- The vulnerability exists across multiple technologies including PHP, NodeJS, Java, and .NET.
- Always determine whether the vulnerable function **reads** files or **executes** them.
- Even if code execution is not possible, reading sensitive files may expose:
  - Source code
  - Database credentials
  - API keys
  - SSH keys
  - Configuration files
- Under the right conditions, LFI can escalate into **Remote Code Execution (RCE)** and complete server compromise.
