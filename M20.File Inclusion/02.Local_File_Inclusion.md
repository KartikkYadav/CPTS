# Local File Inclusion (LFI) — CPTS Exam Notes

## 1. What is LFI?

**Local File Inclusion (LFI)** occurs when a web application uses **user-controlled input** to load a file from the local file system without proper validation.

Common vulnerable parameters include:

* `page`
* `file`
* `language`
* `template`
* `view`
* `module`

Example:

```text
/index.php?page=about
```

If the parameter controls which file is loaded, it may be vulnerable to LFI.

---

# 2. Basic LFI

A simple vulnerable PHP application may use:

```php
include($_GET['language']);
```

Since the `language` parameter is directly passed to `include()`, the application may load any accessible local file.

Example test:

```text
/index.php?language=/etc/passwd
```

Common files used to identify LFI:

| OS      | Common File           |
| ------- | --------------------- |
| Linux   | `/etc/passwd`         |
| Windows | `C:\Windows\boot.ini` |

> The goal is to understand **how the application constructs the final file path**.

---

# 3. Path Traversal

If the application adds a directory before the input:

```php
include("./languages/" . $_GET['language']);
```

A direct path may fail because the application constructs:

```text
./languages//etc/passwd
```

Use `../` to move to the parent directory.

Example:

```text
../../../etc/passwd
```

`../` means:

```text
Current Directory
      ↓
../  → Parent Directory
```

Example:

```text
/var/www/html/languages/
```

To reach `/`:

```text
../../../
```

Then access the desired file.

### Important Point

Always determine the **minimum number of `../` sequences** required.

---

# 4. Basic LFI Testing Logic

```text
Identify file-related parameter
        ↓
Test direct file path
        ↓
Check application behavior
        ↓
Try relative path traversal
        ↓
Determine prefixes/directories
        ↓
Determine appended extensions
        ↓
Test accessible local files
```

---

# 5. Filename Prefix

Sometimes the application adds a prefix:

```php
include("lang_" . $_GET['language']);
```

If the input is:

```text
../../../etc/passwd
```

The final path becomes:

```text
lang_../../../etc/passwd
```

This may fail because the prefix becomes part of the filename.

A leading `/` may sometimes change how the resulting path is interpreted:

```text
/../../../etc/passwd
```

> **CPTS Point:** Always think about the **final string generated by the vulnerable code**, not just the payload you entered.

---

# 6. Appended Extensions

Applications often append extensions automatically.

Example:

```php
include($_GET['language'] . ".php");
```

Input:

```text
/etc/passwd
```

Results in:

```text
/etc/passwd.php
```

which normally does not exist.

### Key Concept

When LFI fails, check whether the application adds:

* A directory
* A filename prefix
* A suffix
* A file extension

Understanding these modifications is essential for choosing the correct LFI technique.

---

# 7. Absolute vs Relative Paths

## Absolute Path

A complete path:

```text
/etc/passwd
```

Example:

```text
/index.php?language=/etc/passwd
```

## Relative Path

A path relative to the application's current directory:

```text
../../../etc/passwd
```

### Exam Tip

If the application's location is unknown, path traversal can be tested with multiple `../` sequences. However, use the minimum required number when documenting or developing a clean proof of concept.

---

# 8. Reading vs Executing Files

A critical concept is determining whether the vulnerable function:

* **Reads file contents**
* **Includes and executes the file**

For example, including:

```text
index.php
```

may result in:

* PHP source code being displayed, or
* PHP code being executed and HTML output being shown.

This depends on the application's file-handling function and execution context.

| Behavior  | Impact                                            |
| --------- | ------------------------------------------------- |
| Read only | Source code or sensitive data disclosure          |
| Execute   | Potential code execution under certain conditions |

---

# 9. Second-Order LFI

A **Second-Order LFI** occurs when attacker-controlled input is stored first and later used by another application function to construct a file path.

Example flow:

```text
Attacker-controlled input
        ↓
Stored in database
        ↓
Application retrieves value
        ↓
Value used in file path
        ↓
LFI triggered
```

Example scenario:

```text
/profile/$username/avatar.png
```

If an application allows a user-controlled value to be stored and later trusts that value when constructing a file path, the vulnerability may occur indirectly.

### Important Concept

Developers may sanitize direct parameters such as:

```text
?page=
```

but trust values retrieved from a database.

> **Stored data is not automatically trusted or safe.** If user-controlled data reaches a sensitive file-handling function, it must still be validated.

---

# 10. Common LFI Patterns

Look for parameters related to:

```text
?page=
?file=
?language=
?template=
?view=
?module=
?document=
?include=
```

Also investigate functionality involving:

* Language selection
* Page loading
* Templates
* Themes
* File previews
* Downloads
* User avatars
* Profile images
* Configuration files

---

# 11. CPTS Methodology

A simple methodology for LFI testing:

```text
1. Identify user-controlled file/path parameters
                ↓
2. Determine normal expected values
                ↓
3. Test direct local file paths
                ↓
4. Test path traversal with ../
                ↓
5. Analyze the application's final path
                ↓
6. Identify prefixes or directories
                ↓
7. Identify appended extensions
                ↓
8. Determine whether files are read or executed
                ↓
9. Look for second-order file inclusion
                ↓
10. Assess impact
```

# 12. Troubleshooting LFI

## Problem: Direct File Path Does Not Work

### Symptoms/Error

```text
File not found
```

### Possible Cause

The application may prepend a directory:

```php
include("./languages/" . $_GET['language']);
```

### Check

Analyze the final path and consider relative path traversal.

---

## Problem: Path Traversal Does Not Work

### Symptoms/Error

```text
Invalid file path
```

### Possible Cause

The application may add a prefix:

```php
include("lang_" . $_GET['language']);
```

or another fixed string.

### Check

Determine exactly how the application combines user input with the fixed path.

---

## Problem: Target File Has an Unexpected Extension

### Symptoms/Error

The requested file becomes:

```text
/etc/passwd.php
```

### Possible Cause

The application appends an extension:

```php
include($_GET['language'] . ".php");
```

### Check

Look for suffixes or extensions added to the user input.

---

# 13. Key CPTS Takeaways

* **LFI occurs when user-controlled input influences a local file path without proper validation.**
* Always identify the **final path constructed by the application**.
* Direct file paths may work when input is passed directly to a file-handling function.
* Use `../` to traverse to parent directories when the application prepends a directory.
* Check for **prefixes, directories, suffixes, and appended extensions**.
* Understand whether the vulnerable function **reads** or **executes** files.
* Second-order LFI occurs when attacker-controlled data is stored and later used in a file operation.
* LFI can lead to:

  * Sensitive file disclosure
  * Source code disclosure
  * Credential exposure
  * Configuration disclosure
  * Further application compromise
  * Potential code execution under specific conditions
