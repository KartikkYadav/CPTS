

# Kerberos Double Hop Problem

## 1. What Is the Double Hop Problem?

The **Kerberos Double Hop Problem** occurs when credentials used to authenticate to a remote host cannot be reused to authenticate to another resource from that host.

**Example attack path:**

```text
Attack Host → DEV01 → DC01
  (1st Hop)    (2nd Hop)
```

You can connect to `DEV01` using WinRM, but accessing `DC01` or querying Active Directory from that session may fail.

### Why Does It Happen?

- Kerberos tickets are issued for specific services/resources.
- During WinRM authentication, the remote session receives a ticket for the target service, such as `HTTP/DEV01`.
- The user's **Ticket Granting Ticket (TGT)** is not available in the remote session for authenticating to subsequent resources.
- The user's password or NTLM credentials are not cached in a way that allows them to authenticate to the next host.

**Result:** Authentication to the first host succeeds, but access to the second resource fails—even if the user has sufficient permissions.

> **Exam tip:** Authentication success does not guarantee that credentials can be delegated to another host.

---

## 2. Identify the Problem

After connecting through WinRM, try querying Active Directory with PowerView:

```powershell
Import-Module .\PowerView.ps1
Get-DomainUser -SPN
```

If the query fails with an `Operations error occurred`, the Double Hop Problem may be responsible.

Check cached Kerberos tickets:

```powershell
klist
```

If the session only has a service ticket for the current host, such as `HTTP/DEV01`, it may lack the TGT needed to authenticate to other domain resources.

---

## 3. Workaround #1 — PSCredential Object

**Best suited for:** Evil-WinRM sessions.

Create a credential object and explicitly pass it to commands that access another resource.

### Step 1: Create a Secure Password

```powershell
$SecPassword = ConvertTo-SecureString '<PASSWORD>' -AsPlainText -Force
```

### Step 2: Create the Credential Object

```powershell
$Cred = New-Object System.Management.Automation.PSCredential('DOMAIN\USERNAME', $SecPassword)
```

### Step 3: Pass Credentials to PowerView

```powershell
Get-DomainUser -SPN -Credential $Cred | Select-Object samaccountname
```

**Why it works:** The credentials are explicitly supplied for the subsequent request instead of relying on the remote session to delegate authentication automatically.

**Important:** Commands requiring access to another resource must support the relevant credential parameter.

---

## 4. Workaround #2 — Register a PSSession Configuration

**Best suited for:** Windows hosts where you have an appropriate elevated PowerShell session.

This method creates a PowerShell session configuration that runs under specified credentials.

### Step 1: Register the Configuration

```powershell
Register-PSSessionConfiguration -Name <SESSION_NAME> -RunAsCredential DOMAIN\USERNAME
```

Example:

```powershell
Register-PSSessionConfiguration -Name backupadmsess -RunAsCredential INLANEFREIGHT\backupadm
```

### Step 2: Restart WinRM

```powershell
Restart-Service WinRM
```

**Note:** Restarting WinRM disconnects existing sessions.

### Step 3: Connect Using the New Configuration

```powershell
Enter-PSSession -ComputerName <TARGET> -Credential DOMAIN\USERNAME -ConfigurationName <SESSION_NAME>
```

### Step 4: Verify Tickets

```powershell
klist
```

Look for a cached TGT:

```text
krbtgt/DOMAIN.LOCAL
```

You can then retry the Active Directory enumeration command.

### Important Limitations

- Requires appropriate administrative privileges.
- Registering the configuration can affect existing WinRM sessions.
- Not suitable for a standard Evil-WinRM session according to the HTB example.
- The configuration must be secured carefully because `RunAsCredential` changes the security context of sessions using that endpoint.

---

## 5. Unconstrained Delegation

With **unconstrained delegation**, a service can receive and cache a user's TGT under the relevant circumstances, allowing it to request service tickets on the user's behalf for other resources.

This can prevent the usual Double Hop limitation.

**Exam tip:** Unconstrained delegation is a separate Kerberos delegation mechanism, not the default behavior of WinRM.

---

## 6. Quick Comparison

| Method | Use Case | Key Requirement |
|---|---|---|
| PSCredential object | Evil-WinRM / PowerView | Explicitly pass credentials to supported commands |
| PSSession configuration | Windows PowerShell remoting | Appropriate privileges and a configured endpoint |
| Unconstrained delegation | Delegation-enabled environments | Applicable delegation configuration |
| CredSSP | Alternative delegation approach | Properly configured CredSSP |

Other possible approaches mentioned by HTB include port forwarding and using a sacrificial process.

---

## 7. CPTS Exam Quick Checklist

- [ ] Connect to the first host using WinRM.
- [ ] Attempt the required Active Directory enumeration.
- [ ] If it fails, check the cached tickets with `klist`.
- [ ] Determine whether the remote session has a usable TGT.
- [ ] In Evil-WinRM, try passing a `PSCredential` object to the relevant command.
- [ ] If using Windows PowerShell with appropriate privileges, consider a registered PSSession configuration.
- [ ] Re-run the original command to verify access.

### Commands to Remember

```powershell
# Check cached Kerberos tickets
klist

# Create a secure password
$SecPassword = ConvertTo-SecureString '<PASSWORD>' -AsPlainText -Force

# Create a credential object
$Cred = New-Object System.Management.Automation.PSCredential('DOMAIN\USERNAME', $SecPassword)

# Pass credentials to PowerView
Get-DomainUser -SPN -Credential $Cred

# Register a session configuration
Register-PSSessionConfiguration -Name <SESSION_NAME> -RunAsCredential DOMAIN\USERNAME

# Restart WinRM
Restart-Service WinRM

# Connect using the registered configuration
Enter-PSSession -ComputerName <TARGET> -Credential DOMAIN\USERNAME -ConfigurationName <SESSION_NAME>
```

## Key Takeaways

1. **Double Hop = First-host authentication succeeds, but authentication to a second resource fails.**
2. WinRM sessions do not automatically delegate the user's TGT for subsequent authentication.
3. Use `klist` to inspect cached Kerberos tickets.
4. **Evil-WinRM:** Explicitly pass credentials using a `PSCredential` object when supported.
5. **Windows PowerShell:** A registered PSSession configuration can provide an alternative when the required privileges are available.
6. Always verify that the workaround succeeds by repeating the original enumeration command.
