# Active Directory Enumeration & Attacks — Hardening Active Directory

**Module:** HTB Academy – Active Directory Enumeration & Attacks

---

## Purpose

- Goal as a pentester: help defenders get a better operational picture and improve security posture.
- **Basic hardening** does more for most orgs than buying the next big EDR/SIEM — those tools only help on top of a solid baseline (logging enabled, documentation, host tracking).

---

## Step One: Document & Audit

- Proper hardening keeps attackers **contained** — limits lateral movement, privilege escalation, and access to sensitive data.
- First step: **understand everything in the AD environment**. Audit **annually, ideally every few months**.

### Things to Document & Track
- Naming conventions (OUs, computers, users, groups)
- DNS, network, DHCP configurations
- Full understanding of all **GPOs** and what they're applied to
- **FSMO role** assignments
- Full/current application inventory
- Complete list of enterprise hosts + locations
- Trust relationships with other domains/external entities
- Users with **elevated permissions**

## People, Process, Technology Framework

### People

- Users remain the **weakest link** even in hardened environments.

**Key measures:**
- Strong password policy + **password filter** blocking common words (welcome, password, months/seasons, company name). Enterprise password manager recommended.
- **Rotate service account passwords** periodically.
- **Disallow local admin** on user workstations unless a specific business need exists.
- **Disable the default RID-500 local admin account**; create a new admin account subject to **LAPS** password rotation.
- **Split tiers of administration** — avoid one admin account used for everything (a common quick win for pentesters: finding DA creds on an admin's everyday workstation).
- **Clean up privileged groups** — restrict Domain/Enterprise Admins membership to those who actually need it.
- Place appropriate accounts in the **Protected Users group**.
- **Disable Kerberos delegation** for administrative accounts (Protected Users membership doesn't automatically do this).

#### Protected Users Group (Windows Server 2012 R2+)

```powershell
Get-ADGroup -Identity "Protected Users" -Properties Name,Description,Members
```

**Protections provided:**
- Members **cannot** be targeted with constrained or unconstrained delegation.
- **CredSSP** won't cache plaintext credentials in memory, even if "Allow delegating default credentials" is set.
- **Windows Digest** won't cache plaintext passwords.
- Members **cannot authenticate via NTLM**, and cannot use **DES or RC4** keys.
- After getting a TGT, **long-term keys/plaintext creds are not cached**.
- Members **cannot renew a TGT** beyond the original **4-hour TTL**.

**⚠️ Caution:** Can cause authentication issues / account lockouts if rolled out carelessly — **stage and test** before adding all privileged users.

### Process

- Defined policies make employees **accountable** and enable proper incident response (e.g., disaster recovery plans).

**Key measures:**
- AD asset management policies/procedures.
- Host audits, asset tags, periodic inventories.
- Access control policies (provisioning/de-provisioning), **MFA**.
- Host provisioning/decommissioning processes (baseline hardening guidelines, gold images).
- **AD cleanup policies:**
  - Are former-employee accounts **removed** or just disabled?
  - Process for removing **stale records**?
- Decommissioning process for legacy OS/services (e.g., proper Exchange removal when migrating to O365).
- Regular audit schedule for users, groups, hosts.

---

### Technology

**Key measures:**
- Run **BloodHound, PingCastle, Grouper** periodically to spot AD misconfigurations.
- Ensure admins **aren't storing passwords in the AD account description field**.
- Review **SYSVOL** for scripts containing passwords/sensitive data.
- Avoid "normal" service accounts — use **Group Managed Service Accounts (gMSA)** / **MSA** to mitigate Kerberoasting risk.
- **Disable Unconstrained Delegation** wherever possible.
- **Hardened jump hosts** to prevent direct access to Domain Controllers.
- Consider setting **`ms-DS-MachineAccountQuota` to 0** — prevents users adding machine accounts; mitigates noPac and **Resource-Based Constrained Delegation (RBCD)** attacks.
- **Disable the print spooler service** where possible (mitigates several attacks, e.g. PrintNightmare-class issues).
- **Disable NTLM authentication** on Domain Controllers if possible.
- Use **Extended Protection for Authentication** + enforce **HTTPS-only (Require SSL)** for CA Web Enrollment / Certificate Enrollment Web Service.
- Enable **SMB signing** and **LDAP signing**.
- Take steps to prevent enumeration via tools like BloodHound.
- **Quarterly** pentests/AD security assessments ideally; **annual minimum** if budget-constrained.
- **Test backups** and practice disaster recovery plans.
- Set **`RestrictNullSessAccess`** registry key to **1** to block NULL session enumeration by unauthenticated users.

## Protections by Section (TTP ↔ MITRE ATT&CK Mapping)

| TTP | MITRE Tag | Key Defense Notes |
|---|---|---|
| **External Reconnaissance** | T1589 | Very hard to detect/defend (no direct interaction with the environment). Control what's publicly released: scrub document metadata, avoid revealing tooling/naming conventions in job postings. |
| **Internal Reconnaissance** | T1595 | Active phase → generates traffic you CAN monitor. Watch for large/bursty scan traffic via Firewall/NIDS + SIEM. Tune Windows Firewall/EDR to not respond to ICMP and other probing traffic. |
| **Poisoning** (LLMNR/NBT-NS) | T1557 | **SMB signing** + strong traffic encryption stops poisoning/MITM — breaks relay attacks since signing verifies sender/recipient identity. |
| **Password Spraying** | T1110/003 | Easiest to defend/detect. Monitor **Event IDs 4624 and 4648** for strings of invalid login attempts. Strong password policy + account lockout + MFA. (See linked article and NIST docs for policy specifics.) |
| **Credentialed Enumeration** | TA0006 | No real way to block once an attacker has valid creds — they can do whatever that user can do. Detection relies on monitoring unusual activity (unexpected CLI usage, repeated RDP hops, unusual file movement). Admin-level compromise is harder to detect — network heuristics + **segmentation** help. |
| **LOTL (Living Off The Land)** | N/A | Hard to spot since it uses built-in OS tools. Requires a **baseline of normal behavior** to detect anomalies. **AppLocker** can restrict unauthorized tool/application use. |
| **Kerberoasting** | T1558/003 | Use encryption stronger than **RC4** for Kerberos. Strong password policy. **Group Managed Service Accounts** effectively eliminate the attack. Periodically audit for excessive group membership. |

## Reading MITRE ATT&CK Tags

- **TA####** = **Tactic** (overarching goal) — e.g., `TA0006` = Credential Access.
- **T####** = **Technique** within a tactic — e.g., `T1558` = Steal or Forge Kerberos Tickets.
- **T####.00#** = **Sub-technique** — e.g., `T1558.003` = **Kerberoasting** specifically (siblings: Golden Ticket, Silver Ticket, AS-REP Roasting).
- Each technique/sub-technique page includes: general explanation, platform classification, real-world examples, mitigation/detection guidance, and references.
- Full reference: the Enterprise ATT&CK Matrix.

---

## Key Takeaways

- Hardening = **People + Process + Technology** — all three matter; technology alone (EDR/SIEM) is insufficient without the baseline (documentation, logging, policy).
- **Protected Users group** and **gMSA/MSA accounts** are two of the highest-leverage technical controls against common AD attack chains (credential theft, Kerberoasting) — but require careful staged rollout.
- As a pentester, understanding these defenses helps you both **plan alternate attack paths** when they're in place and **write better remediation guidance** when they're missing.
- MITRE ATT&CK gives a standard vocabulary (Tactic → Technique → Sub-technique) for describing and mapping both attacks and their corresponding defenses — useful for report-writing and cross-referencing findings.
