# ACL Enumeration

## 1. Overview

**Access Control Lists (ACLs)** define which users or groups can perform actions on Active Directory objects.

- **ACE (Access Control Entry):** A specific permission assigned to a security principal on an object.
- **SID:** Security Identifier used to identify users and groups.
- **GUID:** Identifies a specific extended right or object type.
- **PowerView:** Useful for targeted ACL enumeration.
- **BloodHound:** Visualizes direct and transitive control relationships to identify attack paths.

> **Exam tip:** Start with a user you control and enumerate the objects and permissions associated with that user's SID.

---

## 2. Enumerating ACLs with PowerView

### Find Interesting ACLs

```powershell
Find-InterestingDomainAcl
```

This can return a large amount of data, making manual analysis inefficient.

### Get a User's SID

```powershell
Import-Module .\PowerView.ps1
$sid = Convert-NameToSid wley
```

### Find Objects Controlled by the User

```powershell
Get-DomainObjectACL -Identity * | ? {$_.SecurityIdentifier -eq $sid}
```

The `SecurityIdentifier` property identifies the principal granted the permission.

### Resolve GUIDs into Readable Rights

```powershell
Get-DomainObjectACL -ResolveGUIDs -Identity * |
  ? {$_.SecurityIdentifier -eq $sid}
```

- Without `-ResolveGUIDs`, permissions may appear as GUIDs.
- With `-ResolveGUIDs`, rights are displayed using readable names, such as `User-Force-Change-Password`.

**Example finding:** User `wley` has `User-Force-Change-Password` rights over `damundsen`.

### Alternative: Map a GUID Manually

```powershell
$guid = "00299570-246d-11d0-a768-00aa006e0529"

Get-ADObject -SearchBase "CN=Extended-Rights,$((Get-ADRootDSE).ConfigurationNamingContext)" `
-Filter {ObjectClass -like 'ControlAccessRight'} -Properties * |
Select Name,DisplayName,DistinguishedName,rightsGuid |
? {$_.rightsGuid -eq $guid} | fl
```

This GUID maps to **User-Force-Change-Password** (`Reset Password`).

> **Note:** If PowerView causes a conflict with the cmdlet, the source recommends trying a new PowerShell session.

## 3. Enumerating ACLs with Built-in PowerShell

This method is an alternative when PowerView is unavailable, but can be slower.

### Export Domain Usernames

```powershell
Get-ADUser -Filter * |
Select-Object -ExpandProperty SamAccountName > ad_users.txt
```

### Check ACLs for a Specific User

```powershell
foreach($line in [System.IO.File]::ReadLines("C:\Users\htb-student\Desktop\ad_users.txt")) {
    Get-Acl "AD:\$(Get-ADUser $line)" |
    Select-Object Path -ExpandProperty Access |
    Where-Object {$_.IdentityReference -match 'INLANEFREIGHT\\wley'}
}
```

Review the `ActiveDirectoryRights`, `ObjectType`, and `IdentityReference` fields to understand the permissions granted.

## 4. Understanding Important Permissions

| Permission | Significance in the HTB example |
|---|---|
| `User-Force-Change-Password` | Allows changing another user's password without knowing the current password. |
| `GenericWrite` | In the example, allows `damundsen` to add a member to the `Help Desk Level 1` group. |
| `GenericAll` | Broad control over an object; the example identifies potential user/group modification, password change, and targeted Kerberoasting opportunities. |
| `DS-Replication-Get-Changes` | A domain replication right relevant to DCSync. |
| `DS-Replication-Get-Changes-In-Filtered-Set` | Another replication right identified in the example's DCSync path. |

**Important:** Always assess the target object, effective permissions, and group relationships before concluding that a permission provides a usable attack path.

## 5. Follow ACL Attack Paths

The HTB example demonstrates this chain:

```text
wley
  |
  | User-Force-Change-Password
  v
damundsen
  |
  | GenericWrite
  v
Help Desk Level 1
  |
  | Nested membership
  v
Information Technology
  |
  | GenericAll
  v
adunn
  |
  | DS-Replication-Get-Changes
  | DS-Replication-Get-Changes-In-Filtered-Set
  v
Potential DCSync
```

### Step-by-Step Reasoning

1. **`wley` → `damundsen`:** `wley` has the `User-Force-Change-Password` right over `damundsen`.
2. **`damundsen` → `Help Desk Level 1`:** `damundsen` has `GenericWrite` over this group.
3. **Group nesting:** `Help Desk Level 1` is nested in `Information Technology`.
4. **`Information Technology` → `adunn`:** The group has `GenericAll` over `adunn`.
5. **`adunn` → Domain:** `adunn` has the replication rights identified in the example, indicating a potential DCSync path.

### Enumerate Group Nesting

```powershell
Get-DomainGroup -Identity "Help Desk Level 1" | select memberof
```

### Check Rights Held by `damundsen`

```powershell
$sid2 = Convert-NameToSid damundsen

Get-DomainObjectACL -ResolveGUIDs -Identity * |
? {$_.SecurityIdentifier -eq $sid2} -Verbose
```

### Check Rights Held by `Information Technology`

```powershell
$itgroupsid = Convert-NameToSid "Information Technology"

Get-DomainObjectACL -ResolveGUIDs -Identity * |
? {$_.SecurityIdentifier -eq $itgroupsid} -Verbose
```

### Check Rights Held by `adunn`

```powershell
$adunnsid = Convert-NameToSid adunn

Get-DomainObjectACL -ResolveGUIDs -Identity * |
? {$_.SecurityIdentifier -eq $adunnsid} -Verbose
```

Look for domain-level replication rights associated with the domain object.

## 6. Enumerating ACLs with BloodHound

BloodHound visualizes direct permissions, group memberships, and transitive attack paths.

### Workflow

1. Upload the SharpHound collection data to BloodHound.
2. Select the starting user, such as `wley`.
3. Open **Node Info**.
4. Review **Outbound Control Rights**.
5. Inspect **First Degree Object Control** for direct control relationships.
6. Inspect **Transitive Object Control** for potential multi-step paths.
7. Right-click an edge and select **Help** to review attack details, tools, and OPSEC considerations.
8. Use pre-built queries to investigate relationships such as DCSync rights.

### Key BloodHound Terms

| Term | Meaning |
|---|---|
| **First Degree Object Control** | Objects the principal can control directly. |
| **Transitive Object Control** | Objects reachable through chains of permissions and relationships. |
| **Outbound Control Rights** | Control relationships originating from the selected principal. |
| **Edge Help** | Details about a relationship, possible abuse methods, tools, and OPSEC considerations. |

## 7. CPTS Exam Quick Reference

| Goal | Command / Location |
|---|---|
| Find potentially interesting ACLs | `Find-InterestingDomainAcl` |
| Convert a username to SID | `Convert-NameToSid <USER>` |
| Enumerate ACLs for a SID | `Get-DomainObjectACL -Identity * \| ? {$_.SecurityIdentifier -eq $sid}` |
| Resolve permission GUIDs | Add `-ResolveGUIDs` |
| Export domain users | `Get-ADUser -Filter * \| Select-Object -ExpandProperty SamAccountName > ad_users.txt` |
| Enumerate group nesting | `Get-DomainGroup -Identity "<GROUP>" \| select memberof` |
| Visualize attack paths | BloodHound → **Node Info** → **Outbound Control Rights** |
| Investigate DCSync relationships | Inspect domain replication rights and use BloodHound's pre-built queries |

### Key Takeaways

- Use **targeted ACL enumeration** rather than relying solely on large, unfiltered output.
- Use `-ResolveGUIDs` to make permission results easier to interpret.
- Track **user permissions, group nesting, and downstream object rights**.
- A permission on a group may create indirect control through nested group membership.
- BloodHound helps visualize and validate attack paths discovered manually.
- Treat identified paths as potential opportunities; validate the effective permissions and conditions before relying on them.
