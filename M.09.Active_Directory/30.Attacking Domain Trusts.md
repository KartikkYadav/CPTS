Attacking Domain Trusts – Cross-Forest Trust Abuse (Windows)
1. Cross-Forest Kerberoasting
Concept:
- Kerberoasting can be performed across domain/forest trusts, depending on trust direction and permissions.
- If a trust is inbound or bidirectional, we may be able to request Kerberos service tickets from the target domain.
- Crack the TGS hash offline to obtain credentials of privileged users in the target domain.
- A compromised account may have Domain Admin or Enterprise Admin privileges in multiple domains.
Step 1: Enumerate Accounts with SPNs
Use PowerView to find accounts with Service Principal Names (SPNs) in the target domain.
Get-DomainUser -SPN -Domain FREIGHTLOGISTICS.LOCAL | select SamAccountName


Example output:
samaccountname
--------------
krbtgt
mssqlsvc


Step 2: Check Account Group Membership
Determine whether the SPN-associated account has privileged group membership.
Get-DomainUser -Domain FREIGHTLOGISTICS.LOCAL -Identity mssqlsvc |
select samaccountname,memberof


Example:
mssqlsvc    CN=Domain Admins,CN=Users,DC=FREIGHTLOGISTICS,DC=LOCAL


Important finding
 The mssqlsvc account is a member of Domain Admins.
Step 3: Perform Cross-Forest Kerberoasting
Use Rubeus with the /domain flag to target the trusted domain.
.\Rubeus.exe kerberoast /domain:FREIGHTLOGISTICS.LOCAL /user:mssqlsvc /nowrap


Important parameters:
Parameter	Description
kerberoast	Perform Kerberoasting
/domain	Specify target trusted domain
/user	Target specific SPN account
/nowrap	Output hash without line wrapping

Example hash format:
$krb5tgs$23$*mssqlsvc$FREIGHTLOGISTICS.LOCAL$...


Step 4: Crack the Hash Offline
Save the extracted hash and crack it using Hashcat.
hashcat -m 13100 hash.txt wordlist.txt


Result: If the password is cracked, we can authenticate as the target account and potentially obtain Domain Admin access to the trusted domain.

2. Admin Password Reuse & Group Membership
A. Password Reuse Across Forests
Concept:
- Administrators sometimes reuse passwords across trusted domains/forests.
- If Domain A is compromised, obtain cleartext passwords or NT hashes of privileged accounts.
- Check whether privileged accounts in Domain B reuse the same password.
- Account names may differ between domains, so don't rely only on matching usernames.
Example:
Domain A	Domain B
adm_bob.smith	bsmith_admin
Domain Admin	Highly privileged user
Password reused	Same password

Exam takeaway: Always check password reuse for privileged accounts across bidirectional forest trusts.
B. Foreign Group Membership
Concept:
- Domain Local Groups can contain security principals from outside their domain/forest.
- A privileged account from Domain A may be added to a Domain Local group in Domain B.
- If that group grants administrative privileges, compromising the external account can provide administrative access to Domain B.
Example:

An Administrator from INLANEFREIGHT.LOCAL is a member of the built-in Administrators group in FREIGHTLOGISTICS.LOCAL.
Step 1: Enumerate Foreign Group Membership
Use PowerView:
Get-DomainForeignGroupMember -Domain FREIGHTLOGISTICS.LOCAL


Look for:
- Foreign security principals.
- Privileged groups such as Administrators.
- Accounts belonging to another trusted domain.
Step 2: Resolve the SID
Foreign group membership may appear as a SID instead of a username.
Convert-SidToName S-1-5-21-3842939050-3880317879-2865463114-500


Example output:
INLANEFREIGHT\administrator


Finding: The built-in Administrator account from INLANEFREIGHT.LOCAL belongs to the Administrators group in FREIGHTLOGISTICS.LOCAL.
Step 3: Verify Access Using WinRM
Use PowerShell Remoting to authenticate against the target Domain Controller.
Enter-PSSession -ComputerName ACADEMY-EA-DC03.FREIGHTLOGISTICS.LOCAL -Credential INLANEFREIGHT\administrator


Verify access:
whoami


Expected output:
inlanefreight\administrator


Result: Successfully authenticated to the FREIGHTLOGISTICS.LOCAL Domain Controller using an Administrator account from INLANEFREIGHT.LOCAL.

Key takeaway
 Always enumerate foreign group memberships when assessing bidirectional forest trusts.

3. SID History Abuse – Cross-Forest
Concept
SID History can be abused across forest trusts when SID Filtering is not enabled.
- When users are migrated between forests, their previous SIDs can be stored in the SIDHistory attribute.
- If SID Filtering is disabled, SIDs from the trusted forest may be accepted during authentication.
- An attacker can abuse this by adding a privileged SID from Forest A to a user in Forest B.
- The user's authentication token may then contain the privileged SID from Forest A.
Example Scenario
Forest A	Forest B
INLANEFREIGHT.LOCAL	CORP.LOCAL
User: jjones	Migrated user: jjones
Original privileged SID	SID stored in SIDHistory

If the original user had administrative privileges in Forest A and SID Filtering is not enabled, those privileges may be retained when accessing resources in Forest A from the migrated account.

Important conditions:
1. A forest trust exists.
2. SID Filtering is not enabled.
3. The attacker can control an account with the required SIDHistory value.
4. The account can authenticate across the trust.
Remember
 SID Filtering is a security mechanism designed to prevent unauthorized SIDs from crossing trust boundaries.

Detailed SID History exploitation is covered in the AD Trust Attacks module.

Key Exam Takeaways
- Kerberoasting: Check SPN accounts in trusted domains, especially privileged accounts.
- Password Reuse: Check whether privileged accounts across forests share passwords.
- Foreign Group Membership: Look for external Domain Admins in target Domain Local Administrators groups.
- SID History: Check whether SID Filtering is disabled across forest trusts.
- Bidirectional Trust: Can provide opportunities to move laterally and escalate privileges across forests.
- Always enumerate both directions of a trust and identify which accounts can authenticate across it.
