# External Recon and Enumeration Principles

**Module:** HTB Academy (AD-focused track) — Section 4/36

---

## Why External Recon?

Performed before kicking off a pentest. Purposes:
- **Validate** info in the client's scoping document.
- **Confirm appropriate scope** when working remotely.
- **Find public info** that could affect the test — e.g., leaked credentials.

Goal: get the "lay of the land" for the most comprehensive test possible, including spotting info leaks/breach data (username formats from a website or social media, up to deep dives like scanning GitHub for leaked creds or hunting documents for intranet links).

---

## What Are We Looking For?

| Data Point | Description |
|---|---|
| **IP Space** | ASN, netblocks, cloud presence/hosting providers, DNS record entries |
| **Domain Information** | Domain admin, subdomains, public-facing domain services (mail, DNS, websites, VPN portals), visible defenses (SIEM, AV, IPS/IDS) |
| **Schema Format** | Email/AD username conventions, password policies — fuel for building a username list (password spraying, credential stuffing, brute force) |
| **Data Disclosures** | Public files (.pdf, .ppt, .docx, .xlsx) revealing intranet listings, user metadata, shares, hardware/software info, or creds pushed to a public GitHub repo |
| **Breach Data** | Publicly released usernames/passwords/critical info that could grant a foothold |

---

## Where Are We Looking?

| Resource | Examples |
|---|---|
| ASN / IP registrars | IANA, ARIN (Americas), RIPE (Europe), BGP Toolkit |
| Domain Registrars & DNS | Domaintools, PTRArchive, ICANN, manual DNS queries (e.g. against 8.8.8.8) |
| Social Media | LinkedIn, Twitter, Facebook, regional platforms, news articles |
| Public-Facing Company Websites | News, embedded docs, "About Us"/"Contact Us" pages |
| Cloud & Dev Storage Spaces | GitHub, AWS S3 buckets, Azure Blob storage, Google Dorks |
| Breach Data Sources | HaveIBeenPwned (corporate emails in breaches), Dehashed (cleartext passwords/hashes to test against AD-auth portals: Citrix, RDS, OWA, O365, VPN, VMware Horizon, custom apps) |

## Finding Address Spaces — BGP Toolkit (Hurricane Electric)

- Search a domain or IP → reveals assigned address blocks and ASN.
- Large corporations often **self-host** and have their **own ASN**; smaller orgs typically host on third-party infrastructure (Cloudflare, GCP, AWS, Azure).

### Scope Caution
- Must know exactly **what infrastructure is in scope** — on shared/third-party infra, you risk impacting other tenants.
- Your agreement is with the **client**, not with others sharing the same server/provider.
- Third-party hosting may require **separate written approval** (varies by provider — AWS has specific self-service guidelines for some services; Oracle requires a Cloud Security Testing Notification).
- **When in doubt, escalate** — clarify scope in writing before attacking any uncertain external-facing service.

---

## DNS Recon

- Validates scope; can reveal reachable hosts **not disclosed** in the scoping document.
- Tools: **domaintools**, **viewdns.info** — DNS resolution, DNSSEC testing, geographic/firewall accessibility checks.
- May surface **out-of-scope hosts** (bring to client to potentially add) or **undisclosed subdomains on in-scope IPs** (fair game, since they live on in-scope infrastructure).

### ViewDNS.info Tools
Reverse IP Lookup, Reverse Whois Lookup, IP History, DNS Report, Reverse MX Lookup, Reverse NS Lookup, IP Location Finder, DNS Propagation Checker, Whois, etc. — good for **validating** ASN/IP findings (info can go stale).

## Public Data Sources

### Job Postings (LinkedIn, Indeed, Glassdoor)
- Reveal technology stack, maturity of security program, and even **specific software versions** in use.
- Example: a "SharePoint Administrator" listing mentioning security programs/backup & DR implies a mature SharePoint deployment — possibly **SharePoint 2013/2016** (upgraded in place), meaning older version vulnerabilities may still be present.

### Company Websites
- Contact emails, phone numbers, org charts, published documents.
- Embedded documents can leak **links to internal infrastructure/intranet sites**.

### Unintentional Leaks — Cloud/Dev Platforms
- Devs may accidentally commit credentials/notes into code pushes.
- Tools: **Trufflehog** (secret scanning), **Greyhat Warfare** (public S3 bucket search).
- Can turn hours/days of password spraying into an **instant foothold** via leaked (sometimes elevated) dev credentials.

**Further reading:** *Footprinting* and *OSINT: Corporate Recon* modules for deeper OSINT coverage.

## Overarching Enumeration Principles

- Enumeration = **iterative process**, repeated throughout the engagement.
- Process: start with **passive** recon (wide scope → narrow down) → examine results → move into **active** enumeration.
- Primary info sources: the scoping document + everything found through recon — leave no stone unturned.

## Example Enumeration Walkthrough — inlanefreight.com

### 1. ASN/IP & Domain Data (BGP.he.net)

Findings:
- IP Address: `134.209.24.248`
- Mail Server: `mail1.inlanefreight.com`
- Nameservers: `NS1.inlanefreight.com`, `NS2.inlanefreight.com`
- No dedicated ASN found (expected — not a large corp).

### 2. Validate with ViewDNS (Reverse IP)

- Confirms the IP matches; also surfaces another domain sharing the same IP (`lycjg.us`) — worth noting but scope-checking before acting on it.

### 3. Validate Nameservers with nslookup

```bash
nslookup ns1.inlanefreight.com
# ns1.inlanefreight.com → 178.128.39.165

nslookup ns2.inlanefreight.com
# ns2.inlanefreight.com → 206.189.119.186
```

- New IPs discovered — **must confirm in-scope status** before active testing; passive browsing may still be fine even if scanning isn't authorized.

### 4. Document Hunting (Google Dorks)

```
filetype:pdf inurl:inlanefreight.com
```

- Found a PDF ("corporate goals and strategy"). **Always save a local copy** of any document, screenshot, or tool output as soon as found — preserves evidence and avoids losing track of sources.

### 5. Email Address Hunting

```
intext:"@inlanefreight.com" inurl:inlanefreight.com
```

- Found a staff contact page listing emails → reveals the org's **naming convention** (`first.last`) and office locations.
- Useful for: password spraying target lists, and social engineering/phishing if in scope.

### 6. Username Harvesting — linkedin2username

- Scrapes a company's LinkedIn presence to generate username permutations: `flast`, `first.last`, `f.last`, etc. → feeds password spraying target lists.

### 7. Credential Hunting — Dehashed

```bash
sudo python3 dehashed.py -q inlanefreight.local -p
```

- Searches breach data for cleartext credentials/hashes tied to the target domain.
- Example fields returned: `email`, `username`, `password`, `name`, `database_name` (source breach).
- Often yields **stale/non-working** passwords for AD-auth portals, but occasional hits are valuable.
- (Example data in the module is fictional; Dehashed's API changes over time — verify script compatibility.)

## Key Takeaways

- External recon blends **ASN/IP research, DNS validation, social media, company websites, dev/cloud leak-hunting, and breach-data mining** — all passive until scope is explicitly confirmed.
- **Document everything immediately** — files, screenshots, tool output — as you find it.
- A realistic, battle-tested fallback when stuck on internal enumeration: build a **wordlist from external OSINT sources** (Google dorking, LinkedIn scraping, Dehashed) and run **targeted password spraying** to obtain a foothold — even low-privilege domain credentials open up the majority of internal AD enumeration and many attack paths.
- Always confirm scope before any active/intrusive action, especially on third-party-hosted infrastructure — escalate in writing when uncertain.
